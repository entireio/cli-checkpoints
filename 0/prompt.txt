### 1. The check is per-`Load`, but the decision is consumed once — `opf_command_trust.go:115`

`pathIsVersioned` forks 2–3 `git` processes (`ls-files`, `rev-parse`, `ls-tree`). It runs inside `loadMergedSettings`, and `settings.Load` has **29 non-test call sites with no caching**. A pre-push hook for an OPF user hits several of them (`manual_commit_push.go:140`, `strategy/hooks.go:634`, `manual_commit_hooks.go:493,2071`, `checkpoint_remote.go:78`, `checkpoint/remote/util.go:90,200,323`), so the cost is roughly 10–30 extra `git` forks on the hook path to answer a question consumed exactly once, at `strategy/common.go:459`.

The `if opf.Command == ""` early return at `opf_command_trust.go:45` is the right guard and means default users pay nothing — this is scoped correctly. But OPF users are precisely the ones paying, and this repo tracks hook latency closely.

**Deeper fix, without giving up the altitude:** memoize `pathIsVersioned` for the process lifetime, keyed on the absolute path. The answer cannot meaningfully change mid-hook, the result is a bool, and it collapses N loads to one probe. That keeps the loader as the choke point and removes the only real cost of choosing it over the point of use.

### 2. The "did the developer own this key" predicate already exists, weaker, guarding a different hazard — `settings.go:1453` vs. `opf_command_trust.go:86`

`CheckpointRemoteIsLocalOnly(ctx)` (settings.go:1442-1467) answers the *same* question — "is this key present in `.entire/settings.local.json`?" — with:

- a different implementation shape (exported, ctx-taking, raw-map walk via `LoadLocalRaw`) vs. the new unexported byte-parser with its own inline `sub` closure;
- a **strictly weaker** check: filename only, no tracked-ness. Its doc comment claims the file "cannot have arrived by cloning or forking someone else's project" — which is precisely the claim `opf_command_trust.go:29-33` explains is false, because `.gitignore` does not apply to an already-tracked path.

This is not cosmetic. Its one caller, `checkpointRemoteIsInherited` (`checkpoint/remote/util.go:412`), uses local-only presence to **skip** the guard that stops checkpoints being pushed to a differently-owned repo. So the weaker predicate gates a data-exfiltration decision, and the new code documents why it is insufficient without touching it.

**Deeper fix:** one predicate, e.g. `settings.KeyIsDeveloperOwned(ctx, keyPath ...string) (bool, error)` in the settings package, doing the raw-map walk *and* the index+HEAD check, with both call sites on it. Two callers is enough to justify the abstraction, and consolidating closes the weaker one for free.

On the broader "untrusted-source fields" registry: **don't build it.** I swept the settings surface for other exec exposure — `ReviewConfig.Agent/Model/Skills` (settings.go:392-414), `InvestigateConfig.Agents` (424), `SummaryGenerationSettings.Provider` (219), `ReviewFixAgent` (125), `ExternalAgents` (138). None is `argv[0]` from a settings string. A generic mechanism would have exactly one member. The single-field gate is correctly scoped; only the *local-ownership predicate* wants generalizing.

- `LoadFromFile` → **ungated**; callers are `status.go:142,151` (display; `formatSettingsStatus` prints only enabled/disabled) and seven `setup.go` + `checkpoint_backend.go:93` writer paths. None reaches exec.
- `LoadFromBytes` → **ungated**; callers are `investigate/cmd.go:477` (local read-modify-write) and `strategy/push_common.go:315` (reads only `GetCheckpointRemote`). Neither reaches exec.
- `LoadProjectRaw`/`LoadLocalRaw` → raw maps, no typed `Command`.
- Only consumer reaching `exec`: `strategy/common.go:459`, which uses gated `Load`. ✓

So the gate holds — but the ungated loaders would leak it the moment someone builds an OPF config from a scoped file read, which is exactly what `setup.go`'s convention does for every other field. The CLAUDE.md bullet is a documentary guard.

**Deeper fix (cheap, proportionate):** a test in the `strategy` package asserting `strategy/common.go:459` is the only non-settings read of `.OpenAIPrivacyFilter.Command`, or a `forbidigo` rule — the repo already uses that pattern to pin `gitrepo.Status` as the sole `worktree.Status()` call site (`.golangci.yaml`). Making it mechanical costs ~10 lines and converts "don't do this" into "you can't."

### 5. Silent in-place reset is the weakest of the four choices — `opf_command_trust.go:82`

`opf.Command = ""` makes a *demoted* value indistinguishable from a *never-set* one for every downstream reader, including writers. The concrete cost is at **`setup.go:651-665`**:

```go
s, loadErr := LoadEntireSettings(ctx)   // gated + merged
...
saveErr = SaveEntireSettingsLocal(ctx, s)  // full-struct overwrite of settings.local.json
```

`SaveLocal` → `saveToFile` (settings.go:1575) marshals the whole struct and atomically overwrites the file. So if `pathIsVersioned` ever returns "cannot verify" — git not on `$PATH`, which is the exact GUI-git-client population `AbsoluteGitHookPath` (settings.go:96) exists to serve, and the same population that most needs an absolute `command` because `$PATH` isn't sourced — the user's own legitimate `command` is dropped from the struct and then persisted away. The only notice is a `logging.Warn` into `.entire/logs/entire.log`. Meanwhile `entire status` renders the local file through ungated `LoadFromFile`, so status and reality can silently disagree.

Note this call site is also the outlier in its own file: `setup.go:175`, `212`, `271`, `300`, `1899`, `2285` all load the *scoped target file* via `LoadFromFile` before saving it back, and `saveEnabledState`'s comment (setup.go:1519-1527) explicitly warns against writing a merged struct into a scoped file. Line 651 does the thing that comment forbids; the gate turns a known leak into a lossy one for a security setting.

**Deeper fix, two parts:**
1. Keep zeroing `Command` (fail-closed for consumers that don't know to check — that property is worth keeping), but *also* record the rejection: an unexported, non-serialized `commandRejected string` on `OPFSettings`, surfaced by `entire doctor` and `entire status`. Right now the user's only feedback that their configured filter binary is being ignored is a log file they won't read, on a path whose whole point is that failing open is unacceptable.
2. Move `setup.go:651` onto the file's own convention (`LoadFromFile(targetFileAbs)` + `saveSettingsToTarget`), which removes the write-back hazard for `command` and for every other field the merged struct carries.

This is the one place where "surface provenance and let the consumer decide" beats mutate-in-place, and it costs one unexported field.

## Not findings

- Gating on `opf.Command == ""` before any git work is the correct guard and keeps the default path free. Good call.
- Treating verification failure as untrusted (`opf_command_trust.go:57-59`) is the right direction, and the reasoning that "outside a repo there is no push" is sound.
- Checking index **and** `HEAD` independently, and handling unborn HEAD as a definitive negative (`opf_command_trust.go:129-132`), is correct and the tests cover the `git rm --cached` case that the index check alone would miss.
- I considered and rejected "make `command` an env var only (`ENTIRE_OPF_COMMAND`)" as the simpler design. It fails for the same reason `absolute_git_hook_path` exists: GUI git clients don't source shell profiles, so neither `$PATH` nor an env var reaches the hook. A file-based, developer-owned setting is genuinely required for that population, which makes the local-file channel necessary rather than incidental.</result>
