## Q1 — Hot-path cost: fast path is cheap; one configuration is not

Benchmarked in a real repo with the `WorktreeRoot` cache warm (M4 Pro, 2000 iters):

| state | per gate call |
|---|---|
| un-set-up repo, no global file (**every user today**) | 6.8 µs (old predicate: 12.1 µs — delta is noise) |
| repo **is** set up | unchanged code path |
| global mode on, no `exclude_origins` | 21.7 µs |
| global mode on **with** `exclude_origins` | **10.9 ms** |

The fast path stays cheap for a structural reason worth recording: `IsSetUpAny` → `paths.AbsPath` → `paths.WorktreeRoot` already warms the per-process cwd-keyed cache before `GlobalModeActive` needs it, so the global tier adds **no** extra `git rev-parse` fork on any route. In dark launch the entire added cost is one ENOENT `os.ReadFile`.

The outlier is `exclude_origins`: `gitremote.GetRemoteURLInDirIfSet` forks `git config --get` with no caching, ~500× the fast path, and it runs on **every** gate evaluation. See Important #1.

## Issues

### Important

**1. `exclude_origins` makes each gate evaluation a ~11 ms fork; ×2 per hook invocation ≈ 22 ms — needs memoization before `enable --global` ships.** `settings/global.go:188` (via `gitremote.go:110`).
Not a blocker for *this* commit — nothing writes the global settings file yet, so the path is unreachable in the dark-launch state, exactly as the commit message claims. But hooks fire on every prompt and every tool event, so once `enable --global` lands this is ~22 ms of pure `fork`/`exec` per event for any user who configures origin excludes. Memoizing `GlobalModeActive` per process is the natural fix and has no invalidation problem, since hooks are one-shot processes (`sync.OnceValue` or a package-level memo). Recommend tracking it explicitly against PR 3 rather than as a general "optimize later", because it becomes user-visible latency the moment the writer command exists.

## Issues

### Important

**1. Repo-level `entire enable` on an already globally-tracked clone permanently orphans `.git/entire/worktree/` — must be handled by the PR that ships `enable`.** `paths/invisible.go:96-107`.
Once `.entire/settings.json` exists, `computeInvisibleRuntimeBase` returns `""` and every previously-written session metadata, prompt, and transcript under `.git/entire/worktree/` becomes unreachable — an in-flight session silently loses its pending checkpoint data. This is not the bounded in-process cache staleness from Q5 (see Minor #4); it's a permanent routing flip with no migration or read-through. Unreachable in the dark-launch state since nothing writes the global settings file, so not a blocker here — but it needs an explicit task on the `enable --global` PR, same treatment as slice 3's memoization item.

### Minor

**2. `AbsPath` resolves `WorktreeRoot` twice on every runtime-data path.** `paths/paths.go:119-127`.
`invisibleRuntimeBase` calls `WorktreeRoot`, then the main body calls it again when `base == ""` (the repo-enabled case) — two `os.Getwd()` syscalls per resolution, and the entire measured 1.2 µs delta over baseline. Resolving the root once up front and passing it into `invisibleRuntimeBase` removes both. Negligible in absolute terms; it's free to fix and removes the redundancy from the hot path.

**3. Q2 — the prefs read before `IsSetUpAny` costs microseconds, so reorder for clarity, not performance.** `strategy/global_setup.go:24-37`.
Measured at 5.0 µs total for a repo-enabled repo, because `ClonePreferencesPath` → `session.GetGitCommonDir` is cwd-cached and the gate's `settings.Load` immediately prior has already warmed it — so the marginal cost is one small `readConfined` inside `.git/`. The spec reviewer's flag is real but not a perf problem. Moving `IsSetUpAny` first is a one-line move with zero risk and makes the 99% case zero-IO, so I'd do it now rather than fold it into slice-3 memoization.

**4. Q5 — in-process staleness is bounded and in the safe direction.** `paths/invisible.go:74-92`.
Hook processes are one-shot, so the window is negligible. Long-lived path-resolving processes (`entire mcp` stdio server, `review`, `dispatch`) hold a stale decision for their lifetime, but the stale direction is *toward* the common dir, so the worst case is reads finding an empty location until restart — never a worktree write, never corruption. Acceptable; the single-entry root-keyed design also matches `WorktreeRoot`'s existing precedent.

**5. `writeHookFile` is non-atomic and this commit widens its exposure.** `strategy/hooks.go:364-376`.
`os.WriteFile` truncates in place, so a process killed mid-write can leave a truncated `commit-msg`, and a `commit-msg` exiting non-zero **aborts the user's commit**. The code is unchanged and pre-existing — but it used to run only from interactive `entire enable`; it now runs inside hook processes that are routinely killed when an agent exits. Worth a follow-up to make it temp-file + rename, given the new caller.

**6. Q4 — the settings-file basenames are now duplicated asymmetrically.** `paths/invisible.go:28-30`, `:130`.
`SettingsFileName` is shared via `paths`, but `settings.local.json` is re-declared (`settingsLocalFileName`, cycle documented) and `"settings.json"` for the *user* settings file is a bare literal tied to `settings.UserSettingsFileName` only by a comment. The asymmetry is what makes it confusing rather than the duplication itself. Acceptable for one commit; moving all three basenames into `paths` (which everything already imports) is the cheap fix if a fourth duplicate appears.

**7. Comment nits.** `paths/invisible.go:119-128` — the divergence *safety argument* is worth keeping (a maintainer needs it before "fixing" the duplication), but the closing "The reverse divergence … i.e. never" is proof-by-exhaustion that belongs in the commit message. `paths/invisible.go:149-151` — "Local copy of session.GetGitCommonDir" undersells and slightly misleads: it is a *corrected* copy (absolutizes properly, doesn't cache), and calling it a copy invites a future unification back onto the weaker relative-path behavior. State what differs.

**8. Test gaps.** The OpenCode and Pi tmp-cache conversions have no test asserting they route. I verified both by reading — `fetchAndCacheExport` does `MkdirAll` on the routed dir (`opencode/lifecycle.go:215`), and `sessionTranscriptPath` only computes a path that `PrepareTranscript` → `fetchAndCacheExport` later creates, so there's no missing-directory bug — but nothing pins it. Separately, on the porcelain-timing question: the harness runs the hook binary synchronously and the only detached spawn on this path is `__send_analytics` (telemetry → userdirs/network, never the worktree), so nothing can land after the assertion today; but the harness doesn't wait for detached children, so a *future* detached worktree write would slip past both assertions.

**9. Unrelated whitespace change** — `gitremote/gitremote.go:140` drops a stray blank line, unrelated to this commit's subject.

## Issues

### Important

**1. `disable --global --uninstall` silently skips the uninstall.** `setup.go:1128-1131`.
Verified with the built binary: exit 0, prints `Global tracking disabled.`, and `.entire/` plus the git hooks are left completely intact. The user explicitly asked to remove Entire from the repository and is told something succeeded. `--global` branches before the `if uninstall` check, so the destructive request evaporates. One line fixes it:
```go
cmd.MarkFlagsMutuallyExclusive("global", "uninstall")
```
(also worth doing for `global`/`project` and `global`/`force`).

**2. `enable --global` silently ignores every repo-scoped flag.** `setup.go:829-834`.
Verified: `--agent claude-code`, `--local`, `--yes`, and `--init-repo --repo-name foo` each produce *only* the machine-wide toggle — exit 0, no agent hooks installed, no `.entire/`, no warning. `entire enable --global --agent claude-code` is a natural thing to type expecting both effects. Mark `global` mutually exclusive with the repo-scoped and bootstrap flags so cobra rejects the combination with a clear message.

**3. Migration has no cross-device fallback, and the summary doesn't say where the leftovers went.** `setup_global.go:196-198`.
`os.Rename` fails with `EXDEV` when the git common dir and the worktree are on different filesystems — reachable via `--separate-git-dir` or a linked worktree on another volume. The file then counts as `failed` with no copy+delete fallback. I confirmed failed files *are* retained in the source (forced a rename failure via an unwritable destination), so this is not data loss — but routing has already flipped, so nothing will ever read them again, and the one-line summary names neither the source directory nor a remedy. Add an `io.Copy` + remove fallback on rename failure, or at minimum print the source path when `failed &gt; 0`.

### Minor

**4. The migration summary is prefixed with `✓` even when it reports failures.** `setup_global.go:203-211`.
Actual output from my forced-failure probe:
```
  ✓ Moved 1 globally-tracked session file(s) into .entire/, 1 could not be moved
```
Every other `✓` line in this file (`setup.go:328`, `:1349`, `:1355`, `:2031`) is an unqualified success, so the checkmark reads as "all good" when it isn't. Drop or swap the prefix when `failed &gt; 0`. (`file(s)` itself is fine — matches `session(s)`/`label(s)` elsewhere.)

**5. Migration runs before `.entire/.gitignore` exists.** `setup.go:1278-1281` (and the non-interactive copy at `:1923-1926`) vs `setupEntireDirectory` → `EnsureEntireGitignore` (`setup.go:2129`).
If `setupEntireDirectory` fails immediately after a successful migration, `.entire/{metadata,logs,tmp}` sit in the worktree *un-ignored* — transcripts and prompts visible in `git status`, precisely the state this feature exists to prevent. Narrow (needs an IO failure) and self-healing on the next enable, but moving the migration call to just *after* `setupEntireDirectory` keeps it well before the settings write and removes the window entirely.

**6. `maybeAskGlobalTracking` swallows a non-cancel form error with no message and no debug log.** `setup_global.go:87-89`.
Staying silent on Ctrl-C is right — "Global tracking cancelled." mid-wizard would be noise, and the docstring explains that saving nothing lets a later enable re-ask. But a genuine form failure vanishes entirely, where the local pattern is `handleFormCancellation` and slice 2 established `logging.Debug` for swallowed side-path failures. One debug line would make it consistent.

**7. Strict decoding now blocks a writer path on forward-incompatible files.** `setup_global.go:26-29`.
Once a newer binary adds a key, an older `entire enable --global` fails with `cannot update user settings: parsing user settings: json: unknown field "…"`. This is the downstream cost of the (correct) slice-1 tradeoff, now user-visible on a command people will run. The message at least names the field; adding "upgrade entire, or remove that key" would make it self-service.

## Verdict

**Needs fixes** — scoped narrowly to the flag exclusivity. Issue #1 is a silent no-op on an explicitly destructive, user-requested action (`disable --global --uninstall` reports success and uninstalls nothing), and #2 is the same class across the enable surface; both are `MarkFlagsMutuallyExclusive` one-liners in the onboarding path, which is exactly where a silent half-apply does the most damage. Everything else here is genuinely good work — the atomic hook write, the memoization with tests that pin the interesting direction, and the migration's conflict/re-run semantics all hold up under mutation testing — and issues #3–#7 are all reasonable follow-ups rather than blockers.</result>

so are these not addressed? "Catch in hooks when the path is a different entire-enabled repo" — designed, parked. Tool events carry file paths; the resolver maps each path to its git common dir and notices "not my repo." This is the activity-time binding layer (also what fixes #1439 and #529). "How do we link sessions — or is the session just in both repos?" — answered in the design: it's in both, linked by the shared session ID. On first evidence in repo B, the session state replicates (additively — never moved, source never retired) into B's .git/entire-sessions/ under the same ID. Every repo's checkpoints reference that one ID; no cross-repo pointer graph needed.

"Store in each repo if a commit happens there / track which repos were looked at" — designed: state is pre-positioned at bind time, so when a commit happens in repo B, B's own hooks find the session locally and the trailer machinery works unchanged. Each repo touched in a turn gets a checkpoint with its own diff; a machine-level session record keeps the bound-repo list. "Duplicate the data, make the API/backend unduplicate" — the sharpest catch, and it's recorded as a hard prerequisite in the spec: self-contained checkpoints mean a two-repo session stores the transcript in both repos' v1 branches.
