## The defect

`PushQueuedCheckpointRefs` (`cmd/entire/cli/strategy/manual_commit_push.go:428`) flushes the checkpoint-ref push queue with no OPF (OpenAI Privacy Filter) gate. Its only production caller is the migration command's opt-in push (`cmd/entire/cli/doctor_migrate.go:100`), so with `redaction.openai_privacy_filter.enabled` set, answering yes to the "Push N migrated checkpoint ref(s) now?" prompt sends 8-layer content to the remote, untagged.

The pre-push path a few lines above does gate it:

```go
// prePushCheckpointRefs, manual_commit_push.go:399
if redact.OPFEnabled() && !runOPFForCheckpointRefs(ctx, repo) {
    return nil
}
```

`PushQueuedCheckpointRefs` goes straight from the checkpoint-policy check to `flushCheckpointRefsQueue`, and that function has no OPF or redaction call of its own, so nothing downstream compensates.

## Why it matters, stated precisely

Un-OPF'd content reaching the remote is not itself the bug. `runOPFForCheckpointRefs` (`manual_commit_push.go:239`) has three outcomes: `OPFRun` rewrites, `OPFAbort` withholds, and `OPFSkip` deliberately flushes 8-layer content as-is and untagged when the user opts out for that push. The bug is that this path hard-codes the skip outcome without the decision ever being resolved or surfaced. A user who enabled OPF and never chose to skip gets the skip anyway.

The two answers to one prompt have opposite safety:
- No: "Refs stay queued for the next push", and the next `git push` goes through `prePushCheckpointRefs`, which applies OPF.
- Yes: they go now, without it.

## Scope

- git-refs checkpoint backend only. The `entire/checkpoints/v1` branch has its own OPF rewrite at pre-push and is unaffected.
- Needs `redaction.openai_privacy_filter.enabled` plus an interactive confirmation, so not unprompted. But the prompt says nothing about redaction, so there is nothing for the user to notice.
- Pre-existing. Not introduced by any currently open PR. Found while security-reviewing #2211, which is unrelated to it.

Verified by reading current `origin/main`: the gate exists at `:399` and is absent at `:428`; `flushCheckpointRefsQueue` contains no OPF/redact reference; `doctor_migrate.go:100` is the sole production caller; the four existing tests (`strategy/refs_push_test.go:208,230,258,285`) cover push-disabled, policy-blocked, and failure-leaves-refs-queued, none cover OPF.

On the pre-push side the same misplacement prints the `→ OpenAI Privacy Filter: scanning… (~30s)` line on every non-TTY push with an empty queue.

This is the concrete payoff of finding 1, not a separate fix: put the gate after `flushCheckpointRefsQueue`'s `len(queued) == 0` / `len(existing) == 0` early returns (lines 485, 499) and the class disappears for both callers at once.

**One tension to resolve explicitly, not silently:** `OPFNoCategoriesError`'s doc (opf_rewrite.go:~230) states the v1 decision gate runs "with no knowledge of whether anything is unpushed, so a misconfigured repo aborts every push — including one with nothing to rewrite." ### 3. `push_common.go:58` and `:168` — a genuine cross-backend chokepoint exists, and the invariant worth enforcing there is a *postcondition on the trailer*, not "was the gate called"

Both backends converge: git-refs goes `flushCheckpointRefsQueue` → `batchPushRefs` (push_common.go:58); git-branch goes `prePush` → `pushRefIfNeeded` → `doPushRef` → `tryPushRefCommon` (push_common.go:168, 364) → `remote.Push`. The check that belongs there is not "did someone call a gate" but the property the gate is supposed to produce, which the data already self-describes: every commit OPF has processed carries `Entire-OPF-Applied: true`, and `trailers.HasOPFApplied` already serves as the watermark in `unappliedAncestry` (opf_refs.go:192). One commit-object read per ref, negligible next to a network round-trip, and backend-agnostic by construction.

**Recommendation:** do finding 1 now (small, closes the refs backend); file the egress assertion as the follow-up that closes it for both. **Tradeoff:** the assertion needs a memoized per-process decision so an intentional `OPFSkip` is distinguishable from a missing gate — that plumbing is the real cost, and it is why this is a follow-up and not a blocker on this diff.

Note the asymmetry the diff creates in the meantime: the refs backend now has a named, documented gate whose comment says *"Every path that flushes the queue must pass through here"*, while the v1 backend's identical logic is still 35 lines inline in `prePush` (lines 139-174). Either extract the symmetric `opfGateForV1` or say in the doc that v1 keeps its own copy — as written, a reader can reasonably read `opfGateForCheckpointRefs` as *the* OPF gate.

### 4. `manual_commit_push.go:246-248` — the asymmetric failure behaviour lives in prose in a doc comment, one level away from the two branches that implement it

The gate's doc says *"Reporting belongs to the caller: the pre-push hook warns and carries on… while an explicitly requested push surfaces the error instead."* Nothing in any signature or type says that. A future reader has to hold three files open — the gate's doc (246), the pre-push caller's `return nil` (409), and the migrate caller's `fmt.Errorf` (456) — and reconstruct that the difference is intended rather than an oversight. That is precisely the reconstruction the original bug represents: someone read `PushQueuedCheckpointRefs` and did not reconstruct that a gate was owed at all.

**Recommendation:** name the two behaviours as the policy values from finding 1 (`opfWithholdQuietly` / `opfSurfaceError`), each with a one-line doc carrying the *reason* ("a checkpoint failure must never block the user's git push" / "this push was explicitly requested"). The asymmetry then appears at the call site as a word the reader can look up, and the prose in the gate's doc shrinks to a pointer. **Tradeoff:** two more identifiers; in exchange the invariant and its two sanctioned failure directions are stated once, in the type, where they cannot drift apart.

### 5. Guard test: **not warranted here** — the repo's guard-test precedent exists for constraints the type system cannot express, and this one it can

`TestGitStatusCallSitesPassNoOptionalLocks` (gitrepo/gitstatus_guard_test.go), `TestRootBasesAreTrusted` (osroot/rootbase_guard_test.go), and `TestEntireDirCheckExemptions` all guard things a signature cannot: a string flag buried in a variadic argv, an allowlist of files permitted to call a constructor, a set of annotations. A "did you call the gate" grep-guard for `flushCheckpointRefsQueue` would be strictly weaker than the required parameter in finding 1 — it fails after the fact instead of at compile time, it needs its own staleness detector (the `checked == 0` bail-out), and it would be defeated by any caller that wraps the flush in a helper.

If a source-level guard is wanted anyway, the practical shape is not "callers pass through the gate" but the finding-3 property expressed as a **behavioural** test in `refs_push_test.go`, alongside the two the diff already adds: a table over every exported entry point that can push checkpoint content (`PrePush`, `PrePushFromGitHook`, `PushQueuedCheckpointRefs`) asserting that with OPF enabled and a failing OPF the remote receives nothing, and with a working OPF everything on the remote carries the trailer. Adding an entry point without a row is visible in review in a way an omitted call-site check is not; and unlike a grep-guard it survives refactoring the internals. **Tradeoff:** it costs a real git fixture per row (the diff's two new tests already pay that), versus a grep-guard's near-zero runtime and near-zero value here.
