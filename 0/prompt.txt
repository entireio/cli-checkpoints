before we start, a report from a coworker:

1. Capture persists on push intent, fully decoupled from delivery. (New — most significant.)
Capture runs at the top of the gate block, before the policy gate (checkpointPolicyAllowsGitHook), the OPF decision, the empty-remote deferAutomaticCheckpointPush, and the actual transfer — and none of those roll it back. For git-refs the flush is explicitly fail-soft ("refs left queued"). So a push to a declared remote that then delivers nothing — policy diverged, OPF abort, empty-remote defer, or a rejected/failed transfer — still permanently flips the election off origin. The queued checkpoints can now only drain to the newly-captured remote; if that remote is why delivery failed, they're stranded there until it works, even though origin was fine a moment ago.

2. A stale branch.<name>.remote reroutes sync off origin on a single push, permanently.
git push -u fork (even long ago) sets branch.X.remote=fork forever. The next checkpoint-carrying push to fork captures it, and first-capture-sticks makes the origin-sync loss permanent without manual config. Not exotic — the PR's own integration helper relies on push -u to establish exactly this declaration.

3. git remote rename/removal of a captured remote silently relocates sync and locks out re-capture.
Fail-soft falls through to origin (good — sync isn't disabled), but the stale entry keeps len(loadCapturedSyncRemotes) > 0, so the renamed remote can never be re-captured. Checkpoints stop reaching the remote the user actually pushes to, with no status hint. (This is the stale-capture-lockout I raised as a question; it's worth re-classing as a concrete "stops pushing where you push" path.)

4. declaredPushDestination reads HEAD's branch, not the pushed refspec.
git push fork side:side while on main evaluates main's declaration. A mismatch mis-captures based on the wrong branch, and that mis-capture then gates the correct remote's future pushes. Documented phase-1 simplification, but the failure mode is "wrong remote elected → the right remote's checkpoints stop."

5. (Restating, distinct) The merge gate is about readability, not pushing. Capturing fork before #1956/#1951 land means checkpoints are pushed to fork but can't be read back (resume/explain resolve via origin). Different axis from the above.

Net: none of these harm the push in front of them, and overall sync fail-softs rather than fail-closes — but #1 and #2 mean the election can move off a working remote based on a single push that carried nothing, and #3 means it can then get stuck there. The mitigation that would close most of it: persist capture only after a checkpoint actually reaches the remote, and self-heal the state file by dropping entries whose remote is no longer configured.

### 1. `maybeCaptureCheckpointSyncRemote` resolves the same election three times per pre-push
`cmd/entire/cli/strategy/checkpoint_sync_capture.go:129-151` (snapshot root: `…/scratchpad/wctx`)

Each load = 1 git subprocess + 1 `os.ReadFile`. `settings.Load` is likewise re-run per resolve (up to 3 file reads + parse + validate each), on top of the one in `resolvePushSettings`.

The commit's own rationale ("the two must agree on what a captured entry means") is better served by not having two: the resolver already answers the question.

```go
elected, err := ResolveCheckpointSyncRemote(ctx)

    return // fail-closed on unreadable settings / bad checkpoint_push_remote

switch elected.Source {

}
```
