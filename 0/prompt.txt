## Tolerance / fallback: none

- **No decode-error catch in the CLI:** the error flows `Client.sendXxx` → `fetchAllPages` (`corecmd.go:195`, returns `nil, err`) → `renderCoreList` (`corecmd.go:170`) → command `RunE`. It is surfaced as a top-level command failure (wrapped as `"validate: ..."`). This is true for both table output and `--json`.
- **No "unknown"/"unspecified" enum member** in any of the four enum constant blocks.
- **No custom `UnmarshalJSON` override** beyond the generated ones (which delegate to the lenient `Decode`) — but the lenient decode is moot because `Validate()` runs afterward and rejects.
- **No `x-ogen` extension, no `SkipValidation`/`infer-types` option** anywhere in `internal/coreapi/` (grep found nothing). Validation is hard-wired into every response decoder.

## Conclusion

Both commands are exposed to a **hard failure** if the server returns a newer enum value:

- `mirror list` fails if any mirror's `status` is not one of `processing|ready|failed|suspended`.
- `repo list` fails if any repo's `objectFormat` ∉ `{sha1,sha256}`, `state` ∉ `{provisioning,active,failed}`, or `visibility` ∉ `{public,private}`.

Because these are optional (`Opt*`) fields, a value being *absent* is safe; the hazard is strictly an unknown *present* value. A single offending item aborts the entire list request (the whole page fails to decode/validate), and pagination is not partially recoverable. The failure originates in `oas_validators_gen.go`, not `oas_json_gen.go` as the premise assumed — the Decode methods here are lenient, so any future mitigation (e.g. skipping validation, or treating unknown as passthrough) would need to address the `Validate()` call in the response decoders rather than the `Decode` methods.</result>
