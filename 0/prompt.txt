## Type: `RepoPolicy` (`repopolicy/types.go:92`)

### Invariants identified
- `Active == (ActivationSource != ActivationInactive)`; `InactiveReason == None` iff `Active`. Three fields encode one three-valued state.
- `WorktreeRoot`, `GitCommonDir`, `WorktreeKey` are a copy of a `Repository` and must agree with it (`WorktreeKey == runtimeKey(worktreeid)`).
- When `ActivationSource == Global`, `GitCommonDir` and `WorktreeKey` are non-empty (otherwise `RuntimeRoot()` returns `""`).
- `Trust` is meaningful only when `Active`; `ClassifyActivationAt` deliberately leaves it zero.
- Snapshot semantics: once attached via `WithRepoPolicy`, treated as immutable.

### Ratings
- **Encapsulation: 3/10** — all fields exported; `hook_policy.go:25-30` rewrites `Active/ActivationSource/InactiveReason` by hand outside the package. Nothing prevents `Active: true, ActivationSource: ActivationInactive`.
- **Invariant expression: 6/10** — the `RuntimeRoot()` doc and the `ClassifyRepoPolicyAt` precedence comment are excellent; the redundancy of `Active` + `ActivationSource` + `InactiveReason` is not expressed anywhere.
- **Invariant usefulness: 8/10** — a single classification snapshot on `ctx` is exactly the right shape for a hook process; `RuntimeRoot()` being a pure function of the source is the load-bearing design and it is right.
- **Invariant enforcement: 4/10** — enforced only inside `classifyActivationAt`/`ClassifyGlobalConfig`. `RuntimeRoot()` has no guard: a Global policy with empty `GitCommonDir` yields `""`, and `paths.runtimeRootForPath` (`invisible.go:79`) hands that straight back, so `filepath.Join("", "metadata", ...)` becomes a CWD-relative path — one session split across roots, the exact failure `ErrUnroutableRuntimePath` exists to prevent. Today only reachable from a literal, but there is no check standing between a future refactor and that outcome.

### Strengths
- Value type, cheap to copy, context-carried; the "never persisted" contract is stated at the type.
- `ClassifyActivationAt` vs `ClassifyRepoPolicyAt` split (no egress for foreign roots) is a real invariant captured in the API rather than a flag.

### Concerns
- **Real bug risk (low probability, high blast radius):** `RuntimeRoot()` can return `""`. Add a guard that returns an error or panics on incomplete Global identity, or make `paths.runtimeRootForPath` reject `""` with `ErrUnroutableRuntimePath`. Cost: ~5 lines.
- Mixing three concerns (activation, repo identity, trust) is defensible for a snapshot, but the identity triple should be the `Repository` value itself, not three copied strings — `DecideEgress(ctx, policy, global, repository)` already takes both, so they can disagree.
- `hook_policy.go` reaches in and flips three fields. That is the one place the invariant is maintained by an outside caller.

### Recommended improvements
1. Replace `Active bool` with a method `func (p RepoPolicy) Active() bool { return p.ActivationSource != ActivationInactive }` (or keep the field but make `InactiveReason` the only source of truth). Cost: mechanical rename across ~15 call sites; removes a whole class of literal-induced inconsistency.
2. Embed `Repository` instead of copying three fields: `RepoPolicy{ Repository; ActivationSource; InactiveReason; Trust }`. `RuntimeRoot()` becomes `p.Repository.GlobalRuntimeRoot()`; `DecideEgress` drops a parameter. Cost: small, one-time.
3. Give `hook_policy.go` a package method, e.g. `func (p RepoPolicy) Deactivated(reason InactiveReason) RepoPolicy`, so the outside caller cannot half-update the tuple. Cost: trivial.

## Type: `TrustIdentity` (`types.go:53`)

### Invariants identified
- Exactly one of `OriginKeys` (non-empty) or `Path` (non-empty) is set — "the flip is whole".
- `OriginKeys` are deduplicated, normalized `host/owner/repo`, lowercased.
- `RemoteName`/`Dedicated` are display-only and do not participate in matching.
- Zero value = "identity unresolved" (used under `trust_all` when resolution fails, and on `RepoTrustIdentity` error).

### Ratings
- **Encapsulation: 4/10** — exported slice and strings; a literal `{OriginKeys: [...], Path: "..."}` is representable and `identityTrusted` would then silently take the origin branch only.
- **Invariant expression: 6/10** — the doc comment is precise; the struct shape says "any combination".
- **Invariant usefulness: 9/10** — the exclusivity rule and the all-URLs-must-be-listed rule are the security core of the feature and both are correct.
- **Invariant enforcement: 6/10** — `ResolveTrustIdentity` enforces exclusivity and normalization correctly; no other constructor, but nothing stops literals. `DisplayScope()` on the zero value returns `""`, which status/prompt then render as an empty scope.

### Strengths
- `OriginKeyed()` + `DisplayScope()` are the right minimal accessors; callers (`trust_prompt.go:92-97`, `setup.go:1518`, `trust_cmd.go:94`) only use these plus `RemoteName`.
- Path fallback on *any* unparseable URL (rather than partial key set) is the correct fail-closed choice and is tested.

### Concerns
- **Display fields beside the matching key**: `RemoteName`/`Dedicated` are harmless functionally, but they make the type's equality meaningless and blur "what is the consent key". This is a style/clarity issue, not a bug. A cleaner split is `TrustKey` (origins | path) and `TrustIdentity{ Key TrustKey; Remote SyncRemote }`, or just keep `SyncRemote` on `TrustDecision` instead.
- The JSON tags (`origin_keys`, `path`, `remote`, `dedicated`) have no user in the tree — dead surface that implies a serialization contract nobody honors.
- Zero value doubling as "unresolved" means `status --json` can emit `sync_remote: ""` and the prompt can fall back to "this folder only" wording when in fact resolution failed. It is not wrong, but an explicit `Resolved bool`/`error` would make the three states (origin/path/unknown) visible.

### Recommended improvements
1. Make the key a two-case sum: `type TrustKey struct{ origins []string; path string }` with unexported fields and constructors `OriginKey(keys)`/`PathKey(root)`. Cost: moderate (the settings writer `TrustCurrentRepo` iterates `OriginKeys`; expose `Origins() []string`). Benefit: exclusivity becomes unrepresentable-to-violate.
2. Drop the JSON tags until something serializes it. Cost: zero.
3. Cheaper alternative if you keep the flat struct: add `func (id TrustIdentity) valid() bool` and assert it at the end of `ResolveTrustIdentity` (a test-time tripwire). Cost: 3 lines.

## Type: `TrustDecision` (repopolicy, `types.go:72`)

### Invariants identified
- `Allowed =&gt; Source ∈ {Local, All, Repo} &amp;&amp; Reason == None`.
- `!Allowed =&gt; Source == None &amp;&amp; Reason ∈ {Inactive, Untrusted, InvalidOrigin, Settings}`.
- `Identity` is set whenever it resolved, regardless of `Allowed`; empty under `Inactive`, `InvalidOrigin`, `Settings`.

### Ratings
- **Encapsulation: 3/10** — four exported fields; `Allowed: true, Source: None` is representable.
- **Invariant expression: 5/10** — `Allowed` is redundant with `Source != None`; reason/source are two half-enums of one outcome.
- **Invariant usefulness: 8/10** — `Source` drives real UX (banner under `trust_all`, `not_applicable` while tier is off) and `Reason` drives diagnostics.
- **Invariant enforcement: 7/10** — `DecideEgress` builds every value correctly and `TrustSourceLocal` is correctly restricted to "tier off".

### Concerns
- **Name collision (style, but a real reading hazard):** `strategy.TrustDecision` (an `int` enum: `TrustHeld`/`TrustGranted`, `trust_prompt.go:18`) and `repopolicy.TrustDecision` (this struct) share a name across two packages that both appear in `manual_commit_push.go`. Rename the strategy one `TrustPromptOutcome` (or `promptResult`). Cost: trivial.
- `computeRepoTrustState` (`status.go:271`) discards `Reason`, so `status --json` cannot distinguish "untrusted" from "user settings file unreadable" (`TrustReasonSettings`) from "election failed" (`TrustReasonInvalidOrigin`). The information exists in the type and is thrown away on the way out. Usefulness gap, cheap to fix (`trust_reason` field).

### Recommended improvements
1. Collapse to `Outcome TrustSource` where `TrustSourceNone` means held, and derive `Allowed()`; keep `Reason` for the held case. Cost: small; removes an impossible state.
2. Surface `Reason` in `globalTrackingJSON`. Cost: 3 lines.

## Type: `RepoActivation` (`types.go:121`) and `ReadRepoActivation` (`activation.go:50`)

### Invariants identified
- `Enabled` is meaningful only when `Configured`.
- `LocalOverride =&gt; Configured`, and the effective `Enabled` came from a trusted `settings.local.json` with an explicit key.
- A local file without an `enabled` key never sets `Configured`.
- A tracked/symlinked local file is ignored wholesale (via `LocalSettingsTrusted`).

### Ratings
- **Encapsulation: 4/10** — three bools, any combination constructible; `Enabled: true, Configured: false` is representable and only safe because `policy.go` checks `Configured &amp;&amp; Enabled`.
- **Invariant expression: 7/10** — the type comment explains the "set up" notion clearly; `LocalOverride` is well named for its one consumer (the exclusion bypass at `policy.go:99`).
- **Invariant usefulness: 8/10** — `LocalOverride` encodes exactly the trust-relevant fact ("the developer's own action on this clone outranks user exclusions, cloned content does not"); that is the right distinction and it is tested.
- **Invariant enforcement: 7/10** — `ReadRepoActivation` is the sole producer and is correct, including the null-`enabled` case.

### Concerns
- Three bools are really a four-state enum: `NotConfigured | ProjectEnabled | ProjectDisabled | Local{enabled bool}`. Modeling it as `type RepoActivation int` (or a small struct with `Source ActivationFile` + `Enabled`) would make `LocalOverride &amp;&amp; !Configured` unrepresentable. Style preference; the code is correct as is.
- `LocalOverride` is set to `!isProject` even when no project file exists, so the name "override" is slightly off — it means "came from local", not "overrode project". The doc comment says the right thing; the identifier does not.

### Recommended improvements
- Rename to `FromLocal` or `LocalDecided`. Cost: trivial. Or fold into an enum as above; cost: small, two call sites.

## Type: `Repository` (`repository.go:18`)

### Invariants identified
- `WorktreeRoot` and `GitCommonDir` are absolute, symlink-canonicalized.
- `WorktreeKey == runtimeKey(WorktreeID)` (16 hex chars).
- `GlobalRuntimeRoot()` returns `""` when identity incomplete.

### Ratings
- **Encapsulation: 4/10** — `WorktreeKey` is a derived field that can be set independently of `WorktreeID`.

1. Delete `RuntimeDir`. Cost: zero.
2. Drop `WorktreeKey` as a field; compute it in `GlobalRuntimeRoot()` from `WorktreeID` (or unexport and expose `Key()`). Cost: small; removes a derivable-field inconsistency.

## Types: `SyncRemote`, `SyncRemoteResolver`, and the seams `ResolveSyncRemote` / `LocalSettingsTrusted` (`sync_remote.go`, `activation.go:32`)

### Invariants identified
- `Name == ""` ⇔ no remote ⇒ `URLs` empty ⇒ path identity.
- `URLs` deduplicated; in `Dedicated` mode exactly one derived URL.
- Seams: the real implementations are installed by `settings` (init) and `strategy` (init); the defaults are weaker/different.

### Ratings
- **Encapsulation: 3/10** — the two seams are exported mutable package globals with no mutex, no `Set…ForTesting` accessor, and no way to tell whether the real implementation is installed.
- **Invariant expression: 7/10** — both defaults document exactly why they exist and what differs; `trust_sync_remote.go` explains the cycle.
- **Invariant usefulness: 8/10** — keying consent on the elected remote rather than `origin` is the right invariant, and routing it through one resolver is the right seam.
- **Invariant enforcement: 4/10** — see concerns.

### Concerns (this is the most important design question in the PR)
- **Link-dependent semantics.** `settings` imports `repopolicy` but does not link `strategy`. Every test in `settings` (e.g. `TestTrustCurrentRepoAndRevoke`) therefore runs against the *origin* default, not the election. Any future binary or test package that uses `settings.CheckpointEgressAllowed` without linking `strategy` silently gets pre-election semantics — a consent keyed on `origin` while checkpoints go elsewhere. Today the CLI binary links `strategy`, so production is correct, but the correctness is a property of the link graph, not of the type. Same for `LocalSettingsTrusted`: the repopolicy default (symlink-only) is strictly weaker than the installed one (index + HEAD + symlink), so a repopolicy-only test can pass a case production rejects, or vice versa.
- **Silent unguarded globals.** Tests in both packages reassign the vars and restore in `t.Cleanup`. Correct today only because those specific tests do *not* call `t.Parallel()` while `TestEgressDecision_LocalActivationIsGatedWhileGlobalIsOn` and `TestReadRepoActivation` (which read the seams) do — Go's sequential-then-parallel ordering happens to serialize them. CLAUDE.md says "always use `t.Parallel()`"; the first person who obeys that on one of the seam-mutating tests introduces a `-race` failure. Contrast `paths/invisible.go`, which wraps its test seam in an `RWMutex` — the package is inconsistent with itself.
- `Dedicated` on `SyncRemote` and again on `TrustIdentity` is the same fact copied twice.

### Recommended improvements (ordered by value/cost)
1. **Make "real resolver not installed" loud.** Keep the var but have the default *fail* (`errors.New("repopolicy.ResolveSyncRemote not installed")`) in non-test builds, or record `installed bool` and have `ResolveTrustIdentity` return an error when it is false and `!testing.Testing()`. Cost: ~10 lines. Benefit: converts a silent semantic downgrade into a hard error — this is the one change I would call a real bug-risk reduction.
2. **Replace the bare vars with `Set…ForTesting(fn) (restore func())` accessors guarded by a mutex**, mirroring `paths.SetInvisibleProbeFailureForTesting`. Cost: ~20 lines plus two test call sites. Removes the latent `t.Parallel` race.
3. Longer term: pass a `Resolver` interface through `ClassifyRepoPolicyAt` (a `PolicyDeps{SyncRemote, LocalTrusted}` param with a `Default()` in `settings`). Cost: touches every `ClassifyRepoPolicy` caller (~10). Worth it only if a third seam appears; the accessor approach is the pragmatic stop.

## Type: `UserSettings` (`types.go:209`, `user_settings.go`)

### Invariants identified
- `Global == nil` ⇔ unconfigured tier.
- `global` block strict; other top-level blocks preserved byte-for-byte in `extra`.
- Whole file is one JSON value (trailing-data check).

### Ratings
- **Encapsulation: 8/10** — `extra` is unexported; the only mutation path is `ModifyUserSettings` (locked, atomic write). Good.
- **Invariant expression: 9/10** — type and method docs state the per-block rule and its reason.
- **Invariant usefulness: 9/10** — forward-compat for mixed-version machines without weakening consent decoding is exactly the right trade.
- **Invariant enforcement: 7/10** — see the receiver issue.

### Concerns
- **Real bug risk (latent):** `MarshalJSON` has a pointer receiver. If any caller ever marshals a `UserSettings` *value* (embeds it by value in another struct, or `json.Marshal(*us)`), `encoding/json` will not find the method, will emit only `global` and **silently drop every preserved block**. Nothing today does that (`persistUserSettings` passes `*UserSettings`), but the failure is silent and destructive to another binary's settings. Make `MarshalJSON` a value receiver (it only reads). Cost: one token.
- `extra` is a map, so copying a `UserSettings` aliases it; harmless because the type is only produced by `LoadUserSettings` and consumed under the lock.
- `"global": null` is skipped on read and not preserved in `extra`, so a round-trip drops the key. Negligible.

## Types: `ActivationSource`, `TrustSource`, `TrustReason` (string) vs `InactiveReason` (int)

- **Consistency (style, but it leaks into the API):** three of the four enums are strings with stable wire values and are emitted directly (`string(info.ActivationSource)`); `InactiveReason` is an `int` and needs a hand-written `inactiveReasonJSON` mapper in `status.go:1139` plus `globalInactiveHereText`. Pick one. Strings with stable values are the better fit here since they *are* already a public JSON contract; make `InactiveReason` a string enum with the JSON values it already maps to (`repo_excluded`, `repo_disabled`, `global_off`) and delete the mapper. Cost: small; the `settings` package re-exports the constants so callers do not change.
- **Zero values:** `ActivationSource("")` is not a member (the zero is not `ActivationInactive`), so a zero `RepoPolicy` has an out-of-domain source. `TrustReasonNone == ""` and `InactiveReasonNone == 0` are the zero — inconsistent. Prefer making the zero value the "none/inactive" member for every enum so a zero struct is at least well-formed.
- `InactiveReasonGlobalOff` is overloaded: it is also what `classifyActivationAt` returns when `git rev-parse` fails and what `ClassifyGlobalConfig` returns on a nil resolver. `status.go` sidesteps this via `PolicyError`, but the type itself cannot say "unknown". A `InactiveReasonUnknown`/`ClassificationFailed` member would let the reason stand alone. Cost: one constant + two returns.
- `TrustSourceLocal = "local_activation"` is really "global tier off" (the only way an active repo can hit it). The name reads as "activated locally", which is also true of a repo-enabled repo *with* the tier on — where the source is `repo` or `trust_all`. `TrustSourceTierOff` would be truthful. Style.

## Summary: real bug risks vs. style

**Real bug risks (fix in this PR or a fast follow):**
1. `UserSettings.MarshalJSON` pointer receiver — a value marshal silently drops preserved blocks. One-token fix.
2. Seam defaults are silent semantic downgrades that depend on the link graph (`settings` tests already run on the wrong resolver). Make an uninstalled `ResolveSyncRemote` fail loudly outside tests.
3. Bare mutable seam vars + `t.Parallel()` house rule = latent `-race` failure. Wrap in mutex-guarded `Set…ForTesting` (as `paths` already does).
4. `RepoPolicy.RuntimeRoot()` can return `""` and `paths.runtimeRootForPath` forwards it — guard at either end.
5. `ResolveCheckpointSyncRemoteForTrust` mislabels an override as `config` source.
6. Dead `RuntimeDir()` duplicates `GlobalRuntimeRoot()` without its guard — delete.

**Usefulness gaps (cheap):**
- `trust_reason` lost from `status --json`; `InactiveReason` cannot say "unknown".

**Style / structure (worth doing, not blocking):**
- Derive `Active` from `ActivationSource`; embed `Repository` in `RepoPolicy`; enum `RepoActivation`; string-typed `InactiveReason` with the JSON values; rename `strategy.TrustDecision`, `TrustSourceLocal`, `LocalOverride`; drop unused JSON tags on `TrustIdentity`; split display fields (`RemoteName`, `Dedicated`) from the matching key or accept them as documented.

**1. New unconditional pre-push count gate silently disables checkpoint sync for every repo, including tier-off ones, when the count fails**
`/Users/peytonmontei/dev/entire/devenv/entireio/cli/.worktrees/global-settings-tier/cmd/entire/cli/strategy/manual_commit_push.go:197-206`

```go
pendingCheckpoints, pendingErr := CountUnpushedCheckpoints(ctx, ps.remote)
if pendingErr != nil {
    logging.Warn(ctx, "could not determine pending checkpoints; holding checkpoint sync", ...)
    return nil
}
if pendingCheckpoints == 0 {
    return nil
}
```

This block is new in the PR (main's `prePush` has no count) and runs *before* `gateCheckpointEgress`, so it applies to users who never configured the tier and to already-trusted repos. The comment justifies the silent hold with "checkpoint egress must never make the user's branch push fail or consume Git's stdin" — that rationale covers the *prompt*, not the *push*. On main, a repo whose `git rev-list` / push-queue read fails still attempted the push (`pushRefIfNeeded` / `flushCheckpointRefsQueue`, which print their own stderr line on failure). Now the push is skipped with only a `.entire/logs` Warn: nothing on stderr, nothing in `status` (which computes its own count independently). Because `git rev-list --invert-grep` is a subprocess on every push, a transient failure becomes a silent stall until the next successful count.

Secondary effect of the `== 0` early return: `cleanupPushedShadowBranches` (line 331 / 528) and `deferCheckpointPushOnEmptyRemote` no longer run on pushes with nothing pending, so shadow branches of already-pushed checkpoints accumulate until a push with pending data — a small state drift from main.

Fix: only count when a consent decision is actually needed, and treat a count failure as "unknown, proceed" when consent is already granted:
```go
if !settings.CheckpointEgressAllowed(ctx) {
    n, err := CountUnpushedCheckpoints(ctx, ps.remote)
    if err != nil { warn; return nil }   // hold only affects an untrusted repo
    if n == 0 { return nil }
    if ctx, ok = gateCheckpointEgress(ctx, pendingCapture); !ok { return nil }
}
```
and keep the cleanup call reachable on the zero path. Also print one stderr line on the count-failure hold (the same shape as the other holds in this function), since `status` cannot see it.

## Critical

### C1. Adoption's 2s lock budget is passed into the foreign repo's status walk, latching `statusBudgetBreached` process-wide and degrading capture in the *source* repo

`binding_adopt.go:81` caps `lockCtx` at `bindingAdoptLockTimeout = 2s`, and that same ctx is threaded into `buildReplicatedSessionState(lockCtx, …)` (`:91`) → `targetUntrackedFiles(ctx, repo)` (`:171`) → `gitrepo.StatusWithBudget(ctx, repo)` (`:172`).

`StatusWalkBudget` is 20s (`gitrepo/status.go:53`), but `statusWithBudget` treats `&lt;-ctx.Done()` exactly like a timer breach: it sets the process-local latch (`gitrepo/status.go:124-126`), and `statusWithBudget` then fails fast on *every subsequent* call in the process (`:96-99`). So any foreign repo whose walk takes longer than the ≤2s left on the adopt ctx will:

1. return `nil` untracked — swallowed silently at `binding_adopt.go:174` (no Debug line), so `UntrackedFilesAtStart` for the adopted repo is wrong; **and**
2. poison the source repo's own turn: the later `DetectFileChanges` → `StatusWithBudget` in `handleLifecycleTurnEnd` returns `ErrStatusBudgetExceeded`, new-file detection is skipped, and `CaptureDegradedAt` is set — for a repo whose walk was perfectly healthy.

Adoption runs on the **ToolUse** hook, so this fires before the user's turn-end. A 2-second go-git walk is unremarkable on a medium repo with a cold page cache; this is not an exotic trigger.

Fix: keep the 2s cap on *lock acquisition only*. Give the state build its own ctx — `context.WithoutCancel(ctx)` (or the caller's hook ctx) — so `StatusWithBudget` gets its intended 20s and its own latch semantics. Separately, log the swallowed error at Debug in `targetUntrackedFiles` so a nil untracked baseline is diagnosable.

### C2. A linked worktree of the *same clone* is adopted and replayed as if it were a separate repo — two hook processes then race one shared session-state file

The "not foreign" skip keys on the worktree root only (`binding_tap.go:168`), by design ("a different worktree of the same clone … IS recorded"). `ensureSessionReplicated` then guards with `sameAdoptPath(currentWorktreeRoot, ev.Repo.WorktreeRoot)` (`binding_adopt.go:53`) — also worktree-root-keyed. **There is no guard comparing the evidence's `CommonDir` against the current repo's `CommonDir`.**

Consequence for a sibling worktree of the same clone:

- `targetStore` is `&lt;CommonDir&gt;/entire-sessions` — byte-identical to the source's store (`session/state.go:822-832`; global-tracking.md confirms session state stays in `.git/entire-sessions` regardless of activation source).
- Inside the lock, `existing != nil` (it *is* the source state), so `ensureSessionReplicated` writes nothing, calls `MarkRepoAdopted`, and returns `true`.
- `true` enrolls the sibling in the collector, so `replayBindingTurn` spawns a full `entire hooks &lt;agent&gt; stop` there.

That child runs `handleLifecycleTurnEnd` against the sibling worktree while loading and mutating the *source session's* state (`BaseCommit`, `StepCount`, `CheckpointTranscriptStart`, shadow-branch alignment all belong to the other worktree), concurrently with the source hook doing the same. This is trivially reachable in worktree-heavy setups — an agent in `&lt;repo&gt;/.worktrees/foo` touching a file in `&lt;repo&gt;/` resolves to the same `CommonDir`.

No test covers it: every case in `binding_checkpoint_test.go:26-46` uses distinct `CommonDir`s.

Fix: resolve the current repo's `CommonDir` once and return `(false, nil)` from `ensureSessionReplicated` when `ev.Repo.CommonDir` matches it — replicating into a store you already own is a no-op by construction, so it must not enroll a replay target. (Keeping the *evidence* record is fine; it's the adopt+replay promotion that must be gated on `CommonDir`, not `WorktreeRoot`.)

### C3. `replayBindingTurn` waits on child hooks with no bound

`binding_checkpoint.go:111-134` fans out one child process per bound repo and `wg.Wait()`s. `executeBindingReplayHook` (`:137`) uses `execx.NonInteractive(ctx, …)` with the hook ctx — and no agent-hook path installs a deadline (`executeAgentHook` never calls `context.WithTimeout`; `prepareHookPolicy` doesn't either). Each child runs a complete turn-end: transcript read, redaction, tree build, condensation, plus a **blocking** session-state flock in the target (`WithSessionStateLocks` takes the no-deadline kernel path when ctx has none — `flock/flock_unix.go:47-55`).

The comment at `:107-109` cites host-side Stop deadlines as the reason for parallelism, but parallel-and-unbounded still means the parent Stop hook is held for as long as the slowest child, and a wedged lock holder in any target repo hangs the agent's hook indefinitely. That is the same class of failure the record lock's own `recordLockTimeout` comment (`binding/record.go:216-222`) says must never happen.

Fix: wrap the replay fan-out in a `context.WithTimeout` (a few seconds of headroom under the agent's hook timeout), and log a Debug line per child that hits it.

## Important

### I1. `runRevParse` normalizes `CommonDir` but not `WorktreeRoot` — the own-worktree skip can never match on Windows

`binding/resolve.go:174` applies `filepath.Clean` to `commonDir` only; `root` is returned as git emitted it (`:178`). On Windows `git rev-parse --show-toplevel` emits `C:/path/to/repo`, while `filepath.Clean`/`EvalSymlinks` produce `C:\path\to\repo`. So one `RepoIdentity` carries two different separator conventions, and at `binding_tap.go:125-168` the comparison is between `filepath.EvalSymlinks(currentWorktreeRoot)` (backslashes) and `id.WorktreeRoot` (forward slashes) — never equal. The session's own worktree is therefore classified as foreign on Windows: it consumes one of the 8 `maxForeignReposPerTurn` slots, is written into the machine record, and only `sameAdoptPath` (`binding_adopt.go:53`, which *does* go through `filepath.Clean`) stops it short of self-adoption. The same mismatch makes `filepath.Rel(id.WorktreeRoot, p)` in `resolveForeignRepos` produce `../…` and silently drop the evidence `Files`.

Fix: `root = filepath.Clean(root)` alongside the existing `commonDir` clean in `runRevParse`, so both halves of the identity are in `filepath` form on every platform.

### I2. The replay child captures the target repo's unrelated dirty working tree

In a replayed turn `preState == nil`, so `DetectFileChanges(ctx, nil)` builds no pre-existing baseline (`state.go:317-322`) and reports every untracked file as new. `filterBindingReplayNewFiles` (`lifecycle.go:1025`) correctly narrows `relNewFiles` to transcript-evidenced paths — but `relDeletedFiles` and the `mergeUnique(relModifiedFiles, changes.Modified)` fallback one line earlier (`:1022`) are **not** narrowed. Every tracked file the developer has uncommitted in the touched repo, and every file they deleted, is merged into the step's file list and its content stored in the checkpoint — then pushed if that repo is trusted.

The git-status fallback is sound in the source repo (the session owns that worktree); in a repo the agent touched once it turns a colleague's unrelated WIP into checkpoint content.

Fix: extend the replay narrowing to all three lists — under `bindingReplayActive() &amp;&amp; preState == nil`, filter `changes.Modified` and `changes.Deleted` to transcript-evidenced paths the same way `New` is filtered, rather than merging raw git status.

### I3. Non-primary token suppression zeroes the session-wide total, not just the checkpoint delta

`lifecycle.go:1120` sets `tokenUsage = nil` for every repo that isn't the turn's primary. `stepCtx.TokenUsage == nil` skips *both* accumulations in `strategy/manual_commit_git.go:124-126`:

```go
if step.TokenUsage != nil {
    state.TokenUsage = accumulateTokenUsage(state.TokenUsage, step.TokenUsage)
    state.CheckpointTokenUsage = accumulateTokenUsage(state.CheckpointTokenUsage, step.TokenUsage)
}
```

CLAUDE.md defines these as distinct scopes: "`SessionState.TokenUsage` is the session-wide total used by `entire status`; `SessionState.CheckpointTokenUsage` is the pending checkpoint delta." Deduping the *checkpoint* aggregate is the stated goal, but the current lever also blanks the session-wide total. A user whose agent's last edit landed in a sibling repo sees their own repo's `entire status` under-report tokens for that turn, with the count living in a state file in a repo they aren't looking at.

Fix: keep passing `TokenUsage` everywhere and suppress only the checkpoint-scoped half — e.g. a `StepContext` flag that makes `SaveStep` accumulate `state.TokenUsage` but skip `state.CheckpointTokenUsage` (and the checkpoint metadata) in non-primary repos.

### I4. The no-repo path can print raw slog lines to the agent's stderr

`binding_norepo.go:36-38` states the invariant explicitly: "`logging.Init` never ran here …, so only `logging.Debug` may be used: pre-Init it is a silent no-op, while Info/Warn/Error would leak raw slog text onto the agent's stderr." `logging.log` falls back to `slog.Default()` (`logging/logger.go:230-236`), which writes INFO+ to stderr.

Since this slice, the no-repo path calls `ensureSessionReplicated`, which reaches two non-Debug sites:

- `gitrepo/status.go:136` — `logging.Warn` on a status-budget breach, reachable from `targetUntrackedFiles` on any large foreign repo (and see C1, which makes the breach far more likely).
- `session/state.go:622` — `logging.Info` in `NormalizeAfterLoad`, reachable from `targetStore.Load`.

Fix: in the no-repo path, install a discarding logger on the ctx before calling into adoption (or gate adoption's status read behind a Debug-only wrapper), so the documented invariant holds transitively rather than only for code the file itself calls.

### I5. Skipping `shouldSkipForwardedHook` in the no-repo path now writes durable, wrongly-attributed session state

`binding_norepo.go:60-63` deliberately omits the forwarded-hook guard because it needs a repo root, reasoning that mis-attributing the *agent type* is "harmless for evidence, and the record's meta is first-write-only." That was true for slice 1. It no longer is: the record's `AgentType` flows into `buildReplicatedSessionState` (`binding_adopt.go:135-145`) and is saved as `session.State.AgentType` in a real repo, alongside the other agent's `TranscriptPath`.

This is the #1262 shape (`hook_guard_test.go:65-71`): only `.claude/settings.json` installed, Cursor invokes `entire hooks claude-code stop` with a Cursor payload. Launched from a parent directory, the guard never runs, and the target repo ends up with a claude-code-typed state pointing at a Cursor transcript — which selects the wrong extractor for every later read.

Fix: before adoption in the no-repo path, run the transcript-ownership half of `shouldSkipForwardedHook` (it only needs `event.SessionRef` and the agent's session dir, not a repo root) and bail out of adoption/replay on a mismatch. Recording evidence-only is fine to keep.

- **`selectBindingTurnPrimary` has no fork budget** (`binding_checkpoint.go:191`). # PR #2030 `feat/global-trust` — review (head `7ac91dd4f`)

Scope read: `CLAUDE.md`, `docs/architecture/global-tracking.md`, and the non-test Go diff vs `origin/main`, with depth on the egress/consent path (`settings/repopolicy/*`, `settings/trust.go`, `strategy/{trust_sync_remote,trust_prompt,manual_commit_push}.go`, `trust_cmd.go`), plus `paths/invisible.go`, `strategy/{global_setup,hooks,common}.go`, `hook_policy.go`, `hooks_git_cmd.go`, `agent/user_hooks.go`, `agent/{claudecode,geminicli}/hooks_user.go`, `gitremote.go`, `root.go`, `status.go`, `setup.go`, `doctor.go`.

## Critical

**1. `entire enable` writes a machine-wide egress grant in a repo the tier excludes**
`cmd/entire/cli/setup.go:1501` (`recordEnableTrust`; called unconditionally at `:1386`, `:1474`, `:2045`)

`recordEnableTrust` gates only on `us.GlobalEnabled()`. In an excluded or unclassifiable repo, `settings.CheckpointEgressAllowed` returns false *because `policy.Active` is false*, so the "already trusted, nothing to record" guard falls through and `settings.TrustCurrentRepo` runs — identity resolution never consults activation. Because `trusted_origins` is origin-keyed and machine-wide, every *other*, non-excluded clone of that origin on the machine then passes the gate without ever being asked. The user is also misdiagnosed: they see `Warning: trust for … was written …, but checkpoint sync is still held — check that file's trust entries`, when the cause is the exclusion, not a bad entry. This is exactly the case `trust_cmd.go:111 refuseTrustWhenInactive` exists to block ("silently pre-consenting an excluded repo is the bug consent exists to prevent"); `enable` bypasses it.

Fix — give `recordEnableTrust` the same precondition, and let the note explain:
```go
if active, _ := settings.IsActiveForRepoWithReason(ctx); !active {
    return // noteExcludedAfterEnable explains why
}
```

## Important

**2. The new "nothing pending" early return changes `git push` behaviour for every user, not just global-tracking users**
`cmd/entire/cli/strategy/manual_commit_push.go:196-205`

```go
pendingCheckpoints, pendingErr := CountUnpushedCheckpoints(ctx, ps.remote)
if pendingErr != nil { … return nil }
if pendingCheckpoints == 0 { return nil }
```
This sits *above* `gateCheckpointEgress`, so it runs unconditionally — including when the tier is off and `CheckpointEgressAllowed` would return true. On `origin/main` there was no such gate. It now skips: `syncCheckpointPolicyForPrePush` (`:239`, `:501`), so the local checkpoint-policy ref stops refreshing and divergence stops being reported on any push carrying no checkpoints; `cleanupPushedShadowBranches` (`:528`, git-refs backend), so a cleanup that failed once never retries. Worst case is dedicated `checkpoint_remote` URL mode: the count is measured against `refs/remotes/&lt;ps.remote&gt;/entire/checkpoints/v1` while the push target is a URL. A repo that migrated from origin-sync to a dedicated store keeps that tracking ref advancing on ordinary `git fetch`, so `tracking..local` reads 0 and the push to the dedicated store is skipped entirely — `pushRefIfNeeded` (`push_common.go:97-101`) deliberately refuses this optimization for URL targets, and the count gate reintroduces it against the wrong ref.

Fix — the stated intent is "don't ask for consent when there is nothing to send", so consult the count only where a prompt or hold would happen. Move it inside `gateCheckpointEgress`, after the `CheckpointEgressAllowed` fast path, so trusted repos (and every repo while the tier is off) take main's exact path.

**3. Bare `entire agent` still funnels a globally tracked repo into repo-level setup**
`cmd/entire/cli/agent_group.go:52`

```go
if settings.IsSetUpAny(ctx) { return runManageAgents(...) }
return runSetupFlow(ctx, w, opts)
```
`IsSetUpAny` is file-presence only (`settings.go:1456`), so it is false in a globally tracked repo — and `runSetupFlow` → `runEnableInteractive` (`setup.go:1264`) calls `saveSettings()`, writing `.entire/settings.json`. That is precisely the hazard `root.go:143-149` was rewritten to avoid: *"A globally-tracked repo must not be funneled into repo-level setup: completing it writes .entire/settings.json, which permanently pins the repo out of the global tier (exclude lists stop applying to it)."* The user-level agent hooks are already installed, so the wizard is also pure redundant work.

Fix: use the predicate root.go now uses — `settings.IsActiveForRepo(ctx)` (or `repoActivationConfiguredOrUnreadable` plus the tier bit) — so a globally tracked repo lands in `runManageAgents`.

**4. Trust identity unions fetch and push URLs, over-granting consent when `pushurl` is set**
`cmd/entire/cli/settings/repopolicy/sync_remote.go:61-67`

`RemoteURLsInDir` merges `remote.&lt;name&gt;.url` and `remote.&lt;name&gt;.pushurl` into `SyncRemote.URLs`, and `ResolveTrustIdentity` turns each into a `trusted_origins` key. But git's own rule — documented two files away in `gitremote.go` ("When any pushurl is set, git's pushurl-replaces-url rule sends pushes there INSTEAD of the fetch URLs") — means the fetch URL never receives checkpoints. So `entire trust` in a repo with `url = github.com/acme/widgets`, `pushurl = internal.example/mirror` records **both** keys, and a different repo whose sync remote is only `github.com/acme/widgets` then passes `identityTrusted` without ever being asked. That contradicts the design statement that consent is keyed on where checkpoints actually go.

Fix: in `RemoteURLsInDir`, when `pushFound` and at least one push URL is non-empty, return only the push URLs. Leave the union in `ExcludedByGlobalConfig` (`repository.go:174-185`), where breadth is the fail-closed direction. Only trust identity is affected.

**5. Repository classification runs three times per hook process, and drags a git-index decode into every repo on the machine**
`cmd/entire/cli/root.go:103`, `config.go:127` (`newLogger`), `hook_policy.go:22`, and `settings/repopolicy/activation.go:55`

Two compounding costs, both new. First, `ClassifyRepoPolicy` is unmemoized — there is no cache or `sync.Once` anywhere in `settings/repopolicy/*.go`, and `ResolveRepositoryAt` (`repository.go:62`) spawns its own `git rev-parse --show-toplevel --git-common-dir` rather than reusing `paths.WorktreeRoot`'s cache. The root `PersistentPreRun` calls `settings.IsActiveForRepo` (pass #1, replacing main's cheap `IsSetUpAny` stat), then `ensureLogger` → `newLogger` → `paths.AbsPath` → `paths/invisible.go:56`, which finds no ctx snapshot and classifies again (#2), then `prepareHookPolicy` classifies a third time — the first one that actually lands on ctx. Each pass costs a git subprocess plus reads of both repo settings files and the user file; with the tier on, `DecideEgress` → `ResolveSyncRemote` adds the sync-remote election and two more git-config reads per pass. This lands on the per-turn and per-tool-call agent hook path and on every git hook. Second, `ReadRepoActivation` calls `LocalSettingsTrusted` *before* the existence check:
```go
if !isProject &amp;&amp; !LocalSettingsTrusted(ctx, path) { continue }
data, err := os.ReadFile(path)
if errors.Is(err, fs.ErrNotExist) { continue }
```
The installed probe (`settings/global.go:33` → `probeLocalSettingsIsVersioned`) does a `gitrepo.OpenPath` plus a full index decode. `loadMergedSettings` (`settings.go:645`) is careful to probe only after a successful read; this path drops that guard, so the cost now lands in every repo including ones with no `.entire` directory. CLAUDE.md's own numbers for this probe are 8.3→2.5 ms here and 39→11 ms on reftable, and it explicitly says to keep it off users who do not need it.

Fix: memoize `ClassifyRepoPolicy` per process keyed on cwd, mirroring `paths.worktreeRootCache`/`ClearWorktreeRootCache` (with a `ClearRepoPolicyCacheForTesting`). Prefer that over attaching a snapshot in the root pre-run, which would bypass `prepareHookPolicy`'s `settings.Load` validation for `ActivationLocal` — that validation is load-bearing. Separately, move the `LocalSettingsTrusted` call below the `fs.ErrNotExist` check; behaviour-identical, since the probe has no side effects.

**6. `entire trust` reports "global tracking is off" when it is verifiably on**
`cmd/entire/cli/trust_cmd.go:136`

This line is reachable only after `us.GlobalEnabled()` returned true at `:120`, so the message is always wrong there. It fires for `InactiveReasonRepoDisabled` — the repo's own settings carry `enabled: false`, and the user should be told to run `entire enable`, not to turn on a tier that is already on — and for any classification error, since `IsActiveForRepoWithReason` returns `(false, InactiveReasonNone)` on error.

Fix: branch on `reason` rather than falling through to one message; give `InactiveReasonRepoDisabled` and the error case their own wording.

**7. `disable --uninstall` leaves the machine-wide trust grant, and its closing note implies otherwise**
`cmd/entire/cli/setup.go:2597`

The note says the next session "will track this repo again unless you add it to `exclude_paths`" — but the `trusted_origins`/`trusted_paths` entry written by `entire enable` or `entire trust` survives, so the repo is re-captured *and re-synced* with no prompt. "Uninstalled" reads to a user as "nothing leaves this machine any more".

Fix: either call `settings.RevokeCurrentRepo` as an uninstall step, or extend the note to name the surviving grant and point at `entire trust --revoke`.

**8. Gemini user-level uninstall never undoes `hooksConfig.enabled`, so turning global tracking off leaves Gemini hooks armed machine-wide**
`cmd/entire/cli/agent/geminicli/hooks.go:247` vs `:412-450`

`installHooksToFile` unconditionally sets `hooksConfig["enabled"] = true`, and `InstallUserHooks` (`hooks_user.go:42`) shares that path against `~/.gemini/settings.json`. `uninstallHooksFromFile` only ever reads and rewrites `rawSettings["hooks"]`; `stripLegacyHooksEnabledField` operates on `rawHooks` (the legacy `hooks.enabled`), a different key from the top-level `hooksConfig`, which is never touched on removal. At repo scope this was contained to one clone. At user scope it now overwrites an explicit user-level `"enabled": false` for every Gemini session on the machine, and survives `global.enabled: false` — the removal that `global_warn.go:131` triggers — so the user's own Gemini hooks keep firing after they turned the tier off. That contradicts the interface contract at `agent/user_hooks.go:43` ("removes only Entire's entries").

Fix: in `uninstallHooksFromFile`, after the removal pass, if no Entire entry remains anywhere and `hooksConfig` contains only the `enabled` key, delete `hooksConfig` from `rawSettings` — restoring the pre-Entire shape where Entire created it, while leaving a `hooksConfig` carrying other user keys alone.

## Suggestions

**9. `heldCheckpointCount` drops the dedicated-remote guard.** `status.go:284` counts against `elected.Name` with no backend check, while `computeCheckpointSyncInfo` (`status.go:645-651`) deliberately suppresses the count in dedicated `checkpoint_remote` + git-branch mode because "pushes to a raw URL update no remote-tracking ref, so it would permanently read 'all unpushed'". `global_tracking.held_checkpoints`, the `(N held)` suffix and doctor's held line inherit that permanent overcount. Reuse the same `PrimaryIsRefs` guard.

**10. One bad `trusted_paths` entry voids path trust for every repo.** `repopolicy/trust.go:89` passes the whole list to `MatchesExcludePathExact`, which returns on the first entry failing `ExpandTilde` (`user_settings.go:326`). A hand-typed relative entry silently disqualifies valid later entries. `settings/trust.go:180 anyPathEntryIsRoot` already evaluates one entry at a time — make `identityTrusted` do the same. Fails closed, so usability rather than security.

**11. Global lazy setup backs up and replaces the user's git hooks with no record anywhere.** `strategy/global_setup.go:74` passes `io.Discard` for the notice writer, so `hooks.go:475/477` — including the "replacing %s (backup already exists)" warning, the one case where an existing hook is *not* preserved — vanishes: not stderr, not `.entire/logs`. Unlike `entire enable`, the user never asked for this install. Route both events through `logging.Info/Warn` so doctor and the logs retain them; consider surfacing "chained your existing `&lt;hook&gt;`" in `entire status`/`doctor` for globally tracked repos.

**12. The consent record inherits whatever mode the file was created with.** `repopolicy/user_settings.go:163` asks for `0o600`, but `jsonutil/write.go:91-93` overrides `perm` with the existing file's mode. The documented onboarding path is hand-editing `~/.config/entire/settings.json`, so the common real file is editor-created 0644 and stays 0644 forever — world-readable, and it now enumerates which repos may ship transcripts off the machine. Mask group/other for this one file (`perm &amp;^= 0o077`).

**13. `userHookConfigContainsEntire` is a raw substring probe.** `global_warn.go:180` does `bytes.Contains(data, []byte("entire hooks"))` over the whole agent settings file; a `permissions` deny rule or unrelated text yields a false "agent present", which makes `reconcileUserHooks` install user-level hooks for an agent that is not on the machine. `claudecode.loadClaudeSettingsFile` + `hookCommandExists` already parse these files properly.

**14. `--detailed` is silently dropped in an excluded repo.** `status.go:121-126`'s `excludedHere()` early return sits above the `if detailed` block at `:128`.

**15. `lockHookInstall` blocks unbounded on a hook hot path with `ctx` already in hand.** `strategy/hooks.go:532` uses `flock.Acquire`, whose own doc points at `AcquireContext` for "latency-critical hooks". `MaybeEnsureGlobalSetup` calls this from inside agent and git hooks — including Codex's session-end hook, which runs under a 3s host cap with its process tree killed on expiry. Swap to `flock.AcquireContext(ctx, …)`; the function already takes `ctx`.

**16. No `Read` deny rule covers metadata in global mode.** `claudecode/hooks.go:60` denies `Read(./.entire/metadata/**)` at repo scope only, and `hooks_user.go:41` passes `projectScope=false` deliberately. In a globally tracked repo metadata lives at `&lt;git-common-dir&gt;/entire/worktree/&lt;key&gt;/metadata`, which nothing denies — so Claude Code can read back its own stored transcripts. Worth an explicit decision (a user-level `Read(./.git/entire/**)` deny, or a written "we accept this") rather than falling out of the scope split.

**17. `gitpath.Equivalent`'s only consumer applies it inconsistently.** `settings/opf_command_trust.go:132` — `gitpath.Equivalent(target, root) || strings.HasPrefix(target, root+sep)`: the equality half folds case, the subtree half does not, so on a case-insensitive volume an absolute command path inside the worktree with different casing escapes the check. Exploitability is nil (the file is the developer's own untracked `settings.local.json`), but the halves should agree — use `gitpath.CanonicalKey` on both sides of the prefix test.

**18. Two comment defects.** `setup.go:1482-1491`: `recordEnableTrust`'s doc block sits above `noteExcludedAfterEnable` (whose comment is appended to it), leaving `recordEnableTrust` undocumented. `root.go:145-149`: a truncated sentence — *"The enabled BIT gates here, not // The activation gate's fail-closed answer…"* — reads as a merge artifact.

## Strengths

- **Two-phase capture with consent re-derived for the *pending* remote.** `policyForPendingCapture` + `withPendingSyncRemote` mean the push that elects a new sync remote asks about the destination it is actually opening, and `WithSyncRemoteOverride` gives the non-interactive user the matching `entire trust --remote` escape. The reasoning for why plain `entire trust` would not work there is correct and non-obvious.
- **Per-block strictness with faithful round-tripping.** `UserSettings.UnmarshalJSON/MarshalJSON` keeps unknown top-level blocks as `json.RawMessage` while making the `global` block strict, and `MarshalIndentWithNewline` disables HTML escaping — so an older binary's `entire trust` cannot corrupt or silently drop a newer binary's block, and cannot misread consent it does not understand.
- **The read-modify-write on the user settings file is genuinely race-free.** `ModifyUserSettings` holds `flock` across load → mutate → atomic write and is the only writer; agent user-hook files get their own bounded lock. `hooks.go:443-454` adds a cross-process install lock specifically because global mode is the first time hook installation runs from concurrent hook *processes*, and puts it in the git common dir rather than the hooks dir precisely because the latter can be worktree-resident.
- **`ErrUnroutableRuntimePath` as a first-class sentinel with one contract.** `paths/invisible.go:17` plus consistent "skip, never fall back to a worktree path" handling at every consumer (`opencode/lifecycle.go:195,221`, `pi/lifecycle.go:286`, `state.go:463`, `lifecycle.go:625,801,1288`), with `sameWorktree` resolving symlinks on both sides as defense in depth.
- **`TestNoDirectEntireJoins`.** Encoding the routing invariant as a mechanical scan with an auditable `// entire-join-ok: &lt;reason&gt;` escape hatch is far stronger than documenting it; all seven current bypasses are legitimately config-class or sentinel-guarded.
- **`HooksDirIsWorktreeResident`'s formulation.** `IsSubpath(worktreeRoot, hooksDir) &amp;&amp; !IsSubpath(gitDir, hooksDir)` with `resolveExistingPrefix` on all three paths cleanly separates `.git/hooks` (install) from a committed `.husky` (skip) across main worktrees, linked worktrees, bare+worktree layouts, and submodules.
- **`gitremote.getAllRemoteConfig`'s exit-1 contract.** Distinguishing "key unset" from "not a repository" (and re-checking `ctx.Err()` around the probe either way), plus deliberately choosing `git config --get-all` over `git remote get-url` to preserve `insteadOf` shorthands for `exclude_origins`, is the kind of detail usually found in production instead.

*Coverage note:* the Claude Code and Gemini `hooks.go` restructures (~1,050 diff lines) and `lifecycle.go` were spot-checked rather than read end to end; their new user-level entry points (`hooks_user.go`, `agent/user_hooks.go`) were reviewed in full. Two hazards were explicitly ruled out: `installGitHooks` does chain to the `.pre-entire` backup, and `writeHookFile` is atomic with the executable bit applied before the rename — so a user's existing `commit-msg`/`pre-push` is preserved, and a lazily-installed hook can never be observed half-written.</result>
