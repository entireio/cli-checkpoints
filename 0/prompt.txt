## How it differs from the v1 path

| | git-branch v1 | git-refs |
|---|---|---|
| Discovery | fetch remote tip → merge-base → divergence check → `listUnpushedV1Commits`, bootstrap cap | `PushQueue.Peek()` (never `Drain`), filtered through `partitionLocalRefs`; no merge-base, no divergence, no bootstrap cap, no network |

| Ref update | one CAS on `refs/heads/entire/checkpoints/v1` | all commits rebuilt first, then one `CheckAndSetReference` per ref (CAS against the observed old hash, so a concurrent checkpoint write isn't clobbered) |

## Failure semantics

Both backends fail closed; only the *mechanism* differs. `runOPFForCheckpointRefs` returns a bool and the call site is `if redact.OPFEnabled() &amp;&amp; !runOPFForCheckpointRefs(ctx, repo) { return nil }`:

- **OPF failure or `OPFAbort`** → flush skipped entirely, `return nil`. Nothing un-OPF'd ships, refs stay queued, the user's `git push` succeeds.
- **`OPFSkip`** → unchanged: flush as-is, 8-layer, no trailer.
- **Where the user sees it:** `logging.Warn("OPF pre-push failed; skipping checkpoint ref push, refs left queued")` **and** a stderr line via the package's `stderrWriter` (the local convention — `checkpoint_policy.go`, `refs_push_destination.go`, `checkpoint_sync_capture.go` all use it): `[entire] OPF did not run, so checkpoint refs were not pushed and stay queued for your next push: &lt;err&gt;`.

## Look hardest at this

**Only each queued ref's *tip* commit is rewritten.** This follows the spec ("each checkpoint ref is standalone, keep the ORIGINAL parent"), but I verified in `refs_store.go` that checkpoint refs genuinely do chain: `refBase` parents each write on the prior tip, and `setRef` re-enqueues. So a checkpoint that gets a session write and then a summary/attribution/transcript backfill before the next push has **two unpushed commits on one ref**. We rewrite the tip; the ancestor is still pushed with the ref and still carries un-OPF'd blobs. The tip's tree is cumulative so the *content* is all present in redacted form at the tip, but the unredacted originals remain reachable from the parent commit.

Closing it needs a per-ref unpushed boundary. The tempting version — walk back until the first commit carrying the OPF trailer — is a clean boundary in steady state but rewrites all history on a repo that enables OPF late, forcing non-fast-forward pushes through the fetch+replay recovery path on every ref. That's exactly the bootstrap hazard the v1 path caps, and the queue records no push watermark to bound it. I did **not** build it; I documented the gap in the commit message's "Known gap" paragraph. Worth a decision before this reaches OPF users on git-refs.

Two smaller things:
- I used `CheckAndSetReference` per ref rather than plain `SetReference`. A CAS conflict mid-loop leaves earlier refs updated — which I believe is safe (each rewritten ref is independently valid and trailer-stamped, the error withholds the flush, and the next push skips the applied ones and retries the rest), but it is a deliberate deviation from "all-or-nothing" that only holds because refs are standalone.
- The `FailureLeavesEveryRefUnmoved` test exercises a **batch-level** OPF failure, not a rebuild failing after a sibling rebuild succeeded. The deferred-update structure is what guarantees the latter; I couldn't construct a genuine mid-batch rebuild failure without contriving storage corruption, so that specific ordering is covered by construction rather than by test.</result>

## The walk

`unappliedAncestry(repo, tip) ([]*object.Commit, plumbing.Hash, error)` walks first parents from a queued ref's tip, appending every commit lacking `Entire-OPF-Applied` and stopping at the first commit that carries it. It returns the chain reversed to **ancestor-first** plus `base` — the hash it stopped at, or `plumbing.ZeroHash` at a root. Checkpoint refs are a single-parent chain, so the first parent is the whole history.

Per ref in pass 1: walk → `len(chain) == 0` means the tip is already applied, skip → `len(chain) &gt; bootstrapLimit` returns `BootstrapTooLargeError{Count, Limit}` → otherwise collect tree blobs for **every** commit in the chain. `resolveBootstrapLimit()` is hoisted out of the loop and applied per ref (a single ref's ancestry is the thing that can run deep). The raw-bytes cap keeps accumulating across the whole flush — all refs, all commits — as before.

## Reparenting

Pass 3 replays each ref's chain ancestor→tip:

```go
parent := pr.base
for _, pc := range pr.commits {
    newHash, _ := rebuildCheckpointCommit(ctx, repo, pc.commit, parent, redactedByPath)
    parent = newHash
}
rebuilt[i] = parent // new tip
```

So the deepest rewritten commit keeps `pr.base` (the trailered ancestor, or zero at a root) and each rewritten parent carries into its child. Every commit across every ref is still rebuilt before any ref moves; ref updates are still the per-ref `CheckAndSetReference` (left as-is per your call).

### 2. `!hasTaskContent` disables the read-only skip only in the multi-session case — and the justification doesn't hold there — confidence 85

## Suggestions

- **Freshness should key on `CompletedAt` for completed records** (`manual_commit_hooks.go:888`). A subagent that started 30h ago and completed 5 minutes ago has an unmaterialized record that is stale by `StartedAt` and fresh by any useful measure — it loses linkage on the very commit that should carry it. `now.Sub(task.StartedAt)` is the right bound for in-flight records only.
- **Consider `state.OwnerExited()` as a cheap tightening** of `idleWithTaskContent`. A crashed agent's IDLE session with a fresh record currently links every no-TTY commit for up to 24h; if the owner process is provably gone, no background subagent is still running, so the in-flight-record premise is false. `proclive.Check` already backs this and degrades to Unknown on Windows/cross-host, which would fall back to today's behavior.
- **`addTrailerForAgentCommit`'s doc (`:2181`) says the session "is trusted unconditionally."** It isn't quite — the caller's empty-session guard rejects sessions with nothing condensable. Minor, but this doc is now the load-bearing explanation of the trust boundary.
