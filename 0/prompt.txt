# Silent-failure audit: PR #1987 (fix/gated-push-checkpoint-sync-hint)

Scope reviewed: `cmd/entire/cli/strategy/checkpoint_sync_remote.go` (`hintGatedCheckpointSync`), its call site in `cmd/entire/cli/strategy/manual_commit_push.go:85`, and the harness change in `cmd/entire/cli/integration_test/testenv.go`.

Structural context that frames every verdict: the hint only runs after `checkpointSyncAllowedForRemote` (checkpoint_sync_remote.go:95-112) has already returned false **and already logged** — `logging.Warn` for a resolution failure (:101), `logging.Debug` with both remote names for the normal mismatch (:106). So `.entire/logs` always carries a record that the gate fired before the hint is even consulted. The question is only whether the hint's own suppression is traceable.

## Findings, ranked

### 1. MEDIUM-HIGH — `CountUnpushedCheckpoints` error is swallowed with zero trace
`cmd/entire/cli/strategy/checkpoint_sync_remote.go:133-135`

```go
count, err := CountUnpushedCheckpoints(ctx, syncRemote.Name)
if err != nil || count == 0 {
    return
}
```

This is the one silence in the function that no other code path covers. The `count == 0` half is correct silence (nothing to say). The `err != nil` half is not: `CountUnpushedCheckpoints` (unpushed_checkpoints.go:21) has real, persistent failure modes — on the git-refs backend it can fail at `OpenRepository`, `PushQueueForRepo`, or `queue.Peek()` (a corrupt/locked push queue fails on *every* push); on the git-branch backend `git rev-list` can fail. Hidden error types include repo-open failures (reftable/alternates edge cases), queue-file corruption, and rev-list errors from a broken ref.

User impact: if counting fails persistently, the hint never fires, and the exact symptom this PR exists to fix — checkpoints stranding locally with no signal — reappears. Worse, it reappears *undiagnosably*: the gate's Debug line says "sync skipped" (expected, benign-looking), and nothing anywhere records that the hint was attempted and suppressed by an error. A support engineer reading `.entire/logs` six months from now cannot distinguish "hint correctly silent, nothing waiting" from "hint broken, count failing" without reproducing locally. Notably, on the gated path `prePush` returns immediately (manual_commit_push.go:86), so none of the later repo-open warnings (:107) run either — the count failure has no proxy log.

Verdict: **silence not justified.** Silence toward the *user* is right (never degrade a best-effort hint into push noise or a blocked push), but the error must reach `.entire/logs`. Recommend:

```go
count, err := CountUnpushedCheckpoints(ctx, syncRemote.Name)
if err != nil {
    logging.Debug(ctx, "gated checkpoint sync hint suppressed: cannot count unpushed checkpoints",
        slog.String("sync_remote", syncRemote.Name),
        slog.String("error", err.Error()))
    return
}
if count == 0 {
    return
}
```

Debug matches the gate's severity for expected-skip paths; Warn is defensible since a failing count is abnormal, but Debug is the floor. This is a two-line, zero-risk change.

### 2. LOW (justified, with a caveat) — `isConfiguredRemote` failure conflated with "URL push"
`checkpoint_sync_remote.go:126-128`

`isConfiguredRemote` (manual_commit_push.go:241-246) treats *any* `git remote get-url` failure — git binary broken, config unreadable, context cancelled — as "not a configured remote", so a transient git failure silences the hint for a genuinely configured remote, indistinguishably from the intended raw-URL case. However: (a) this is the helper's documented pre-existing contract, used identically at manual_commit_push.go:224; (b) if git subprocesses are failing, the enclosing `git push` is failing too, with far louder symptoms; (c) the gate's Debug line already recorded `push_remote`. Verdict: **justified** — no change required. If finding #1 is fixed, the log gap here becomes negligible.

### 3. Justified — `ResolveCheckpointSyncRemote` error swallowed
`checkpoint_sync_remote.go:129-131`

The identical call just failed inside `checkpointSyncAllowedForRemote` microseconds earlier on the same code path and was logged at Warn with the wrapped specifics (:101-102). Logging again in the hint would be a duplicate entry for one event. The only theoretical gap is a race where the gate's call succeeds and the hint's re-read fails (settings file mutated between the two reads within one hook invocation) — negligible. Verdict: **silence justified.** (Optional hardening, not a defect: pass the gate's resolved `CheckpointSyncRemote` into the hint instead of re-resolving, which removes the double-read and this race entirely.)

### 4. Justified — silence on `Source == SyncRemoteSourceConfig` and on `Name == ""`
`checkpoint_sync_remote.go:130`

The config-source suppression is a deliberate, documented, and integration-tested product decision ("a decision already made must not nag" — asserted by `TestCheckpointSyncRemote_ConfigOverride_RoutesToNamedRemote` passing `expectGatedHint: false`), and the gate's Debug log still records the skip with both remote names. The `Name == ""` arm is actually unreachable here — `isConfiguredRemote(pushRemote)` passing means at least one remote exists, so election always returns a name — a harmless defensive check, not a hidden failure. Verdict: **justified.**

### 5. Justified — `Fprintf` return values ignored
`checkpoint_sync_remote.go:137-142`

Writes go to `stderrWriter` (`os.Stderr` in production, manual_commit_hooks.go:821), inside a git hook where stderr is relayed by git. If the write fails (EPIPE), there is no remaining channel to report on and nothing actionable. This matches every existing user-facing warning in the package (checkpoint_policy.go:60, refs_push_destination.go:114-116). Verdict: **justified.**

### 6. Clean — testenv.go harness change
`cmd/entire/cli/integration_test/testenv.go:1983-2015`

No error path was lost: `runPrePush` still logs combined output via `T.Logf` on **all** paths (:2010) before returning, still wraps the exec error (:2012), and now also returns the output alongside the error (useful, not lossy). `RunPrePush` still `Fatalf`s through `RunPrePushWithError`; the new `RunPrePushOutput` correctly `Fatalf`s on error rather than returning partial output as if it were a clean run — the important trap, and it was avoided. `RunPrePushWithError` discards the output string, but callers doing error-path assertions still get it in the test log. Verdict: **no issues.**

### 7. Observation (pre-existing, not this PR's defect) — the fail-closed misconfiguration remains user-silent at push time

A typo'd `checkpoint_push_remote` disables checkpoint sync on *every* push with no stderr signal; the hint's comment claims the case "warns through the gate itself", but the gate's warning goes to `.entire/logs`, not the user. This is an accepted design: status.go:281-283 explicitly designates `entire status` as the user's signal for this case (`checkpointSyncInfo.Err`), and the resolver's error message is self-explanatory when found. Worth knowing when triaging "my checkpoints stopped syncing" reports; not a regression here.
