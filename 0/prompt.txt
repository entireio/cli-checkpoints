[cmd/entire/cli/setup.go:1059](vscode://file//Users/alex/workspace/cli/.worktrees/fix-legacy-bff-trails-enabled-routing/cmd/entire/cli/setup.go:1059) and [cmd/entire/cli/agent_help_cmd.go:352](vscode://file//Users/alex/workspace/cli/.worktrees/fix-legacy-bff-trails-enabled-routing/cmd/entire/cli/agent_help_cmd.go:352)

The third user of this seam does handle it, at [cmd/entire/cli/trail_context_cache.go:301](vscode://file//Users/alex/workspace/cli/.worktrees/fix-legacy-bff-trails-enabled-routing/cmd/entire/cli/trail_context_cache.go:301), with an explicit comment about why the definitive negative must be persisted.

What changed: the old BFF path returned 404 for these repos, and `api.TrailsEnabled` maps 404/403/410 to `(false, nil)` ([api/trails.go:26](vscode://file//Users/alex/workspace/cli/.worktrees/fix-legacy-bff-trails-enabled-routing/cmd/entire/cli/api/trails.go:26)) — so a repo not onboarded to Entire got a cached `false`. The cell client is fail-closed by design (`resolveRepoCellTarget` errors rather than falling back), so for exactly those repos the *client construction* now fails and no decision is cached:

- `probeAndCacheTrailsEnablement` returns early without caching. That silently drops the enable-time negative the enclosing `reportRepoEnabled` explicitly cares about — its own `info.Forge == ""` branch persists the negative "so a stale true cache from a previous origin does not inject on the prompt path" ([setup.go:1019-1024](vscode://file//Users/alex/workspace/cli/.worktrees/fix-legacy-bff-trails-enabled-routing/cmd/entire/cli/setup.go:1019)). A repo that was onboarded and is no longer can now keep a `true` entry (same repo key) until the hourly TTL expires.
- `refreshAgentHelpTrailsEnabledCacheIfStaleForScope` returns the error, which lands in the 5-minute `agentHelpTrailsRefreshFailureBackoff` instead of the hour-long definitive negative. So in a non-onboarded repo, `entire agent-help` re-pays up to `trailEnablementRefreshTimeout` (3s) of control-plane resolution every 5 minutes, where the sibling path answers it once per hour.

Fix: mirror the `trail_context_cache.go:301` branch in both — on `errors.Is(err, errRepoNotOnboarded)`, write the negative (`saveTrailsEnabledForScope` / `saveTrailsEnabledForRemote` with `false`) and return `nil`. Since this is now the third caller needing the same classification, extracting it (e.g. a `trailRefreshClientForScope` that returns "definitively disabled" as a value) would stop a fourth caller from missing it.

Related, same area, lower stakes: `reportRepoEnabled`'s 5s budget is now shared between the BFF `ReportEnable` and a probe that has to do control-plane repo resolution plus an identity-token exchange, where it previously reused an already-built client. Both are best-effort and silent, so I'd leave it — but it does mean the enable-time probe is the first thing to lose on a slow network, which is another reason the not-onboarded case wants a local answer rather than a network one.
