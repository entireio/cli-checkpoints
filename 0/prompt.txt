Target posture, in one screen
Every file Entire touches falls into one of four tiers, and the tier — not the individual call site — decides how it is opened, who may set what in it, and whether its contents may ever name something to execute.

owner-trusted
User
~/.config/entire · ~/.cache/entire
The developer's own machine state. The only place exec-bearing settings (OPF command) are honored. Symlinks are legitimate here (dotfile managers). Private perms, strict decode where it matters.

machine-local, repo-scoped
Clone
<git-common-dir>/entire…
Shared by every worktree of one clone, never committed. Runtime and caches only: session state, redact cache, sync-remote capture, per-worktree runtime roots. No policy, no preferences.

repository-controlled
Worktree
<worktree>/.entire
Arrives with a clone. Configuration, never consent, never a command. Read through os.Root, symlinks refused (#2154/#2156), strict decode, IDs validated before joining paths.

hostile input
Remote
entire/checkpoints/v1 · API responses
Anyone with push access authored it (CVE-2026-57208). Every field that becomes a path is validated at the read boundary; every write lands through an os.Root anchored at the destination.

Compatibility hazard already latent in #2030
LoadUserSettings strict-decodes the whole file and any unknown key turns the global tier off machine-wide (by design, fail closed). The moment a newer binary adds redaction or repos to that file, every older entire on the same machine — a pinned Scoop install, a CI image, the git-remote-entire helper if it ever reads it — stops tracking. Extending the file requires a decode rule that is strict per block (unknown top-level keys tolerated with a warning; unknown keys inside a security-bearing block still fail that block closed). See schema.

The problems, precisely
1. settings.local.json is per worktree, and it is where the sensitive knobs live
Linked worktrees are the norm in this repo (fifteen under .worktrees/). Every one needs its own settings.local.json to carry the OPF command, the checkpoint_remote, the investigate config. Nothing propagates. And because the file sits inside content the repository controls, the loader has to prove on every load that the file is not tracked — that is the index probe, and for OPF the HEAD probe. The security work is paying for a location choice.

2. preferences.json mixes two lifetimes
Review profiles are a developer's durable preference for a repo. The trails enablement cache is a one-hour network answer keyed by repo_key + api_base + auth_key — all three are properties of the user's identity and the remote, not of the clone. Putting them in one file means every SessionStart refresh rewrites the review prefs, the cache is duplicated per clone of the same repo, and the writer has to run git rev-parse --git-common-dir under a 3 s deadline (the comment in trail_context_cache.go about answering at 2.9 s and then failing to store is exactly this). It is also written 0644 in a 0750 directory, lenient-decoded, with no owner semantics at all.

3. Three "user directory" resolvers, three write idioms
userdirs (config/cache), plugin_store.go (data, Windows-aware), and 16 bare os.UserHomeDir() calls. Writers use gofrs/flock, internal/flock, or no lock; dirs are 0700, 0750 or 0755 depending on which code path ran first. #2163 exists precisely because of that last point.

4. The safety story is per call site
readConfined is right but lives privately in settings; osroot (on the global branches) is a thin, unwrapped helper; state.go, clean.go and session/state.go each open their own os.Root. Each fix is correct and none is reusable, so the next path-bearing field will be joined with filepath.Join again.

5. Windows gets the non-idiomatic location and the least-tested primitives
Config resolves to %USERPROFILE%\.config\entire, permissions are synthetic, os.Rename onto an open file fails with a sharing violation, directory fsync is unsupported, and os.Root treats junctions as symlinks (so an os.Root anchored above a junctioned ~/.config refuses to read through it). Twenty-plus Windows issues in the tracker (#455 object-rename Access Denied, #886, #1424, #1398, #1707…) say the platform needs the convention to be explicit, not implied.

Why the tiers are shaped this way
Exec-bearing keys live in one tier, so trust needs one check. Today enforceOPFCommandTrust proves a repo file is not tracked (index + HEAD) because the file sits in the repo. A file under ~/.config needs no such proof — the repository cannot reach it. The whole classifyLocalSettingsDeep path and its memoization go away.
Symlink policy flips at the boundary. #2156 is right to refuse symlinks inside .entire, because a repository put them there. The same rule applied to ~/.config/entire would break every stow/chezmoi user; the branch's WriteFileAtomicFollowingSymlinks already encodes the opposite policy. Making "symlinks followed?" a property of the tier, not of the helper, keeps both correct.
Clone tier stops holding preferences. A developer who rm -rfs a clone and re-clones expects their review setup to survive; a developer with two clones of the same repo expects one setting. Both point at the user tier keyed by repo, which the global tier already has a normalized key for (host/owner/repo, repopolicy.NormalizeOrigin).
Runtime consolidates under one root per clone. #2030 already introduces <git-common>/entire/worktree/<key>/ for global mode. Adopting it for repo-enabled mode too gives one layout, one os.Root anchor, and a byte-clean git status everywhere — but it is a behaviour change (`doctor bundle`, log tailing docs) and is listed as a decision, not assumed.

Go's os.Root: what it does and does not give you (Go 1.26.6 doc)
Confines every method to the directory; follows symlinks but refuses ones that escape or are absolute; on Windows also rejects reserved device names and treats junctions as symlinks. It does not stop bind mounts or /proc, and Chmod/Chown/Chtimes race against a file-to-symlink swap on Unix — so set perms on the open file (f.Chmod, as the branch's writer now does), never by path. Every helper in safefile should carry that list in its doc comment so call sites stop re-deriving it.

Decode rule
Top level: tolerant. Unknown top-level keys are kept as json.RawMessage, round-tripped on write, and reported once by entire doctor ("key foo is not understood by this version"). This is what lets a 0.11 binary and a 0.12 binary share a machine.
Inside global and redaction: strict, fail that block closed — exactly #2030's current behaviour, scoped to the blocks where an unrecognized key could mean an unrecognized exclusion or an unrecognized command option.
Inside preferences blocks (review_*, investigate, summary_generation, repos.*): strict on the known struct, but a failure drops the block with a warning rather than the file. Losing a review preference must never disable tracking.
Precedence (lowest → highest)
<worktree>/.entire/settings.json — team
User file, top-level blocks — me, every repo
User file, repos["<key>"] — me, this repo, every worktree of every clone
<worktree>/.entire/settings.local.json — me, this worktree only. Kept for what is genuinely per-worktree (enabled for enable --local, an experiment in one checkout). Exec-bearing keys are no longer read from here.
Consent stays where #2030 put it: global.trust_* is the only egress switch, a committed enabled: false still vetoes, and nothing in the repository can open the sync path. The per-repo checkpoint_remote moving to the user tier actually strengthens CheckpointRemoteIsLocalOnly: "the developer chose this remote" becomes a fact about which file it came from, with no tracked-file probe needed.

Migration 3 — logs and tmp
Three candidate homes for .entire/{metadata,logs,tmp}; the choice is about layout, not trust, since all three are Entire-owned and gitignored or outside the tree.

A · Keep <worktree>/.entire/… for repo-enabled repos (status quo)
No migration; doctor bundle and docs unchanged. Cost: two layouts to reason about once #2030 lands (global repos use B), and the runtime dir sits inside a tree the repository controls, so it needs the #2154/#2156 guard forever.

B · <git-common>/entire/worktree/<key>/… for every active repo ← recommended
#2030 already builds this for global mode; adopting it for local mode gives one layout, one os.Root anchor, byte-clean git status in every repo, and takes runtime data out of the repository-controlled tier. Cost: a one-time move of existing logs (or just start fresh — full.jsonl is regenerated per Stop), and the temp file for an atomic write must be on the same filesystem as its destination (it will be — same .git).

C · ~/.local/state/entire/repos/<key>/… (XDG state; %LOCALAPPDATA% on Windows)
Right for logs that are not about one repo (login, version check, the future session-binding records currently in ~/.config/entire/sessions/). Wrong for metadata/tmp: hooks would write across filesystems, and two clones of one repo would collide on the key.

So: B for repo runtime, C as a new userdirs.State() for the handful of things that are genuinely per-user (move sessions/ there from ~/.config — config directories should hold things a user might edit). doctor bundle learns both roots; doctor logs keeps its --worktree semantics by resolving through RuntimeRoot().

Windows checklist
Each item is a real failure mode seen in this repo's history or a documented platform difference; the convention is only worth having if these are encoded in the primitives, not remembered by reviewers.

Location. Keep config at %USERPROFILE%\.config\entire. It is non-idiomatic, but contexts.json and tokens.json are already there for every Windows user, and git-remote-entire reads the same path; moving it means a coordinated migration across two binaries for a cosmetic gain. New Data()/State() surfaces should use %LOCALAPPDATA%\entire as plugin_store.go already does. Document the asymmetry once in userdirs.
Permissions. 0600/0700 are no-ops; Chmod toggles read-only. EnsurePrivateDir already skips; ReadOwned's mode check must skip too. Privacy comes from the profile directory's inherited ACL, which is the norm for every other CLI (gh, aws, git).
Rename over an open file fails (ERROR_SHARING_VIOLATION). Any concurrent reader — a second hook, Defender, an editor — makes WriteFileAtomic's rename fail. Retry with backoff (a few attempts over ~250 ms) inside the primitive; #455 was this in go-git's object store.
No directory fsync. Already best-effort; the branch's syncdir_windows.go whitelists ERROR_INVALID_FUNCTION/ERROR_NOT_SUPPORTED/ERROR_ACCESS_DENIED. Keep that list in one place.
Locks leave .lock files behind. LockFileEx needs a real file; they already litter ~/.config/entire and .git/entire. Fine, but entire clean should know they are ours.
os.Root and junctions. A Root refuses to traverse an absolute symlink, and Windows junctions are reported as symlinks. A user whose ~/.config is a junction (Scoop users, OneDrive-redirected profiles) would get every user-tier read rejected if we anchored a Root above it. This is why the user tier resolves first, then opens, and never uses os.Root for its own files. The worktree tier keeps os.Root, where refusing junctions is the desired behaviour.
Reserved names and separators. os.Root rejects NUL, COM1… by itself; filepath.Join does not. paths.ValidateID is the one place that rejects them for plain joins, so an ID like con from a checkpoint can never create .entire/metadata/con.
Case folding. Repo keys and path exclusions fold on darwin/windows (repopolicy.caseInsensitivePaths); the repos map in the user file must be looked up with the same fold, or C:\Code\Cli and c:\code\cli become two entries.
MSYS/Git-Bash paths. Hooks run under Git for Windows' bash, which hands us /c/Users/...; paths.normalizeMSYSPath exists — every resolver that compares a hook-supplied path to a stored key must route through it.
Long paths. <git-common>\entire\worktree\<64-bit key>\metadata\<session>\tasks\<toolUseID>\agent-<id>.jsonl approaches MAX_PATH under a deep %USERPROFILE%. Go enables long-path awareness for \\?\-prefixed paths only when the manifest allows it; keep the key short (the branch already moved to 64-bit) and prefer opening through a Root handle, which sidesteps path-length limits for the relative part.
CI. #1843 added a Windows job; make safefile's tests the ones that exercise rename-under-open-handle, junction refusal in the worktree tier, and junction tolerance in the user tier, so the platform is tested where the rules live.
Decisions the team needs to make
Does OPF's enabled/categories stay team-level? Proposal says yes — what gets redacted before it leaves a machine is a policy the repo owner sets; only how the binary is found is per-machine. The alternative (everything user-level) means a teammate without OPF installed silently pushes un-filtered content; the fail-closed pre-push already handles "enabled but missing binary", which is the right outcome.
Per-block tolerant decoding of the user file vs. #2030's whole-file strictness. Needed before any key is added to the file, otherwise a nightly and a stable on one machine fight. Suggest folding it into the #2030 stack now, since that is where the loader lives.
Runtime layout B for repo-enabled repos. One layout is a real simplification but a visible change (.entire/logs disappears from worktrees; docs and doctor hints move). Could ship behind the global-tier work or as its own follow-up.
How hard to fence with lint. The os.UserHomeDir ban with an agent/** allow-list is cheap and catches the next stray resolver. Banning os.ReadFile in four packages is more work (many test helpers) but is what turns "please use the safe primitive" into something CI enforces, the way Worktree.Status is enforced today.
Where ~/.config/entire/sessions/ (#1959) should live. If userdirs.State() is added, land #1959 on it rather than migrating later.
Windows config location. Stay at ~\.config\entire (recommended) or migrate to %APPDATA% in lockstep across entire and git-remote-entire.
Suggested first PR
User-tier loader in settings (lifted from repopolicy/user_settings.go, per-block decode), safefile.ReadOwned/ReadConfined/WriteAtomic extracted from their current homes with no behaviour change, the os.UserHomeDir lint fence, and OPF command honored from the user file. Everything else layers on top, and that PR alone deletes the HEAD probe from the pre-push path.

Where the Entire CLI puts its files
Local state is scattered across the working tree and eleven ad-hoc entries in the git directory. This proposes two roots, five lifecycle buckets, and one rule for deciding where anything new goes.

Two things, stated plainly, because everything below is judged against them.

Local files live outside the working tree. Nothing the CLI writes at runtime should appear in git status, be reachable by git clean -xdf, or need an ignore rule to stay invisible.

03
What's wrong
Four problems. None of them is fixed by renaming the entries.

Local files in the working tree are hostile to git
git clean -xdf deletes .entire/metadata/<sessionID>/ — the copied transcript and prompt.txt for every session in flight (lifecycle.go:748-813) — along with entire.log and tmp/. A routine cleanup silently destroys unfinished checkpoint work and the log that would explain it. Everything under a git directory is immune by construction.

Scattered paths leave nothing to secure
The eleven entries are declared as constants in seven packages — session/state.go:28, strategy/session_state.go:838, strategy/checkpoint_sync_capture.go:23, checkpoint/shadow_ref.go:139, checkpoint/pushqueue.go:26, checkpoint/redact_cache.go:72, investigate/state.go:25, review/manifest.go:759. Each package joins its own path onto a git root, so each has to defend that path itself.

It shows. The same session-ID traversal guard is written out seven times across three packages (session/state.go:952,997,1053, strategy/session_state.go:886, checkpoint/ephemeral.go:68,287, checkpoint/persistent.go:73) because there is no single owner of the join to put it in — and the names being guarded come from agent-supplied session IDs, tool-use IDs, and investigation run IDs, feeding directories that get RemoveAll'd.

The deeper cost is that there is no directory whose contents are all ours. entire-sessions/ is a sibling of HEAD, config, and hooks/, so nothing can be scoped to Entire's files as a unit: not a containment root, not a permission mode, not an audit, not a single RemoveAll. A bucket layout gives one root per tree and makes the bucket the only join, which is what containment can actually be anchored on.

Scattering also drifts silently. entire-checkpoint-push-queue.jsonl is already declared in two places — checkpoint/pushqueue.go:26 and integration_test/multi_pushurl.go:31 — so renaming it in one leaves the other pointing at a file that no longer exists.

The scoping axis is invisible
All eleven git-directory entries resolve against the git common dir, so every linked worktree shares them — and review/marker_fallback.go:42 depends on exactly that. Nothing in the paths says so. Writing the target as .git/entire/… erases the distinction and is literally wrong inside a linked worktree, where .git is a file. The bug seed is already in the tree: strategy/common.go:356 defines gitDir = ".git" as a plain string.

.entire/metadata/ means two different things
paths.EntireMetadataDir is both an on-disk staging directory and a path inside the orphan-branch tree, read through go-git in manual_commit_hooks.go:1816,2817,2871, manual_commit_condensation.go:1444, and ephemeral.go:367. The in-tree layout is committed history on entire/checkpoints/v1.

Any move must split this constant first. Otherwise a rename to .git/entire/metadata changes the on-disk path and the tree path together, and the tool stops finding its own history.

05
Tradeoffs
What each change buys, and what it costs. None of the costs are blocking; two of them need a decision baked in from the start.

Moving local state out of the working tree
Everything the CLI writes at runtime leaves .entire/ for a git directory.

Gains
git clean -xdf can no longer destroy in-flight session data or the log that would explain the loss.
.entire/ becomes purely committed content, so "is this directory fully tracked?" is a one-line test assertion and .entire/.gitignore disappears.
Nothing the CLI does shows up in git status, so it can't be accidentally staged or land in a PR diff.
Costs
Paths get harder for a human to find by hand, especially in a linked worktree where the git dir is .git/worktrees/<name>/. Bug-report collection has to go through entire doctor bundle rather than a known path.
git clean stops resetting CLI state, so a user reaching for it to "start fresh" no longer gets that. entire clean becomes the only route.
Any external tooling or muscle memory pointing at .entire/logs breaks.
Two roots instead of one
Common dir for anything shared between worktrees; git dir for anything scoped to one checkout.

Gains
Makes the sharing axis explicit, and correct inside linked worktrees and submodules — where the single-root shorthand is simply wrong.
Retires the gitDir = ".git" string literal, the seed of the class of bug this fixes.
Fixes two live defects at once: interleaved logs from concurrent agents, and fixed-name collisions under tmp/.
Costs
Every new file needs a scoping decision, and a wrong one fails silently — a shared file placed per-worktree only misbehaves once someone adds a second worktree.
Two places to look when debugging, and migration has to handle both.
Five lifecycle buckets
config, state, cache, run, plus logs and tmp on the per-worktree side.

Gains
entire clean collapses from a hand-maintained path list into three RemoveAll calls that can't fall behind the code.
"Is this safe to delete?" is answerable from the path alone, by a reviewer who has not read the package.
A new file has a derivable home, so the layout stops accreting names.
Costs
Some files are genuinely ambiguous. checkpoint-sync-remotes.json is captured rather than authored, and sits in config/ only because losing it changes behaviour.
Locks move away from the data they guard, so a stale .lock is no longer next to the file it belongs to.
One more path segment everywhere.
One package owns every path, enforced by test
The name of every local file moves behind a typed accessor; a test forbids filepath.Join onto a git root anywhere else.

Gains
The layout cannot drift back. This is the only part of the proposal that is self-enforcing.
One place to validate an agent-supplied ID before it becomes a path, replacing the guard currently repeated across seven call sites.
Migration and the legacy-path fallback live in exactly one place, so they can be added and later removed cleanly.
Test helpers stop hardcoding .git/entire-sessions.
Costs
Seven feature packages gain a dependency on one path package — real coupling, in exchange for the guarantee.
The forbidding test needs an allowlist, and will occasionally block someone doing something legitimate.
Staged migration with a one-release fallback
Relocate once on first command of the new version, under a flock; read the legacy path for one minor release.

Gains
An upgrade landing mid-session doesn't lose state or strand a running agent's hooks.
Each of the four steps ships on its own, so a problem is bisectable to one release.
entire doctor can report leftovers instead of leaving them to rot.
Costs
Two path resolutions coexist for a release, which is exactly the ambiguity this proposal removes — so the fallback has to be deleted on schedule, not left in.
A rename across filesystems is not atomic and needs a copy fallback for the large redact-cache.
Downgrading to the previous version leaves the moved state unreadable.
06
The rules
This is the part that has to survive. Each one is testable.

R1
Everything under .entire/ is committed.
No code path writes there at runtime.
Makes .entire/.gitignore dead weight, and makes the directory's tracked state a one-line assertion in a test.
R2
Every local path is <root>/entire/<bucket>/…
root ∈ {git-common-dir, git-dir}, bucket ∈ {config, state, cache, run, logs, tmp}.
No file sits directly under entire/. No third naming shape.
R3
Root is chosen by one question: does a second worktree need to see this?
Yes → common dir. No → git dir.
Both come from git rev-parse, never from joining .git onto the worktree root. That is what makes the layout correct in linked worktrees and submodules.
R4
cache/, run/, and tmp/ are deletable at any moment, by anyone, including mid-session.
config/ and state/ are not.
Turns entire clean from a hand-maintained path list into three RemoveAll calls, and gives a reviewer a one-glance answer to "is this safe to nuke?"
R5
One package owns every join onto a git directory.
Nothing outside it calls filepath.Join(commonDir, …) or filepath.Join(gitDir, …).
Enforced by a test, not a convention. Without this, R2 decays back to the current state within a few features. The root handles are already centralized in gitdir/entiredir/worktreedir; this extends that to the names.
R6
On-disk paths and in-tree paths are separate constants.
The checkpoint branch keeps .entire/metadata/<sessionID>/ as its tree layout forever.
Prerequisite for the metadata move. Can land on its own, before anything else here.

08
The open decision
Where do trail worktree checkouts go?

.entire/worktrees/ is the last thing standing between this proposal and R1, and it is the largest object in the working tree — full source checkouts, not metadata. It should leave its current location and stay out of the git common dir, so all three candidates move real checkouts somewhere a person can comfortably cd into.

A. Sibling of the repo — ../<repo>.worktrees/<branch>/
Gains
Satisfies both constraints with no new machinery.
Checkouts stay one cd .. away, matching what people already do by hand.
Same filesystem as the repo, so checkout stays fast.
Costs
The CLI writes outside the repo it was invoked in — needs care around permissions.
Two clones of the same repo sharing a parent directory collide.
Cleanup on git worktree remove has to reach outside the repo too.
B. User state directory — ~/.local/state/entire/worktrees/<repo-id>/<branch>/
Gains
Cleanest separation: nothing near the repo at all.
Extends the tier that already exists in internal/entireclient/userdirs (~/.config/entire, ~/.cache/entire).
Costs
Paths become unguessable, so it needs an entire trail path command to be usable at all.
Needs a stable <repo-id> that survives the repo being moved — otherwise it orphans checkouts.
Often lands on a different filesystem from the repo: slow, and it breaks hardlink-based checkout optimizations.
C. Configurable, defaulting to A
Gains
Costs the least in surprise: the default is A's familiar location.
Lets a monorepo point every checkout at one scratch volume.
Costs
One more setting in .entire/settings.json to document and support.
Needs a validation path that rejects any location inside the working tree, or it reintroduces the problem it was added to solve.
Recommendation
Start at A and add C only if someone asks. B's filesystem-boundary risk is real for large repos, and the <repo-id> stability problem is a genuine source of orphaned checkouts. Whichever wins, the decision is independent of the rest of this proposal and should not block it.

09
Getting there
Order
Four steps, each independently shippable, in this order because each removes a hazard from the next.

Split the metadata constant (R6). Pure refactor, no path changes, no migration. Removes the trap.
Move the eleven names behind typed accessors (R5) that still return today's paths, and add the test that forbids joins elsewhere. The root handles already exist; this is about the names. No behaviour change.
Move the git-directory entries into buckets. Contained: nothing outside the accessor package changes.
Move the working-tree entries out, delete .entire/.gitignore, add the .entire-is-fully-tracked assertion.
Migration mechanics
The hazard is a CLI upgrade landing mid-session: an agent is running, hooks are firing, and the session state file moves underneath it. Relocate once, on first command of the new version, under a flock in the common dir — the same mechanism recentlySpawnedMarker already uses — so concurrent hooks serialize rather than racing. Rename directories rather than copying, so it is atomic within a filesystem and cheap for a large redact-cache.

Keep a read-only fallback to the legacy path for one minor release, so a session that started under the old binary and continues under the new one still resolves. Do not write to the legacy path. Drop the fallback on the following release, and have entire doctor report any legacy path still present.
