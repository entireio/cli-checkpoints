# Review: PR #1886 — remote: classify a remoteless repo as checkpoint-ref absence, not outage

**Scope:** 2 files, +103/-0. `cmd/entire/cli/checkpoint/remote/checkpoint_ref.go` (guard + helper) and its test file. Base `main`, head `fix/local-repo-checkpoint-probe` (verified this worktree is on that branch).

## Overview

Main is red from a semantic conflict between #1824 (fetch-probe: transport failure is never absence) and #1811 (backfill writes routed through the refs store). In a repo with no remotes, `FetchCheckpointRef`'s origin-name fallback runs `git ls-remote origin`, gets exit 128, and the contract turns "no remotes exist" into a hard error, breaking backfill routing and `explain --generate`. The fix inserts a pre-probe guard: when the fetch target is the non-authoritative `"origin"` name fallback, settings load successfully, no `checkpoint_remote` key exists at all, and origin has no URL, return `plumbing.ErrReferenceNotFound` (absence) without probing. Three regression tests cover the matrix.

## Correctness analysis

**Does the guard preserve the false-absence protections? Largely yes.** I traced every path into the `("origin", false)` fallback of `checkpointFetchTarget` (util.go:41-47, reached only when `fetchURLAuthoritative` errors or yields an empty URL — which always implies origin's URL was unresolvable):

- Unreadable settings → `loadErr != nil` → guard skipped → hard failure (test 2 verifies).
- Key present but malformed (`GetCheckpointRemote` collapses to nil, settings.go:1421-1432) → `checkpointRemoteKeyPresent` true → guard skipped → hard failure (test 3 verifies). This correctly distinguishes "no intent" from "botched intent", which `GetCheckpointRemote` alone cannot.
- Valid `checkpoint_remote` + no origin → key present → guard skipped → hard failure. Correct.
- The fallback-emptiness refusal (checkpoint_ref.go:97-104) and the unreachable-remote path are untouched.
- The guard cannot fire on a resolved-URL target: `fetchTarget == originRemote` only matches the literal name fallback (a real remote URL never equals `"origin"`).

**Important — canceled/expired context is misclassified as absence** (checkpoint_ref.go:84). `GetRemoteURL` → `gitremote.GetRemoteURLInDir` (gitremote.go:98-108) runs `git remote get-url` via `exec.CommandContext` and collapses **every** failure — including context cancellation — into `"remote %q not found"`. Walkthrough: parent ctx already canceled → `fetchURLAuthoritative`'s own `getRemoteURL` fails → `originURL == ""` → (settings load ignores ctx, succeeds; no key) → falls back to `("origin", false)` → guard: load OK, key absent, `GetRemoteURL` fails again → returns `ErrReferenceNotFound` — **false absence in a repo that has an origin remote**. The refs store then acts on it (refs_store.go:396-402) and write routing falls through to another backend — exactly the misdirection #1824's contract exists to prevent. Note the surrounding code is deliberately careful about this same class: refs_store.go:404-407 refuses to memoize ctx-cancellation failures. How realistic: `HookCheckpointRefFetcher`/`BoundedCheckpointRefFetcher` mint fresh 15s child timeouts, so it needs the *parent* hook ctx to be dead (overall hook deadline exhausted mid-loop, SIGINT) — an edge, but a one-line fix closes it:

```go
if _, urlErr := GetRemoteURL(ctx, originRemote); urlErr != nil &amp;&amp; ctx.Err() == nil {
```

(Other exec-failure modes — git binary missing, unreadable repo — also collapse into `urlErr != nil`, but in those worlds the subsequent ls-remote fails everywhere anyway; ctx is the only one where the guard flips an otherwise-correct outcome.)

**TOCTOU between the guard's re-resolution and `checkpointFetchTarget` — analyzed, safe.** The guard re-runs `settings.Load` and `git remote get-url` that `fetchURLAuthoritative` just ran. I checked all four drift orderings: remote added between calls → guard doesn't fire, proceeds to a now-valid probe (safe); key added → guard skipped, hard failure (safe); key removed → absence matches final state; remote removed → can't matter (fallback already implied it was gone). No dangerous ordering, so this is a cleanliness concern, not correctness (see suggestions).

**Transient `GetRemoteURL` failure while origin exists:** to even reach the guard, the *first* `getRemoteURL` inside `fetchURLAuthoritative` must already have failed, so a single transient blip doesn't get you there — it takes two consecutive failures with the same ctx. Outside the ctx-cancellation case above (where both fail deterministically), there is no plausible transient double-failure on a local `git remote get-url`; acceptable.

## Project conventions

**Important — settings access convention** (checkpoint_ref.go:131-137). `checkpointRemoteKeyPresent` reaches into `s.StrategyOptions["checkpoint_remote"]` from the `remote` package, duplicating the storage-key literal that lives in settings.go:1417. CLAUDE.md is explicit: "Do NOT ... create new settings helpers without adding them to the `settings` package." This helper is a settings helper by function; it belongs next to `GetCheckpointRemote` as e.g. `(s *EntireSettings) CheckpointRemoteKeyPresent() bool`, keeping key-name knowledge in one file. As written, a future key rename would silently break this guard.

Otherwise clean: tests use `testutil.InitRepo` per convention; no `t.Parallel()` is correct here since every test calls `t.Chdir` (documented exception); error wrapping uses the sentinel properly; comments explain the *why* at appropriate length.

## Performance (git hooks, 15s budget)

Net positive. The guard's cost is one string compare on the happy path (resolved URL → skipped entirely). On the fallback path it adds one `settings.Load` (local file reads) + one `git remote get-url` subprocess, and in the remoteless case it *removes* the doomed `git ls-remote origin` subprocess. Both added operations are local and fast (~10ms). The per-store failure memo in the refs store is unaffected — absence is per-ref and unmemoized, which is correct since remoteless-repo "absence" is cheap to recompute. Suggestion: the duplicate `settings.Load`/`get-url` could be eliminated by having `fetchURLAuthoritative` surface a "no remotes at all" signal (sentinel error or reason enum) instead of the guard re-deriving it — also removes the drift surface.

## Issue 2: "No origin" is not "no remote" — repos with only non-origin remotes get a false absent verdict

- **Location**: `/Users/peytonmontei/Documents/entire/devenv/entireio/cli/.worktrees/fix-local-probe/cmd/entire/cli/checkpoint/remote/checkpoint_ref.go:69-88` (comment and guard), plus the test name `TestFetchCheckpointRef_NoRemoteAtAllIsAbsence`
- **Severity**: HIGH

The comment claims the guard identifies a repository that "has no remote that could host checkpoint refs," but the code only proves *origin* is missing. A repo whose sole remote is `upstream` (or `fork`, or an `entire://` mirror — `git remote rename origin upstream` is a common workflow) satisfies the guard and gets classified as absence. This matters because checkpoint refs are written by the pre-push hook to **whatever remote the user pushes** — `PushURL` at `/Users/peytonmontei/Documents/entire/devenv/entireio/cli/.worktrees/fix-local-probe/cmd/entire/cli/checkpoint/remote/util.go:158` derives from `pushRemoteName`, not origin. So checkpoints can genuinely live on a non-origin remote in a repo with no origin.

**Hidden error**: "the fetch path can't see the remote your checkpoints live on" — previously surfaced as a probe error (exit 128 on `ls-remote origin`, retryable, visible); now silently converted to "checkpoint does not exist."

**User impact**: exactly the stated stake — backfill misroutes onto a stale store, forking checkpoint data, in a configuration the user can't tell is degraded because nothing errors. The test name (`NoRemoteAtAll`) documents an invariant the code doesn't enforce.

**Recommendation**: enumerate all remotes and require **zero** before classifying absence (`git remote` / `repo.Config().Remotes` emptiness). This also composes cleanly with the Issue 1 fix — a config-based enumeration answers both questions in one non-exec read. Add a test: repo with only an `upstream` remote must NOT classify as absence.

## Issue 3: The swallowed `loadErr` leaves no diagnostic trail; users get a misleading exit-128 message

- **Location**: `/Users/peytonmontei/Documents/entire/devenv/entireio/cli/.worktrees/fix-local-probe/cmd/entire/cli/checkpoint/remote/checkpoint_ref.go:83`
- **Severity**: MEDIUM

The `settings.Load` error handling is *directionally* correct — an unreadable config falls through to the probe rather than classifying absence (and the test locks that in). A user with a remoteless repo **and** corrupt settings gets `probe checkpoint ref ... on origin: exit status 128` — a transport-flavored message whose actual root cause (unreadable `.entire/settings.json` disabled the local-repo shortcut) is nowhere in any log. ## Issue 4: Duplicate resolution creates a consistency window and redundant execs

- **Location**: `/Users/peytonmontei/Documents/entire/devenv/entireio/cli/.worktrees/fix-local-probe/cmd/entire/cli/checkpoint/remote/checkpoint_ref.go:67-88` vs `/Users/peytonmontei/Documents/entire/devenv/entireio/cli/.worktrees/fix-local-probe/cmd/entire/cli/checkpoint/remote/util.go:70-99`
- **Severity**: LOW
