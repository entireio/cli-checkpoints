Overall the change is at a sensible depth. The recovery tier lands at the one chokepoint every git-branch read already funnels through (`getSessionsBranchTree`), the seam is shaped like its siblings, and the backend guards reuse a predicate that already exists and is already used in ~8 places. ### 1. The backend guards express "primary is refs" where the actual invariant is "nothing in this topology writes v1"

**Files:** `cmd/entire/cli/strategy/common.go:684`, `cmd/entire/cli/strategy/checkpoint_remote.go:112` (and pre-existing `common.go:500`)

`primaryIsGitRefs(ctx)` is not a new special case — it is `checkpoint.PrimaryIsRefs`, already consulted in `manual_commit_push.go:94`, `unpushed_checkpoints.go:22`, `attach.go:521`, `status.go:310`, and elsewhere. Adding two callers to an established shared predicate is not layering. **The guards are in the right functions**, and I'd keep them there: the two justifications genuinely differ (bootstrap: there is no orphan to protect against; push: the "one-time cost" amortization is false because the branch is never created), so hoisting them into a shared `ensureV1BranchLocal` helper would collapse two different reasons into one.

What is wrong is the *predicate*, and it fails concretely. `buildMirrors` (`open.go:171`) explicitly supports **git-refs primary + git-branch mirror** ("during the branch-&gt;refs rollout"). In that topology `primaryIsGitRefs` is true, so both new guards fire — yet the mirror *does* write v1, and `GitStore.ensureSessionsBranch` (`persistent.go:2176`) creates a fresh orphan when the ref is missing. That is precisely the diverging orphan `bootstrapPrimaryFromCheckpointRemote` exists to prevent, now unguarded.

The staleness is already visible in the tree: the comment at `common.go:491-499` still says "We still adopt real v1 data that already exists on origin or a checkpoint_remote below (so legacy checkpoints stay readable); we only suppress the empty-orphan fallback." After this PR that sentence is false for the checkpoint_remote half.

**Deeper alternative:** put the answer on the backend registry, next to the `gitBacked` capability flag that is already there for exactly this purpose (`registry.go:47-60`) — a `writesMetadataBranch bool`, surfaced as `checkpoint.TopologyWritesMetadataBranch(cfg)` that considers primary *and* mirrors. Call sites don't collapse, but the guard then names the rule instead of the backend.

**Why less fragile:** a third git-backed backend, or a mirror that writes v1, declares its answer once instead of falling into whichever branch a `== "git-refs"` string comparison happens to take at 8 sites. It also removes the need to re-derive "git-refs never writes v1" in ~10 lines of prose at each guard (`common.go:685-696`, `checkpoint_remote.go:106-111`), which is where the invariant currently drifts.

### 2. `MetadataBranchFetchFunc` is at the right layer, but drops the one argument its sibling carries

**File:** `cmd/entire/cli/checkpoint/fetching_tree.go:42`

The seam is consistent with its siblings in every structural respect: field on `OpenOptions` → copied to `OpenEnv` → applied by the backend factory behind a nil check → consumed at the point of local miss → degrades to the pre-existing error on failure. `resolveSessionsBranchRef` (`persistent.go:2270`) extracting the local-only resolution so the fetch can retry it is the right shape, and it mirrors `resolveRefMaybeFetch` in the refs store. Placing it in `getSessionsBranchTree` rather than in `List`/`getFetchingTree` separately is correct — that is the single chokepoint.

The one asymmetry: `RefFetchFunc` takes the ref it must fetch; `MetadataBranchFetchFunc` takes nothing, so the injected implementation re-derives the target itself (`FetchMetadataFromCheckpointRemote` → `strategy.FetchMetadataBranch` → `checkpoint.ResolveRefs(ctx).Primary`). The store knows `s.refs.Read`/`s.refs.Primary`; the fetcher independently recomputes it from ambient context. Callers that override the topology — `resume.go:428` passes `Refs: &amp;refs` — can make those two disagree.

**Deeper alternative:** `type MetadataBranchFetchFunc func(ctx context.Context, ref plumbing.ReferenceName) error`, passing `s.refs.Primary`.

**Why less fragile:** it makes the seam a literal sibling of `RefFetchFunc` and removes a second, ambient source of truth for "which ref". Costs one parameter today and closes the divergence permanently.

### 3. Selective wiring is a real trap, and `resume.go` is already caught in it

**Files:** `cmd/entire/cli/explain.go:828`, `:1012`, `:2520` (wired) vs `cmd/entire/cli/resume.go:215,300,428,997` (not)

The doc comment ("Only wire it on foreground, user-initiated read paths") states a policy the code does not enforce — omission at a foreground site silently yields unreadable checkpoints rather than a compile or test failure. The repo already has the mechanism that fixes this, twice: `checkpoint.WithRemoteListDiscovery` (`refs_store.go:95`) gates `RemoteRefListFunc` on a context marker so the seam can be wired freely and only fires when a caller opts in; `strategy.WithCheckpointRemoteBootstrap` (`common.go:69`) does the same thing for the enable-time fetch. This PR introduces a *third* expression of the same "foreground vs hook path" distinction, this time as convention.

That the trap is live, not hypothetical: `resume.go` is a foreground read path with four unwired `Open` calls, and it compensates by hand-rolling the identical recovery ladder inline in `getMetadataTree` (`resume.go:465`: checkpoint_remote → local → origin → remote tree). That hand-rolled ladder is exactly the duplication this seam should have absorbed. `checkpoint_list.go` (via `GetStrategy` → `manual_commit.go:44`), `tokens_profile.go:115`, and `attribution.go:360` are also foreground and unwired.

**Deeper alternative:** gate the store's use of the fetcher on a context marker (reuse `WithRemoteListDiscovery`, or generalize both into one `checkpoint.WithForegroundNetwork`), then wire `MetadataBranchFetcher` at every CLI-layer `Open` that already passes `BlobFetcher`/`RefFetcher`. The principled version of "foreground vs hook" is to set that marker once at command entry — Cobra commands are foreground by definition, the `entire hooks` subtree is not — rather than at each `Open`.

**Why less fragile:** it inverts the failure mode. Today, forgetting the field costs a user their checkpoints with no signal; with the gate, the safe answer is the default and opting in is the deliberate act. The minimal, immediately-scoped step is just wiring the four `resume.go` sites and deleting the hand-rolled ladder.

### 4. `FetchMetadataBranch` bakes in both the budget *and* the filter policy, so new consumers silently inherit `resume`'s choices

**File:** `cmd/entire/cli/strategy/checkpoint_remote.go:132`

This PR establishes a good principle in `bootstrapPrimaryFromCheckpointRemote` (`common.go:722-728`): fetch the ref blob-filtered, let `BlobFetcher` hydrate on demand, because v1's blobs are the whole transcript archive. The new read-recovery tier does not follow it. `FetchMetadataBranch` hard-codes `noFilter: true` *and* `checkpointRemoteForegroundFetchTimeout`, so the `MetadataBranchFetcher` path pulls the entire archive unfiltered — at all three explain call sites that already pass `BlobFetcher: FetchBlobsByHash` and would have hydrated only what they read.

The same baked-in budget leaks onto a hook path. `FetchBlobsByHash` (`git_operations.go:582`) falls back to `FetchMetadataFromCheckpointRemote` → `FetchMetadataBranch`, and `FetchBlobsByHash` is wired into `GetStrategy()` (`config.go:70`), which the lifecycle hooks use. That fallback's budget went from 30s to 2 minutes as a side effect of a change aimed at foreground commands.

**Deeper alternative:** follow the in-repo precedent for exactly this, `remote.BoundedCheckpointRefFetcher(d)` / `remote.HookCheckpointRefFetcher()` (`checkpoint/remote/checkpoint_ref.go:161-177`) — return a configured fetcher whose budget and filter are chosen at the wiring site, rather than fixing them inside a shared exported call.

**Why less fragile:** the policy ends up attached to the caller that knows its own constraints, instead of being inherited by whoever calls the shared function next. (Related, same root cause: `fetchMetadataBranchIfMissing` now spends `checkpointRemoteFetchTimeout` on the ls-remote probe *and* again on the fetch, so the push hot path's worst case is 60s, not the 30s the constant's doc claims — per-call-site budgets don't compose when they're applied at two nesting levels.)

## 1. `cmd/entire/cli/checkpoint/persistent.go:2235-2251` — recovery fetch re-fires on every `getSessionsBranchTree` call; nothing memoizes the attempt

**Cheaper alternative:** a `metadataBranchFetchAttempted bool` on `GitStore` (or nil the fetcher after it runs) so the recovery fetch fires at most once per store instance.

**Cost, and on which path:** `getSessionsBranchTree` is entered ≥3 times per `entire explain` on the same `GitStore` instance — `List` (persistent.go:1627, via `newExplainCheckpointLookup`), `Read` → `getFetchingTree` (persistent.go:1384), `ReadSessionContent`/`ReadSessionMetadata*` → `getSessionTree` → `getFetchingTree` (persistent.go:1432), plus `GetCheckpointAuthor`. This is the largest waste the diff introduces, and it is amplified by the timeout raise in the same diff.

## 2. `cmd/entire/cli/explain.go:2520` — the fetcher is wired on the *enumeration* path, where `kindRoutingStore.List` always hits the branch store

**Cheaper alternative:** drop `MetadataBranchFetcher` from the `getBranchCheckpoints` Open, or gate the fetch behind the same context marker `RemoteRefLister` already uses (`WithRemoteListDiscovery`), so only by-ID reads (`Read`/`ReadSession*`) can trigger it.

**Cost, and on which path:** `routing_store.go:109` calls `s.branch.List(ctx)` unconditionally, regardless of primary type. On a repo that was refs-native from the start (remote has no v1 at all) it degrades to one failing round trip on *every* list invocation, forever, on a command that was previously local-only. Note the diff switched the enable bootstrap/heal fetches to blob-filtered for precisely this reason (common.go:728, :823) while `FetchMetadataBranch` stays `NoFilter: true` (checkpoint_remote.go:145).

## 5. `cmd/entire/cli/strategy/checkpoint_remote.go:222-231` — the new `ls-remote` probe is additive, not a replacement

**Cheaper alternative:** fetch first, and run `ls-remote` only to classify a *failed* fetch as absence-vs-error. That keeps the success path at one round trip and pays the second only on the rare error path, while preserving the positive-evidence contract the comment describes.

**Cost, and on which path:** pre-push, but genuinely narrow. The probe needs `checkpoint_remote` configured AND git-branch primary AND a missing local v1 ref — and under git-branch primary `EnsurePrimaryRef` always ends with a local v1 ref (bootstrap fetch, or `createOrphanMetadataRef` at common.go:543), so the window is effectively one-shot per clone, not recurring. So the probe does **not** replace more expensive work — it adds one handshake, once. Low severity; noted because the comment frames it as establishing a cheaper fact than it does.
