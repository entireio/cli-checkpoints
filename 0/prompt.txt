## Q2 — client-side validation of server rules: right idea, asymmetric placement

The pattern is established here (several files already say "mirrors entire-api's X") and the comment is unusually honest that the bounds are "server parity and nothing more". The thing to name is that the drift is one-directional. Server tightens: CLI merely laxer, one wasted round trip, harmless. Server loosens — 2-char projects, underscores, longer names, all plausible product asks — the CLI hard-refuses a ref that resolves, the error confidently asserts a rule the server no longer makes (`project %q must be 3-32 characters…`), the only workaround is a ULID or a full `entire://` URL, and nothing detects it.

The charset half earns its keep: it is what tells a native ref from `git@github.com:foo/bar`, and it narrows `bareRefSuggestions` (`ab/dogbark` correctly suggests only `/gh/`). The bounds and edge rules buy only the saved round trip, by the comment's own admission.

Placement is inverted. The strict rules live on the *read* path, where being wrong costs a clone the user cannot perform; they are absent from the *write* paths, where a client check would save a real 422 and being wrong costs nothing — I verified `project create` (`cmd/entire/cli/project.go:34-56`) does no name validation at all, and `repo create` now validates only `.git`. Cheapest improvement without changing depth: phrase the bounds failure as a statement about the server rather than a rule of its own, so it degrades into merely unhelpful instead of false. One string, follow-up.
