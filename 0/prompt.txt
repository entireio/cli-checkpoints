## 1. Checkpoint ref naming (ID → git ref)

**File:** `cmd/entire/cli/checkpoint/refs_naming.go`

```go

func RefName(cid id.CheckpointID) (plumbing.ReferenceName, error)                   // :26
func ParseRef(name plumbing.ReferenceName) (id.CheckpointID, bool)                  // :43
```

- `RefName` builds `refs/entire/checkpoints/&lt;shard&gt;/&lt;id&gt;` where `&lt;shard&gt;` = `cid.ShardFor()` and the leaf is `cid.String()`. Errors (does not return a malformed ref) when `cid.Kind() == id.KindUnknown`.
- `ParseRef` is the inverse — strips the prefix, requires exactly `&lt;shard&gt;/&lt;id&gt;` (rejects extra path segments), and re-validates that `cid.ShardFor() == shard`, so mismatched-shard or peeled (`^{}`) refs are rejected. Round-trips with `RefName`.

**Shard logic** — `cmd/entire/cli/checkpoint/id/id.go:134`:

```go
func (id CheckpointID) ShardFor() string {
    s := string(id)
    if len(s) &lt; 2 { return s }
    return s[len(s)-2:]   // LAST two chars, for BOTH legacy-hex and ULID
}
```

Note: this is the **git-refs** ref namespace only. The legacy `entire/checkpoints/v1` branch tree uses a *different* layout — `(id CheckpointID) Path()` at `id.go:249` shards on the **first** two chars (`"a3/b2c4d5e6f7"`). Don't confuse the two.

# Context available for a commit with a MISSING checkpoint

## Summary of the data model

- Commit trailers are defined in `cmd/entire/cli/trailers/trailers.go`. The ONLY Entire-* trailers that exist are: `Entire-Metadata`, `Entire-Metadata-Task`, `Entire-Strategy`, `Base-Commit`, `Entire-Session`, `Entire-Condensation`, `Entire-Source-Ref`, `Entire-Checkpoint`, `Ephemeral-branch`, `Entire-Agent`, `Entire-OPF-Applied`. **There is no `Entire-Trail` trailer** — trail linkage is NOT stored on the commit or in checkpoint metadata.
- Trails are explicitly documented as **branch-centric, served by the core API** (`cmd/entire/cli/trail/trail.go:1-5`): "Trails ... answer why/what ... while checkpoints answer how/when."

---

## 1. Trail linkage (commit/checkpoint → trail number/URL)

**There is no local mapping.** A trail is resolved from a **branch name** via the control-plane API. So the chain is: commit → branch → trail (network call required).

Getting the branch for your commit (all local, git-native):
- `session.State.Branch` — the branch HEAD pointed at when the session last took a turn (`cmd/entire/cli/session/state.go:136-142`). This is the intended "map a stopped session back to its branch" field.
- Or compute which branch(es) contain the commit from git directly (see section 3).

Resolving branch → trail (`cmd/entire/cli/trail_cmd.go`):
- `resolveTrailBySelector(...)` at `trail_cmd.go:229` — when no selector is given, calls `resolveTrailBranch` then `findTrailByBranch`.
- `findTrailByBranch(ctx, client, forge, owner, repo, branch)` at `trail_cmd.go:1899` — matches `t.Branch == branch`.
- `findTrailBySelector` at `trail_cmd.go:1875` — accepts a trail number, id, or branch string.
- `findTrailByNumber` at `trail_cmd.go:1906`.
- All go through `findTrail(...)` at `trail_cmd.go:1912`, which **paginates `GET /api/v1/trails/{forge}/{owner}/{repo}`** and matches client-side. There is no direct "trail by commit/checkpoint id" endpoint.

The resulting `api.TrailResource` (`cmd/entire/cli/api/trail_types.go:22-53`) gives you the trail Number, URL, Title, Status, Base, etc.

Trail number → URL:
- Prefer `TrailResource.URL` (server-supplied).
- Fallback constructor `trailWebURL(base, forge, owner, repo, number)` at `trail_cmd.go:369` → `&lt;origin&gt;/&lt;forge&gt;/&lt;owner&gt;/&lt;repo&gt;/trails/&lt;number&gt;`.
- `trailDisplayURL` at `trail_cmd.go:353` encapsulates the prefer-URL-else-build logic.

Repo/forge resolution: `resolveTrailRemote(ctx)` at `trail_cmd.go:1990` → `gitremote.ResolveRemoteRepo(ctx, "origin")` returns `(forge, owner, repo)`.

Trail metadata display struct: `trail.Metadata` at `cmd/entire/cli/trail/trail.go:134-153` (Number, TrailID, URL, Branch, Base, Title, Body, Status, Phase, Author, Assignees, Labels, Type, Priority, Reviewers, CreatedAt, UpdatedAt, MergedAt). Convert via `TrailResource.ToMetadata()` at `trail_types.go:62`.

## 2. Checkpoint metadata fields (available only when the checkpoint IS present)

Primary struct — `strategy.CheckpointInfo` at `cmd/entire/cli/strategy/manual_commit_types.go:33-45`:
```go
type CheckpointInfo struct {
    CheckpointID     id.CheckpointID `json:"checkpoint_id"`
    SessionID        string          `json:"session_id"`
    CreatedAt        time.Time       `json:"created_at"`
    CheckpointsCount int             `json:"checkpoints_count"`
    FilesTouched     []string        `json:"files_touched"`
    Agent            types.AgentType `json:"agent,omitempty"`      // e.g. "Claude Code"
    IsTask           bool            `json:"is_task,omitempty"`
    ToolUseID        string          `json:"tool_use_id,omitempty"`
    SessionCount     int             `json:"session_count,omitempty"`
    SessionIDs       []string        `json:"session_ids,omitempty"`
    Imported         bool            `json:"imported,omitempty"`
}
```

Author of a checkpoint (from git log on the checkpoints ref): `checkpoint.Author{Name, Email}` at `cmd/entire/cli/checkpoint/persistent.go:2618`, retrieved via `GetCheckpointAuthor(ctx, checkpointID)` / the `AuthorReader` interface (persistent.go ~2626-2636). NOTE: this reads the checkpoint commit, so it is unavailable when the checkpoint is missing.

Richer session-level metadata that carries the "context" fields — `session.State` at `cmd/entire/cli/session/state.go:101`:
- `SessionID` (:103), `CLIVersion` (:106), `BaseCommit`/`AttributionBaseCommit` (:111,:117), `Branch` (:142), `StartedAt`/`EndedAt` (:145,:149), `Phase`/`Kind` (:153,:157)
- `ReviewSkills`, `ReviewPrompt`, `InvestigateRunID`, `InvestigateTopic` (:163-180)
- `TurnCheckpointIDs` (:197), `LastCheckpointID` (:233)
- Token usage: `TokenUsage`, `CheckpointTokenUsage`, `SubagentTokensBaseline` — all `*agent.TokenUsage` (:295,:299,:310)
- `LastPrompt` (:351), `PromptAttributions []PromptAttribution` (:355), `PendingPromptAttribution` (:359)
- `PromptAttribution` struct at `state.go:374` (per-checkpoint user vs agent lines added/removed, per-file maps)

Ephemeral/other checkpoint carriers (also unavailable if the snapshot is gone): `checkpoint.Info` (`checkpoint/checkpoint.go:150`), `checkpoint.EphemeralCheckpointInfo` (checkpoint.go:229).

`explain` builds its checkpoint report from `checkpoint.CheckpointSummary` + `checkpoint.SessionContent` + `checkpoint.Author` + associated commits — see `formatCheckpointOutput` at `cmd/entire/cli/explain.go:1963`. These are the pieces to reuse for a report, but they all require the checkpoint to be readable.

## 3. Commit-derived (git-native) context — ALWAYS available even when checkpoint is missing

`entire trail resume` / `explain` already have helpers you can reuse:

Associated commits + author/date/subject: `getAssociatedCommits(ctx, repo, checkpointID, searchAll)` at `cmd/entire/cli/explain.go:1683`. It walks `repo.Log` (full DAG or first-parent) matching `trailers.ParseCheckpoint(c.Message)`, and produces `associatedCommit` (`explain.go:214`):
```go
type associatedCommit struct {
    SHA, ShortSHA, Message, Author, Email string
    Date time.Time
}
```
Populated from `c.Author.Name`, `c.Author.Email`, `c.Author.When`, and the first line of `c.Message` (explain.go:1692-1706). This is the model for pulling author/subject/date straight from the commit object.

Git author config: `GetGitAuthor(ctx) (*GitAuthor{Name,Email}, error)` at `cmd/entire/cli/git_operations.go:63` (go-git local→global with `git config` fallback). Backing helper `strategy.GetGitAuthorFromRepo(repo)`.

Default-branch / branch detection: `IsOnDefaultBranch` at `git_operations.go:108`; `isOnDefaultBranchRepo` at `:121`; `getDefaultBranchFromRemote`.

"Which branches contain a commit": there is **no existing `git for-each-ref --contains` / `branch --contains` wrapper**. The closest existing logic is `computeReachableFromMain(ctx, repo)` and `walkFirstParentCommits(...)` used inside `getAssociatedCommits` (explain.go:1733-1748) to decide reachability. `for-each-ref` usage in the repo is limited to `cmd/entire/cli/gitrepo/reftable.go` (reftable listing, not `--contains`). To find containing branches you would run git yourself (the repo shells out to git via `exec.CommandContext` as in `getGitConfigValue`, git_operations.go:94) or use go-git `repo.Log`. Trailer parsing helpers to pull checkpoint/session/agent IDs out of the commit message: `trailers.ParseCheckpoint`, `ParseAllCheckpoints`, `ParseSession`, `ParseMetadata` (`cmd/entire/cli/trailers/trailers.go:98-144`).

## 4. Control-plane API client (trail / findings context)

Client: `api.Client` in `cmd/entire/cli/api/client.go` (methods `Get/Post/Patch/Delete` at :135-177; `DecodeJSON`). Base URL via `api.BaseURL()`.

Trail endpoints (all require network + auth):
- List/lookup: `GET /api/v1/trails/{forge}/{owner}/{repo}` via `trailsBasePath` (`trail_cmd.go:1974`) — used by `findTrail`.
- Detail (description/body): `GET /api/v1/trails/{forge}/{owner}/{repo}/{number}` via `trailNumberPath` (`trail_cmd.go:1981`); `fetchTrailDescription` at `trail_cmd.go:378`. **Server keys detail by integer Number, not the UUID ID.**
- Enablement probe: `Client.TrailsEnabled(ctx, forge, owner, repo)` at `cmd/entire/cli/api/trails.go:13`.

Findings/review context tied to a trail (useful for a report): `loadTrailResumeFindingsContext(ctx, client, trailID)` at `cmd/entire/cli/trail_resume_cmd.go:622` → `fetchAllTrailReviewComments` / `fetchTrailReviewComments` (severity/status/freshness filters, `trailResumeTopFindingOptions` at :642). Review types in `cmd/entire/cli/api/trail_review_types.go` (`GET /api/v1/trails/{trail_id}/reviews/...`). Note these use the trail **id**, obtained from the list/detail result.

There is a second, generated OpenAPI client at `internal/coreapi/` (ogen-generated, `oas_client_gen.go` etc.), but the trail flows above use the hand-written `cmd/entire/cli/api.Client`.

**Bottom line for your tool:** trail context is NOT derivable offline — you must (a) determine the commit's branch (from `session.State.Branch` or `git branch --contains`), then (b) call the trails list API and match on `Branch` to get Number/URL/Title/Status. Everything in sections 2's `session.State` and all of section 3 is available locally without the checkpoint snapshot; the checkpoint-commit-derived fields (CheckpointInfo, checkpoint.Author, transcript/token metadata stored in the snapshot) are exactly what's lost when the checkpoint is missing from the remote.</result>
