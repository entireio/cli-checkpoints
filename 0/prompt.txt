<title>explain: missing-blob probe lazy-fetches per blob, hammering mirrors with bogus wants</title>
<description>
> Agent-generated issue. Verify facts against source. Treat proposed solutions, recommendations, and agent-made decisions as hypotheses, not settled direction.

Repo: `entireio/cli`

## Observed facts

* On 2026-08-26 ~21:42–22:12 UTC, `entire explain --checkpoint 01M07BGK52MB63Y83A0RVYQB2N --json` runs (invoked by a codex agent session in a local `entireio/cli` clone) produced **1,805 single-want** `git-upload-pack` **requests** against the `entire://aws-us-east-2` mirrors of `entireio/cli` and `entireio/cli-checkpoints`, all answered `503`. entiredb's shadow classifier tagged 100% of them `verdict:bogus` (objects the repos never contained). The resulting 17–38% error rate on the git-protocol route tripped the availability SLO fast burn and paged P1 ([incident.io](<http://incident.io>) INC-78, Datadog monitor 313962708-family). ap-southeast-2 was paged ~21h earlier by the same server-side class (INC-74).
* Mechanism, verified in source: `prefetchCheckpointBlobs` (`cmd/entire/cli/explain.go:902`) is designed to collect missing blobs and fetch them "in a single `git fetch-pack` invocation per store". But the collection step, `FetchingTree.CollectMissingBlobs` → `blobOnDisk` (`cmd/entire/cli/checkpoint/fetching_tree.go:211`), probes each blob with a bare `git cat-file -e <hash>`. In a `blob:none` partial clone with promisor remotes, `cat-file -e` on an absent object triggers git's internal lazy fetch — one single-want upload-pack request **per configured promisor remote** — before reporting the blob missing. The batching never gets a chance.
* Each failed probe costs ~1s (remote-helper spawn + discovery per attempt, plus node failover inside the helper), so ~900 probed blobs took two ~14-minute grinds while the user-facing command sat on a spinner. Repo-local `.entire/logs/entire.log` shows the prefetch failing (`explain prefetch: cp subtree not found`, 14:46:17 and 14:56:46 -07:00) and per-file fallback reads >1s apart.
* Trigger condition: a checkpoint referenced by a commit trailer whose blobs exist only in local refs (never pushed), so every probe is a guaranteed miss on both mirrors. Any repo with the standard two entire promisor remotes doubles the requests.
* Server-side amplification (separate issue, <issue id="99c35963-dd1b-4bf4-a691-66c80401f30e" href="https://linear.app/entirehq/issue/ENT-1939/decide-whether-to-flip-the-missing-want-503-default">ENT-1939</issue>): entiredb answers never-existed wants with `503 + Retry-After: 5` instead of a terminal 40x, so these client misses count against the git-protocol availability SLO.

## Proposed approach

Set `GIT_NO_LAZY_FETCH=1` (or `--no-lazy-fetch`) on the `git cat-file -e` probe in `blobOnDisk` so the missing-blob analysis is a pure local check and the prefetch batches as designed. Audit the other `git cat-file` call sites in `fetching_tree.go` (`readFileViaGit`, the per-File fallback path) for the same hazard — the per-File fallback may *intentionally* fetch, but it should fetch once per blob, not probe-fetch during analysis.

## Alternatives

* Client-side negative caching / early abort after N consecutive missing-blob fetch failures in one explain run (bounds the damage but keeps the per-blob probes).
* Rely solely on the server fix (<issue id="99c35963-dd1b-4bf4-a691-66c80401f30e" href="https://linear.app/entirehq/issue/ENT-1939/decide-whether-to-flip-the-missing-want-503-default">ENT-1939</issue> terminal 40x): stops the SLO burn but keeps explain slow (~1s per missing blob) and keeps the request storm.

## Open questions

* Should the per-File fallback fetcher also stop attempting remote fetches for blobs already classified missing by the prefetch analysis in the same run?
* `GIT_NO_LAZY_FETCH` requires git ≥ 2.43; confirm the CLI's minimum supported git version or use `cat-file --no-lazy-fetch` / batch `cat-file --batch-check` with the env var accordingly.
