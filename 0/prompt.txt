### 1. Mechanism for #1349: owned `lefthook-local` artifacts — **CORRECTLY SCOPED** (with a caveat)

**Change:** `lefthook_{integration,detection,artifacts,transaction,yaml}.go` write `lefthook-local.yml` + `.lefthook-local/&lt;hook&gt;/entire.sh` + a `.git/info/exclude` block, all ownership-marked.

**I verified the cheap alternatives before crediting this.** Option (4) self-repair is **not** a cheaper alternative — *it already exists and ships today*. Baseline `strategy.EnsureSetup` (`common.go:96`):

```go
if !IsGitHookInstalled(ctx) {
    if _, err := ReinstallGitHooks(ctx); err != nil { ... }
}
```

…and `EnsureSetup` runs at every TurnStart. So a lefthook reclaim is already repaired on the next agent turn. The residual gap is exactly what the reporter guessed: a push/commit between a lefthook re-sync and the next Entire invocation. That gap is **real and uncoverable by self-repair** — there is no file left to hook.

The mechanism is also the *right* seam rather than an arbitrary one, for a reason the PR never states but which justifies it: lefthook resolves `lefthook.yml` + `lefthook-local.yml` **at run time, not install time**. So the moment Entire's artifacts exist, an *already-installed* lefthook launcher dispatches to them — no `lefthook install`, no user action, no refresh needed. And `source_dir_local` is a clone-local, gitignorable namespace, so Entire never edits shared config. Husky/Rush/pre-commit have no equivalent (their hook bodies are committed and shared), which is why generalizing here would be worse, not better.

**Verdict: keep the mechanism.** The caveat is packaging, not depth: this is a #1349/#2263 fix and belongs in its own PR. Cost attributable to it: ~1,515 production + ~1,521 test ≈ **3,036 lines** riding on a `Fixes #2264`.

### 2. Two-phase transaction layer — **TOO DEEP** (~600 lines)

**Change:** `lefthook_transaction.go` `stagedLefthookFile` with `stage → deactivate → publish → finishDeactivation → rollbackStagedLefthookFiles` (380 lines), plus `snapshotHookIntegration`/`restoreHookIntegrationSnapshots` in `hook_integration_transaction.go` (84 lines) which buffers **17 files** (`lefthook-local.yml`, `info/exclude`, and per-hook script + hook + backup) into memory before every install.

**Depth vs problem:** this is ACID semantics over 7 small idempotent file writes. The pre-existing native installer (`InstallGitHook`) writes 5 hook files non-transactionally and has done so for the project's whole life; no issue in the set reports a torn install. Worse, the two layers are redundant: an inner per-file stage/rollback *inside* an outer whole-tree snapshot/restore, so a mid-publish failure unwinds twice.

The odd `deactivate()` step (create temp, close, remove, rename config aside, publish scripts, delete the aside) exists to make the config invisible while scripts are being written — a window measured in microseconds, in a file only read when a git hook fires.

**Right altitude:** the operations are already idempotent and content-compared (`errLefthookFileUnchanged`). Write scripts first, config last — config-last *is* the commit point, because the config is what makes lefthook dispatch. A failed run leaves orphan scripts that the next run overwrites. `EnsureGitHookIntegration` is called on every turn start, so "retry heals it" is a guarantee, not a hope.

**Savings: ~350 production + ~250 test = ~600.**

### 3. Two bridges at once + body-shape matching — **TOO DEEP** (~350 lines)

**Change:** native hooks are installed *and* lefthook artifacts are installed, then reconciled by `inspectActiveHookDelivery` (22 lines) and `restoreProvenLefthookBridges` (45 lines), which needs `looksLikeLefthookHook` + `knownLefthookV2Body` + `knownDirectEntireLefthookBody` (110 lines) to tell the two apart.

This is a hedge, not a root-cause fix, and the runtime-resolution fact from §1 is why. Read `EnsureGitHookIntegration` in order (`hook_integration_transaction.go:113-215`):

1. install lefthook artifacts;
2. if `!activeCurrent`, **also** install native wrappers over lefthook's launcher;
3. then `restoreProvenLefthookBridges` renames `&lt;hook&gt;.pre-entire` **back over** the wrapper just written, if the backup looks like a lefthook launcher.

Step 3 undoes step 2. The PR writes a state and then reconciles it, when the decision was available beforehand: *if the file at `&lt;hook&gt;` is a lefthook launcher and the lefthook artifacts are current, don't wrap it at all.* Decide ownership per hook before writing. The native bridge is then needed only in the genuinely different case — lefthook config present but `lefthook install` never run — and it is the plain existing installer.

**The 90-line matcher is the sharpest instance of over-depth.** `knownLefthookV2Body` embeds a **byte-exact copy of lefthook's generated wrapper tail**, including every package-manager probe branch (`mise`, `devbox`, `uv`, `swift package`, `mint run csjones/lefthook-plugin`, `bundle exec`, `yarn`, `pnpm`, `go tool`…). Byte-exactness buys nothing here: the file is already trusted to execute as a git hook, and whether Entire is actually wired is proven separately by `inspectLefthookArtifacts`. The predicate only needs to establish *lefthook is the dispatcher*, which is `strings.Contains(content, "call_lefthook run \""+hook+"\"")` — about 8 lines.

**Savings: ~200 production + ~150 test = ~350.**

### 1. `strategy/lefthook_transaction.go:149–368` — the hand-rolled two-phase commit re-implements `jsonutil.WriteFileAtomicIn` — **~185 lines**

`stagedLefthookFile` + `stageLefthookFile` + `deactivate` + `finishDeactivation` + `publish` + `rollbackStagedLefthookFiles` + `cleanupStagedLefthookFiles` + `publishLefthookTransaction` + `stageLefthookArtifacts` = 212 lines to write 7 small files.

Two independent reasons it is more machinery than the job needs:

- **`jsonutil.WriteFileAtomicIn` (write.go:85) already is `stageLefthookFile`+`publish`**: `OpenParentNoSymlinks` → `CreateTempIn` → write → `Chmod` → rename, with deferred temp cleanup. The staged type adds only per-file rollback bookkeeping.
- **The rollback bookkeeping is redundant with the outer snapshot layer.** `installLefthookFilesAt` runs only from `EnsureGitHookIntegration` (`hook_integration_transaction.go:175`), which has already snapshotted all 17 relevant paths at :131 and restores every one on any failure via `fail(...)`. So there are two nested rollback mechanisms for the same files; the inner one never gets to do anything the outer one wouldn't.
- **`deactivate`/`finishDeactivation` buys nothing.** Its purpose is "lefthook must not see a config referencing scripts mid-write". Write order gives that for free: scripts first (each an atomic rename), config last. A concurrent hook run then sees either the old script or the new one — both valid — and never a config pointing at a missing file.

**Simpler form:** a `[]lefthookWrite{root, name, data, mode, counted}` built in order (scripts → `info/exclude` → config last), each applied with `jsonutil.WriteFileAtomicIn`, keeping the existing unchanged-content skip for the `written` count. ~30 lines replacing 212, plus ~15 lines of plumbing dropped from `installLefthookFilesAt:85–105`.

### 2. `strategy/session_state.go:347–587` + `lifecycle.go` — the warning claim protocol has two stores where one does the job — **~125 lines**
