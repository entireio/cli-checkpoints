## Answers

**a. Does `← open sidebar` appear in every pane, including mid-turn?**
It appears in **all 13 captured panes — but every one is idle**, so the captures prove nothing about mid-turn. The v1.0.81 source says the opposite of what `e2e/agents/copilot-cli.go:27-30` currently claims. In `app.js`, the footer component `b_e` computes `V = activityIndicator != null &amp;&amp; !== false` and renders:

```js
V ? &lt;Fragment&gt;&lt;MQe vimMode/&gt;{B}&lt;/Fragment&gt; : &lt;Gon {...e}/&gt;
```

`Gon` → `bWr` is the function that pushes the `{left:"open sidebar"}` hint (verified: `bWr` is the enclosing function of the `open sidebar` literal, and `Gon` renders `bWr`). So **while an activity indicator is live (i.e. a turn is running), the hints row containing `← open sidebar · / commands · ? help · tab next tab` is replaced by the activity row.** Only the right-hand `Claude Haiku 4.5` model segment persists (it is rendered in a sibling column). The code comment "like the old ❯, it is drawn while Copilot is working" appears to be **wrong for v1.0.81**.

**b. Is there a busy-only indicator?**
Yes, in source. The activity indicator is `Mje` / `ThinkingAnimation`:

```js
s = e.mode==="executing" ? "Executing"
  : e.mode==="cancelling" ? "Cancelling"
  : e.currentIntent ?? "Working"
```
plus an optional `· &lt;bytes&gt;` streaming size, and — rendered alongside it in the caller — an esc hint whose description is `"interrupt"`, `"stop agents"`, or `` `again to ${…}` ``. There is also the standalone `"Thinking…"` / `Thought for Ns` transcript entry (the `⌄ Thought for 1s` block visible in captures is its settled form) and a `(Esc to cancel)` variant used when `showHelperText` is not disabled — the main-loop call site passes `showHelperText:!1`, so the busy row should read roughly:

`Working · &lt;n&gt; kB   esc interrupt                     Claude Haiku 4.5`

None of these words (`Working`, `Executing`, `interrupt`, `Esc to cancel`) occur in **any** captured pane in either run — consistent with all captures being idle.

**c. Does `❯` appear in v1.0.81 panes?**
**Never in the pane body** — the only occurrences in the v1.0.81 artifacts are inside the harness's echoed regex string. Source explains it: the input frame `Il` defaults to `prompt:"❯ "`, but the `variant:"rail"` branch (the one that draws `╻`/`┃`/`╹`, glyphs `\u257B`/`\u2503`/`\u2579`) does not render the prompt at all. Where `❯` does still appear is as a **list-selection cursor**: `┃ ❯ • 1.` in the session-restore picker and `│ ❯ 1. Yes` in the trust dialog (both captured in the v1.0.82 run), which is exactly the ambiguity `copilotPromptReady` guards against.

**d. The idle input box.**
Three rows, full terminal width: `╻` + `▄`×(width−1); `┃` alone; `╹` + `▀`×(width−1) — the vertical rail (`╻┃╹`) is a separate left column, the `▄`/`▀` are the top/bottom borders of the box body (`KUt = {top:"▄", bottom:"▀", left:"", right:""}`). It is identical in both captured states, and there is no source evidence of a text difference while busy — only the accent color of the rail can change, which tmux pane text capture does not record.

## Verdict

**A reliable busy marker is likely to exist, and it is stronger than you asked for: `← open sidebar` itself appears to be idle-only in v1.0.81** — the hints row is swapped out for the activity row for the whole duration of a turn. If that holds, the current `WaitFor` pattern is already a genuine idle signal rather than an always-true match, and waiting for the *absence* of `Working|Executing|esc interrupt` would be redundant.

But this rests entirely on reading the minified v1.0.81 bundle. **Zero mid-turn panes exist in CI artifacts**, because the harness only dumps after settle. Before you change the runner on this basis, get one cheap empirical confirmation — e.g. a one-off local `copilot` session with a `tmux capture-pane` on a timer mid-turn, or a temporary debug dump inside `WaitFor`'s poll loop that writes the first non-matching pane to the console log. That would cost one prompt, not a suite run.
