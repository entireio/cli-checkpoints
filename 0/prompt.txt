- `tsc`-typed hook signatures (`input.sessionID` on the transform, `args: any` on `tool.execute.after`) match 1.18.30.

### Issues

**Critical** — none.

**Important**

1. `cmd/entire/cli/agent/opencode/entire_plugin.ts:176` — the learn is unconditional and mis-learns on every assistant message. `AssistantMessage.parentID` is a *required* field in 1.18.30 (the parent **user-message** ID — AGENT.md's own "Do not confuse the two" warning). So every `message.updated` for an assistant message, parent's or child's, adds a `msg_…` ID to `childSessions`. It is masked today only because (a) message events resolve `eventSessionID` via `info.sessionID` before `info.id`, and (b) `msg_`/`ses_` prefixes cannot collide. But the set grows by one entry per assistant message for the life of a TUI process, and the comment at 22-23 ("learned from `parentID` on session.created / session.updated") describes code that does not exist. Fix: gate the learn on `event.type === "session.created" || event.type === "session.updated"` (or `startsWith("session.")`). The `learn` marker in `TestInstallHooks_ChildSessionsNeverFireLifecycleHooks` must change with it.

2. `entire_plugin.ts:252-260` and `:161` — child identity is learned from a single source when two others are in hand. Both `part.state.metadata.sessionId` and `output.metadata.sessionId` positively name a child, and neither adds it to `childSessions`. This is the answer to the "never saw `session.created`" question: an OpenCode restart mid-task is benign (the child turn dies with the process; the model relaunches), but **`task_id` resumption** of a child created in an earlier process, or any path where the child's first plugin-visible event is not `session.*`, reopens the original bug for that task — the child's user `message.updated` (`UserMessage` has no `parentID`) hits `resetSessionTracking(child)` → `session-start` + `turn-start` for the child and clears the parent's `seenUserMessages`. Worse, a later child `session.updated` *does* carry `parentID`, so the child is learned mid-turn and its `turn-end` is suppressed: a phantom Entire session left ACTIVE until the sweep. Half-tracked is worse than either extreme. Adding `childSessions.add(part.state.metadata.sessionId)` at 254 closes the common case because the running part (+7ms) precedes the child's first `message.updated` (+127ms) in the captured order; adding it at 161 too costs nothing. Whether `session.updated` for a resumed child fires before its `message.updated` in 1.18.30 is unverified, which is the argument for not relying on it.

**Minor**

3. `entire_plugin.ts:301-302` — clearing `childSessions`/`announcedTasks` on `session.deleted` is the wrong granularity. A child's deletion never reaches this case (the guard at 179 returns first), so the clear only ever fires for a *top-level* session — including an unrelated old one deleted from the TUI's session list while a task is running, which drops a live child back to top-level. Keeping the sets across parent switches (which the change does, via `resetSessionTracking` not touching them) is correct: child identity is not relative to the current parent. Suggest dropping the clear here and keeping only the `server.instance.disposed` one at 320-321. (`currentSessionID = null` on unrelated deletion is pre-existing and out of scope.)

4. Cost of `callHookSync` in `tool.execute.after` (`entire_plugin.ts:163`). The blocked span is: `sh` + `entire` startup, `sessionTranscriptPath`, `opencode export &lt;child&gt;` (a full Bun process start plus DB read — AGENT.md's "tens of ms" understates this; expect a few hundred ms), JSON validate + token calc, then `completeSubagentTaskRecord` under the session flock. No eager condense mid-turn (parent is ACTIVE). Realistically ~0.5–1.5s per foreground task on a healthy machine, added to the parent's turn before the model sees the tool result. The Go side bounds the export at `openCodeCommandTimeout = 30s` (`cli_commands.go:20`), but `spawnSync` itself has no `timeout` — same as the existing sync hooks, so consistent, and fail-open is already the design (a live record is retried at SessionEnd). Acceptable given the `opencode run` exit constraint; a `timeout:` on `spawnSync` for all sync hooks would be a cheap floor and belongs in a follow-up, not this change.

5. `entire_plugin.ts:272` — inner `const props` in the `session.status` block shadows the hoisted `props` at 174, and 182/194/228/286/295 still re-derive `(event as any).properties?.info` now that `props`/`info` exist. Compiles (block scope) but reads as two half-migrated styles; use the hoisted values.

6. `entire_plugin.ts:155-171` — `tool.execute.after` has no enclosing try/catch, unlike `event`. Safe today (all accesses optional-chained; `callHookSync` catches internally) and matches the pre-existing `system.transform` shape, but the repo convention is "everything inside try/catch". Low priority.

7. Tests (`hooks_test.go:435-500`): consistent with the file's string-inspection approach and no more brittle than the siblings (no `t.Parallel()` because of `t.Chdir`, matching the other 17). Two nits: the negative assertion at 498 checks only that `subagent-stop` is not async, not `subagent-start`, though the same rationale applies; and fixing item 1 will require changing the pinned `learn` string — expected for this style.

8. `AGENT.md` "Proposed Mapping" still says "The plugin must forward `parentID` … so the Go side can make the suppression decision from the payload." The shipped design decides plugin-side and the Go side never sees child events at all — a justified improvement (less payload, no ordering dependence), but the paragraph should be rewritten to describe what shipped. Also worth one line documenting that a user who drives a child session directly in the TUI is fully suppressed (acceptable, but deliberate).
