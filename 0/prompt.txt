## Critical Gaps

**1. Quoted-capture head suppression exposes real passwords — untested and verified end-to-end (criticality 9, under-redaction).**
The upstream generic-password *unquoted* value charset is `[^\s'"`,;]{4,}` — it can never contain `;`, `,`, space, or tab, only `&amp;`. So those four delimiters at redact.go:425 fire exclusively on *quoted* captures — exactly where the finding is the verbatim password and splitting at the first delimiter misclassifies. Verified through the real `redact.String`:
- `password="changeme;realSecret42"` → **unredacted** (head `changeme`)
- `password="example S3cr3t!x"` → **unredacted** (head `example` is in `placeholderSecretValues`, redact.go:75)
- `password="changeme now rotate B4Prod!"` → **unredacted**
- `password="redacted then reset to Xk29!f"` → **unredacted** (head `redacted`)

No other layer rescues these (layer 7's `[^\s,;&amp;]+` value capture stops at the space/`;` and sees only `"changeme`, which quote-trims to a placeholder). Regression it prevents: this is the exact failure mode redaction exists for — a real secret shipped to the checkpoint branch. At minimum a test should pin the intended behavior for a quoted secret with a placeholder first token; more likely the fix is to restrict the head check to `&amp;` (or to unquoted-shaped secrets). Given the repo's redaction-corpus practice, this deserves a decision, not silence.

**2. `i &gt; 0` guard has no test (criticality 7, under-redaction on refactor).**
If the guard regresses to `i &gt;= 0` (e.g. a refactor to `strings.Cut`), the head becomes `""`, and `isPlaceholderSecretValue("")` returns **true** (redact.go:432-434) — every delimiter-leading finding would be suppressed. A one-case pin (finding secret starting with `&amp;`, e.g. `password=&amp;Xk29!fQz7`) would catch that mutation. Currently nothing does.
