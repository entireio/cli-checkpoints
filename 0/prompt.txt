Bounded and small for `entire login` (one open, process exits shortly after), more relevant for `experts_tui.go:233`, which is long-lived and can open several links. **Cheaper alternative:** `exec.Command` (no ctx) with `//nolint:noctx` — the ctx is dead weight here, since the code deliberately `Release()`es the child and never wants to kill the user's browser on login-context cancellation. ## Measured non-findings (all of the flagged concerns check out clean)

**Dependency weight is free.** `golang.org/x/sys/windows` was already in the Windows import graph at `main` with 26 importers, two of them in-repo (`cmd/entire/cli/execx`, `cmd/entire/cli/internal/flock`), plus go-git, bubbletea, wincred, posthog. On non-Windows it is absent from both the binary graph and the darwin test binary graph (`go list -test -deps` → 0 hits), because `_windows.go` filename constraints apply to test files too.

Measured `GOOS=windows go build -trimpath ./cmd/entire`: **72,246,784 → 72,247,808 = +1,024 bytes (+0.0014%)**, which is PE page rounding around 5 new symbols (`cli.shellExecute`, `cli.openBrowserPlatform`, `windows.ShellExecute`, `windows.procShellExecuteW`, `windows.StringToUTF16`). Darwin: +80 bytes.

Also worth correcting the premise: `pr-binary-size.yml` runs `scripts/check-pr-binaries.sh` with `MAX_BINARY_SIZE_BYTES=1048576` against *committed blobs* in the PR diff. It never compiles anything, so compiled binary weight is not what that workflow guards.

**Process cost: strictly cheaper, nothing added.** Old path was a cmd.exe process whose `start` builtin then did its own ShellExecuteEx. New path is one lazy `shell32.dll` resolve plus one `Syscall6`. It also drops the `watchCtx` goroutine leak from finding 2 on Windows.

**`var shellExecute = windows.ShellExecute` has zero init cost.** Verified by codegen: the var is statically initialized into `SDATA size=8` with a relocation, and the package `init` body is `STEXT nosplit size=1` — empty. Indirection is one extra `MOVQ shellExecute(SB), DX` before an indirect call; the function measured 100 bytes via the var vs 98 bytes calling directly. It defeats no inlining — `windows.ShellExecute` wraps `syscall.Syscall6`, and both variants report `cost 132 exceeds budget 80`. The only genuinely new init work is x/sys's `procShellExecuteW = modshell32.NewProc("ShellExecuteW")`, which was dead-code-eliminated at `main` (confirmed: absent from `base.exe`, present in `head.exe`). `LazyDLL.NewProc` is `return &amp;LazyProc{l: d, Name: name}` — one 32-byte alloc, no DLL load, no symbol resolution. `modshell32` itself was already in `base.exe`, so the DLL descriptor was already paid. Tens of nanoseconds, once per process, Windows only.

**`StringToUTF16Ptr` allocates once, and once is the minimum.** `&amp;StringToUTF16(s)[0]` heap-allocates `(len(s)+1)*2` bytes (~450 bytes for a real authorization URL). Called exactly once per `openBrowser`, and any wide-string Win32 API requires it. Nothing to shave.

**Not a hot path.** Two callers: `login.go` and `experts_tui.go:233`, both explicit one-shot user actions. Nothing was added to startup or to the hook path.

**The test closure retains ~220 bytes at worst.** It captures `got` only — not `t` — so `got` boxes to a heap string cell. `t.Cleanup` always runs (including after `t.Fatalf`), making the closure unreachable at test end. Even if the restore were skipped, the retained set is a 16-byte string header plus one ~200-byte URL string. Genuinely negligible.
