**File:** `cmd/entire/cli/strategy/caller_session.go:145-195`

```go

	candidates := agent.CallerSessionCandidates()
	if len(candidates) == 0 {
		return ResolvedSession{}, false
	}
	byID := indexByID(states)
	ancestry, haveAncestry := proclive.CurrentAncestry()

	// Pass 1: nearest tracked candidate, if any.
	var best ResolvedSession
	var bestState *SessionState
	bestDepth := -1
	for _, c := range candidates {
		state, tracked := byID[c.SessionID]
		if !tracked {
			continue
		}
		depth := -1
		if haveAncestry &amp;&amp; state.Owner != nil {
			depth = ancestry.Depth(*state.Owner)
		}

			best = ResolvedSession{SessionID: c.SessionID, Resolution: ResolutionCallerEnv, AgentType: c.AgentType, Tracked: true}
			bestState, bestDepth = state, depth
		}
	}
	// Pass 2: nothing tracked — the first published claim is still a real
	// diagnosis (Tracked==false), so report it rather than nothing.
	if !best.Found() {
		first := candidates[0]
		best = ResolvedSession{SessionID: first.SessionID, Resolution: ResolutionCallerEnv, AgentType: first.AgentType}
	}
	// ...debug log, return best, true
}
```

### 1. Tier 4 (`other-worktree`) — report-don't-remove is defensible, but it's only half the fix

TTY-gating (alternative b) is weaker than it looks: this repo's own TTY-detection is documented (`interactive.CanPromptInteractively`) as a five-tier, easily-defeated heuristic, and gating tier 4 on it would silently change `--json`'s behavior based on terminal attachment — `--json` output is inherently meant for non-interactive consumption, so TTY-gating would essentially always suppress tier 4 there while doing nothing to stop a human's own non-interactive script from losing the "what's happening here" answer they wanted.

An explicit `--any-worktree` flag (alternative c), however, is a genuinely stronger design the diff doesn't discuss: it would make the *default* invocation of `session current`/`tokens` — the one an agent runs unprompted — return nothing rather than a foreign session's ID, and would require a positive, visible opt-in to get the guess at all. The cost is a UX regression for the human "what's going on here" case (an extra flag to discover) and it doesn't cover an agent that decides to pass the flag anyway — but it directly closes the exact incident shape described (an agent reads `session current`'s default output and acts on it) at the source, rather than relying on every downstream consumer to check `IsCaller()`.

Whether "report tier 4 + gate on `IsCaller()`" is *actually* the right depth therefore hinges entirely on every action-taking consumer honoring `IsCaller()` — see finding 2, where the one consumer the incident report names (`session adopt`) does not.

### 2. `session adopt` is where the diff's own incident description says the harm happens, and it is completely unguarded

`cmd/entire/cli/session_adopt.go:68-123` (`runAdopt`), `:312-362` (`selectAdoptSourceSession`), `:364-375` (`sessionBelongsToSourceWorktree`)

`session_adopt.go` imports neither `ResolveCallerSession` nor `IsCaller` — confirmed by grep, zero hits. Its own trust model is narrower than "most recent in the store" (it requires an explicit `--from &lt;worktree&gt;`, and its auto-selection is scoped to sessions *in that worktree*, filtered to a 12h-recent, adoptable window), but it has **no mechanism at all** to check that the session it's about to mutate is the *calling* agent's own — `sessionBelongsToSourceWorktree` only checks internal self-consistency (does this ID belong to the named worktree), never "is this mine." Concretely: if an agent reads `entire session current --json` in a worktree with no sessions of its own, it gets back a real, `other-worktree`-tier session ID plus that session's `worktree_path` in the same JSON envelope. Worse, the hazard doesn't even need `session current`: `entire session adopt --from &lt;any-worktree-path&gt;` with no positional ID, where that worktree happens to have exactly one recent adoptable session (a common case — that's literally what made the old `FindMostRecentSession` fallback return a plausible-looking answer), auto-adopts it with zero caller verification, independent of anything this diff touched.

Given `IsCaller()` now exists as exactly the primitive `session adopt` would need (e.g., refuse or require `--force`/confirmation when the resolved candidate for an implicit adopt is not `IsCaller()`-true, or at minimum warn before mutating when the session was reached via `session current`'s weak tier), shipping the resolver without wiring it into the one command whose damage the incident report is about is a real gap, not a cosmetic one. ### 3. Two ancestry-matching implementations — should be one shared primitive, and the fix is cheap

`cmd/entire/cli/strategy/caller_session.go:225-253` (`sessionIDByOwnerAncestry`) vs. `cmd/entire/cli/strategy/session_identity.go:84-112` (`findSessionByCommitAncestry`)

### 4. Env-var tier seam (`agent` declares, `strategy` reads) is the right altitude — reading fresh beats persisting

`cmd/entire/cli/agent/caller_session.go:127-136` (interface), `cmd/entire/cli/strategy/caller_session.go:145-195` (`resolveCallerFromEnv`)

This matches the established pattern elsewhere in the codebase (`agent.TranscriptSanitizer`, `agent.SessionEndBudgeter`): per-agent capability declared in `agent`, consumed by business logic in `strategy` that needs session state the `agent` package doesn't have (avoiding the same kind of import-cycle the `settings` package exists to break). I don't think a `HookInput`-style protocol change or persisting the ID onto `SessionState` at hook time is a deeper fix here, and the reason is different from the `ReadTranscript(path)` case CLAUDE.md discusses: that case needs persistence because the *reader* (`os.ReadFile(sessionRef)`) is a different process than the one that resolved the path, so containment has to be re-derived from data that outlived the original resolution. Tier 1 has the opposite shape — the process asking "which session am I" is, by construction, the same process (or a descendant) that has the env var in its own environment right now. Persisting the ID onto `SessionState` at turn start wouldn't help a *different, later* process identify itself as the caller (it isn't the caller), so it would serve a different purpose (recording provenance for diagnostics) than tier 1 actually needs. I'd call this the "altitude is right" case the task rules invite: the seam mirrors an existing, working pattern, and the alternative doesn't solve a problem tier 1 actually has.

### 5. Test-harness isolation follows half of the documented two-layer pattern — and the missing half may not transfer cleanly here

`cmd/entire/cli/integration_test/setup_test.go:78-84`, `e2e/tests/main_test.go:56-59`, plus three near-identical `clearCallerSessionEnv(t)` helpers (`cmd/entire/cli/session_current_test.go:26`, `cmd/entire/cli/agent/caller_session_test.go:85`, `cmd/entire/cli/strategy/caller_session_test.go:18`)

CLAUDE.md's "Config/Cache/Keyring Isolation in Tests" section documents two layers for this exact class of problem (a developer's real agent environment leaking into `go test`): an in-process safety net baked into the resolver itself (`userdirs`/`tokenstore` detect `testing.Testing()` and fall back automatically, "shared across tests in one process" with no per-test opt-in needed) *and* explicit TestMain-level env plumbing for spawned binaries, which `testing.Testing()` can't see. This diff replicates only the second layer — correctly, and via the same registry-derived, can't-rot mechanism the rest of the section prizes — but adds nothing resembling the first: `agent.callerSessionIDFromEnv` (`cmd/entire/cli/agent/caller_session.go:169-175`) calls `os.Getenv` unconditionally, with no `testing.Testing()` awareness, unlike `userdirs.Config()` or `interactive.CanPromptInteractively()` (which explicitly special-case it, per `cmd/entire/cli/interactive/interactive.go:40`). The result is that isolation for in-process unit tests is entirely opt-in, hand-copied into three files, and depends on every future test that exercises `ResolveCallerSession`/`CallerSessionCandidates` remembering to call it.

That said, I don't think a straight port of the `userdirs` pattern is free here the way it was there, which is worth being honest about: `userdirs` can gate its *fallback* on `testing.Testing()` because the override (`$ENTIRE_CONFIG_DIR`) and the fallback (a resolved default directory) are two different code paths — the override still wins under test. Caller-session env vars have no such second channel: the "deliberate test override" (`t.Setenv("CODEX_SESSION_ID", ...)`) and the "leaked from the real shell" case are the *same* `os.Getenv` call, so a blanket `testing.Testing()` gate would also blind every positive-case test (`TestCallerSessionCandidates_ReadsThePublishedID` and friends) unless a second signal were invented to distinguish them — real added complexity, not a drop-in. The blast radius is also smaller than the config/cache case CLAUDE.md was written for: a leaked var here fails a test assertion locally; it doesn't write into the developer's real `~/.config/entire`. Given that, the chosen approach — TestMain isolation plus opt-in per-test clearing — is a reasonable place to stop, though it is a symptom fix relative to the documented ideal, and the honest cost of the "deeper" version should be named rather than assumed away. Separately, and much more minor: the three `clearCallerSessionEnv` copies could collapse to one if there were a shared test-helper location all three packages can import without a cycle (`testutil` currently imports neither `agent` nor `strategy`, and isn't imported by either in production code) — not worth doing on its own, but worth folding in if a shared test-helper package is ever introduced for other reasons.
