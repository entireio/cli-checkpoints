When the user picks "Save — push to a new branch", `configureSaveAndPush` runs `git switch -c pushBranch`, commits the newly generated onboarding files (e.g. `.entire/settings.json`, agent hook config) there, pushes, then runs `git switch branch` here to return to the original branch. I reproduced this with a local git repo: since those files are tracked only on `pushBranch` and don't exist in `branch`'s tree, and the working tree is clean at that point, `git switch` silently deletes them from the working directory rather than leaving them as local changes. The onboarding flow then prints "✓ Configuration complete … You're set. Start a session with any selected agent" even though the just-written config/hook files are now gone from disk (they only exist on the unmerged `pushBranch`). The same `git switch branch` call in the deferred restore-on-failure path (around line 1344) has the identical effect.

`configureRulesBlockDirectPush` only treats `pull_request`, `required_status_checks`, `required_deployments`, `required_signatures`, `merge_queue`, `update`, and `workflows` rule types as push-blocking. GitHub rulesets also support a `lock_branch` type ("Lock branch" — makes the branch fully read-only), which isn't recognized here. A branch locked via that rule would be treated as unprotected, so `configureBranchProtected` returns `false` and the flow offers/attempts "Save — push to `<branch>`" (`configureSaveDirect`), which will fail server-side instead of falling back to the new-branch flow.
