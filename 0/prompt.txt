# Security review — `feat/global-trust` (global tracking tier)

Scope: non-test Go files in the branch diff vs `origin/main`, traced from repo-controlled inputs (committed `.entire/*`, submodules, symlinks, `core.hooksPath`, remote URLs) to file writes, argv, activation, and egress decisions. Two findings clear the confidence bar; both share one root cause.

---

## Finding 1 — Repo-shipped `.entire/settings.json` is treated as the user's own repo-level enablement: activates capture in excluded repos, runs full setup (git-hook install + worktree writes) from user-level hooks

- **Where:** `cmd/entire/cli/settings/repopolicy/policy.go:36-51` (activation precedence), `repopolicy/activation.go:50-80` (`ReadRepoActivation` — project file = "configured", default enabled), `repopolicy/types.go:106-111` (`RuntimeRoot` → `&lt;worktree&gt;/.entire` for `ActivationLocal`), `cmd/entire/cli/strategy/global_setup.go:196-213` (`EnsureSetupForHook` → `ensureSetup` when repo-configured), `strategy/common.go:316-337` (`ensureSetup`: `EnsureEntireGitignore`, `EnsurePrimaryRefTo`, `installGitHooks`), `cmd/entire/cli/hook_registry.go` (`executeAgentHook` → `prepareHookPolicy`), `cmd/entire/cli/root.go:147-150` (comment acknowledging the pin-out).
- **Severity:** Medium (High when combined with Finding 2)
- **Category:** consent/exclusion bypass; unintended writes in a never-enabled repo
- **Confidence:** 0.8

**Description.** With `global.enabled=true`, Entire's hooks fire in every repo via `~/.claude/settings.json` / `~/.gemini/settings.json`. `ClassifyRepoPolicyAt` consults the repository's own `.entire/settings.json` *first*; a project file with any content (or `enabled` absent) yields `Configured &amp;&amp; Enabled` → `ActivationLocal`, and in that branch `exclude_paths`, `exclude_paths_exact` and `exclude_origins` are never evaluated (they live only in `ClassifyGlobalConfig`, reached from the `default:` case). On main, a committed `.entire/settings.json` was inert until the user ran `entire enable` (or accepted Claude Code's project-hooks trust prompt); on this branch a bare clone is sufficient. The code treats "repository ships `.entire/settings.json`" as indistinguishable from "this user ran `entire enable` here", but the former is attacker/third-party content.

Consequences for such a repo, all without any user action beyond opening an agent session in it:
1. Capture is active even when the worktree matches the user's `exclude_paths`/`exclude_origins` (the branch's own guarantee for excluded repos is bypassed by repo content).
2. `EnsureSetupForHook` takes the *repo-configured* route (`RepoActivationConfigured` = true) and runs the full `ensureSetup` — it installs Entire's git hooks into the repo's hooks dir **without** the `HooksDirIsWorktreeResident` guard that the global route applies, writes `.entire/.gitignore` via plain `os.ReadFile`/`os.WriteFile` (`common.go:1423-1474`, follows a repo-committed symlink), and runtime files (`.entire/{metadata,logs,tmp}`) are written under the literal worktree `.entire/` — a directory the hostile repo controls, including any symlinks it committed there. (The checkpoint walkers do skip symlinked entries, so this is a write-through, not a read-through — see "not exploitable" below.)
3. Egress: under `trust_all` (offered as a first-class option in the pre-push prompt and warned about as "captured AND synced"), `DecideEgress` returns Allowed for this repo, so transcripts from an *excluded* repo are pushed to that repo's sync remote on the user's next `git push`.

**Exploit scenario.** User has `global.enabled=true`, `exclude_paths: ["~/clients/**"]`, `trust_all: true`. They clone a third-party repo into `~/clients/acme/` that carries a committed `.entire/settings.json` (this is the normal way teams share Entire settings, so it is not suspicious). They open Claude Code there. TurnStart → `prepareHookPolicy` → `ActivationLocal` (exclusion never consulted) → `ensureSetup` installs `.git/hooks/pre-push` etc. and creates `.entire/.gitignore`, `.entire/metadata/…`, `.entire/logs/…` in the clone. On the next `git push`, `CheckpointEgressAllowed` is true (trust_all) and the session transcript leaves the machine to acme's remote, contrary to the user's exclusion.

**Fix.** Treat repo-shipped settings as *configuration*, not *consent*: (a) apply the user's exclude lists to `ActivationLocal` as well (an exclusion is the user's explicit "never here" and should outrank repo content), or at minimum apply them whenever the global tier is enabled; (b) record repo-level enablement in a machine-local place the repo cannot ship (e.g. the clone-preferences file in the git common dir, written by `entire enable`) and require that, not merely the presence of `.entire/settings.json`, before taking the `ensureSetup`/worktree-layout route from a hook; repos that only have committed settings would then go through the invisible global route (git-common-dir runtime root, hooks-dir residency check, trust prompt). (c) Have `status`/the SessionStart banner say when a repo is active *because of committed settings* rather than a local enable.

## Finding 2 — Local-layer ownership probe is defeated by a submodule mounted at `.entire`, letting a clone deliver `.entire/settings.local.json` that is honored as the developer's own — including the exec-bearing OPF `command`

- **Where:** `cmd/entire/cli/settings/opf_command_trust.go:284-353` (`probeLocalSettingsIsVersioned`: symlink check at 289-305, index scan 322-330, HEAD scan 337-352), `:401-431` (`treeHasPathFold` — `continue` on `object.ErrDirectoryNotFound`), `settings.go:637-660` (`loadMergedSettings` merges the local layer unless `localTracked`; `enforceOPFCommandTrust` requires `localOwn`), `repopolicy/activation.go:32-39,55` (`LocalSettingsTrusted` uses the same probe), `settings.go:1628-1636` (`CheckpointRemoteIsLocalOnly` → bypasses `checkpointRemoteIsInherited` in `checkpoint/remote/util.go:412`), `redact/opf.go:421-426` (`exec.CommandContext(callCtx, s.command, …)`), `strategy/manual_commit_push.go:251-286` (pre-push OPF run).
- **Severity:** High
- **Category:** exec of repo-controlled command; consent-gate bypass
- **Confidence:** 0.8

**Description.** The gate that decides whether `.entire/settings.local.json` is "this developer's own" is: not a symlink at `.entire` or the file (new on this branch), not present in the superproject index, and (deep) not present in HEAD. A repository that declares a **submodule at path `.entire`** defeats all three: after `git clone --recurse-submodules` (or `git submodule update --init`, which most READMEs instruct), `&lt;root&gt;/.entire` is a real directory containing whatever the attacker's submodule holds; the superproject index/HEAD contain only a gitlink entry `.entire` (mode `0160000`), so `pathsEqualFold(".entire", ".entire/settings.local.json")` is false, and in the HEAD walk `tree.Tree(".entire")` hits go-git's `GetTree` → `ErrObjectNotFound`, which go-git v6 maps to `ErrDirectoryNotFound` (`plumbing/object/tree.go:119-131`), so `treeHasPathFold` `continue`s and returns `(false, nil)`. Both shallow and deep probes therefore report `localOwn`. Effects:

1. `loadMergedSettings` merges the attacker's local layer (so `redaction.openai_privacy_filter.{enabled,prompt_default,categories,command}` all take effect) and `enforceOPFCommandTrust` keeps `command` because `localSetsOPFCommand` is true and the deep probe says `localOwn`.
2. `ReadRepoActivation` honors the local `enabled` key; `CheckpointRemoteIsLocalOnly` returns true, so a `checkpoint_remote` in that file skips the owner-mismatch ("inherited") check.
3. At pre-push, after the egress gate passes, `redact.OPFEnabled()` → `resolveOPFDecisionForPrePush` (`prompt_default: "always"` skips the prompt; non-TTY auto-runs) → `RewriteUnpushedV1WithOPF` → `exec.CommandContext(ctx, command, "--device", …)` with the hook's cwd at the worktree root. A `command` such as `./.entire/opf` (a script shipped in the same submodule) executes on the developer's machine.

The probe's index/HEAD logic itself predates this branch, but on main the chain was unreachable without the user running `entire enable` in the hostile repo. This branch makes the repo active from a bare clone (Finding 1), installs the pre-push hook from the agent hook, and added a symlink guard specifically for "a clone can ship the file without the literal path appearing in the index" — the gitlink shape is the same class and is not covered.

**Exploit scenario.** Attacker publishes a repo with `.gitmodules` mapping path `.entire` to a second attacker repo containing `settings.json` (`{}`), `settings.local.json` (`{"redaction":{"openai_privacy_filter":{"enabled":true,"prompt_default":"always","command":"./.entire/opf"}}}`), and an executable `opf`. Victim (global tracking on) runs `git clone --recurse-submodules …`, opens Claude Code in it (capture starts; `ensureSetup` installs `.git/hooks/pre-push`), and later pushes anything. If `trust_all` is set the egress gate passes immediately; otherwise the victim sees the one-time prompt "Yes — sync this repo's checkpoints to origin (…)" — a natural "yes" for someone pushing their own branch. `pendingCheckpoints &gt; 0` (the session was captured), OPF is enabled by the local layer, no prompt (`always`), and `./.entire/opf` runs as the victim with the victim's environment. Without `trust_all` the same path also needs a TTY-less push (GUI client) or the OPF prompt default; both are attacker-set.

**Fix.** In `probeLocalSettingsIsVersioned`, treat a gitlink at any component of `.entire/settings.local.json` as *versioned/hostile*: while scanning the index, also match entries whose `Name` equals a proper prefix of the target path (`.entire`) — any such entry (file or `filemode.Submodule`) means the path is repository content; in `treeHasPathFold`, if a fold-matching entry has `Mode == filemode.Submodule` (or `Tree()` fails for a non-blob entry), return `true` rather than `continue`. Independently, `enforceOPFCommandTrust` should refuse `command` values that resolve inside the worktree (relative paths, or absolute paths under the worktree root), since an executable delivered by the repository is exactly what the gate exists to block — that closes the exec even if some future delivery shape slips past the ownership probe. Consider also making the OPF `enabled`/`prompt_default` keys committed-or-local-verified in the same way `command` is, since they are what make the exec run unattended.

## Examined and judged not exploitable (with guarding code)

1. **Symlink-following writes into user config** (`jsonutil.WriteFileAtomicFollowingSymlinks`, `resolveWriteTarget`, `write.go:86-159`). Only reached with user-owned paths: `~/.config/entire/settings.json` (`user_settings.go:114`), `~/.claude/settings.json` and `~/.gemini/settings.json` (`claudecode/hooks.go:335,486`, gemini equivalent). No repo-derived path reaches it — repo-side `.entire/settings.local.json` writes use the non-following `WriteFileAtomic` (`settings.go:776`), which replaces rather than follows a link. Hop cap (40) and `seen` map prevent cycles; the final-component walk only follows links the user placed. TOCTOU would require local write access to `$HOME`, out of scope.

2. **Global-route runtime path routing** (`paths/invisible.go:55-80`, `repopolicy/repository.go:64-75`). For `ActivationGlobal` the runtime root is `&lt;git-common-dir&gt;/entire/worktree/&lt;sha256(worktreeID)[:16]&gt;`; `commonDir` comes from `git rev-parse` and is symlink-canonicalized; `runtimeRootForPath` fails closed with `ErrUnroutableRuntimePath` on any policy error or a `WorktreeRoot` mismatch, and every consumer (`lifecycle.go`, `state.go`, opencode/pi lifecycle) skips rather than falling back to a worktree path. Lazy hook install checks `HooksDirIsWorktreeResident` (`global_setup.go:122-157`, symlink-resolved on all sides) so a committed `core.hooksPath` target never receives hook files on that route. The checkpoint walkers (`ephemeral.go:964-980`, `persistent.go:2440-2455`) `Lstat` every entry and skip symlinks, so a hostile `.entire/metadata` symlink cannot pull foreign files into a checkpoint.

3. **Trust-key / exclusion normalization** (`gitremote.ParseURL`, `splitOwnerRepo`, `repopolicy.NormalizeOrigin`, `CanonicalTrustOrigin`). Checked port dropping (`ssh://host:2222/o/r` → `host/o/r`), SCP userinfo (`x@host:o/r`), `.git`/trailing-slash shedding, case folding, control-char rejection, and `..` segments: each either collapses to a key for the *same* repository (GitHub/GitLab ignore case and port), or produces a key that matches no trusted entry (fail-closed), and `exclude_origins` with `**` still over-matches a crafted `..` path (fail-safe). Remote URLs are user-typed (`.git/config` is not cloned), and submodule URLs only affect the submodule's own identity. `getAllRemoteConfig` uses a fixed `git config --get-all remote.&lt;name&gt;.url` argv with no shell.

4. **Committed `checkpoint_remote` redirecting egress.** `checkpointRemoteIsInherited` (`remote/util.go:~400`) ignores a committed checkpoint repo whose owner differs from origin *and every push URL*, and the derived URL keeps the push remote's host, so exfil requires the victim to have push rights to an attacker-owned repo — only bypassed via the local-layer route in Finding 2.

5. **cmd.exe rule / `escapeWindowsCMD`.** The `hook_command.go` change only adds two legacy-prefix detection strings; no new `exec.Command("cmd", …)` with dynamic values was introduced.</result>

## Evidence

**Leg 1 — repo-shipped project file activates an excluded repo (holds)**

- `cmd/entire/cli/settings/repopolicy/policy.go:36-54`: `ReadRepoActivation` is consulted first; `case activation.Configured &amp;&amp; activation.Enabled:` sets `Active=true, ActivationSource=ActivationLocal` and never enters the `default:` branch. `ClassifyGlobalConfig` — the **only** place exclusions are evaluated (`repository.go:124-163`: `MatchesExcludePath`, `MatchesExcludePathExact`, `ExcludeOrigins`) — is skipped entirely.
- `activation.go:53-57`: the `LocalSettingsTrusted` (tracked/symlink) probe is applied only when `!isProject`; the project `settings.json` is read unconditionally. `activation.go:75-76`: a project file with no `enabled` key defaults to enabled.
- `types.go:136-140` documents the contract being violated: "An unusable pattern … deactivates global mode entirely — fail closed — rather than silently tracking a repo the user meant to exclude."
- `docs/architecture/global-tracking.md:57-63` calls this intended ("Committed `.entire/settings.json` activates a fresh clone exactly as it does today") while in the next sentence rejecting a shipped *local* file precisely because "a clone must not be able to … bypass the user's exclusions." The two files carry identical activation power, so the distinction is not principled.
- Test coverage confirms the gap: `hook_policy_test.go:106-142` tests a committed `settings.local.json` vs exclusion; the table at `hook_policy_test.go:33-43` has an "excluded repo" case only with **no** repo settings. There is no case for "committed project settings.json + excluded repo."

**Leg 2 — setup writes + git-hook install from a hook in a never-enabled clone (holds)**

- `hook_registry.go:109-131`: hook proceeds whenever `policy.Active`.
- `lifecycle.go:606` → `strategy.EnsureSetupForHook`. `global_setup.go:196-212`: `RepoActivationConfigured` is true for the committed project file → `return ensureSetup(ctx, io.Discard)`. `common.go:101-127`: `EnsureEntireGitignore` (worktree write), `vercelconfig.InitSettings`, `EnsurePrimaryRefTo`, `installGitHooks`. The `HooksDirIsWorktreeResident` guard exists only in `MaybeEnsureGlobalSetup` (`global_setup.go:53-79`), which returns early at line 49 because `ActivationSource != ActivationGlobal`.
- `types.go:106-111`: `RuntimeRoot()` for `ActivationLocal` is `&lt;worktree&gt;/.entire`, so metadata/logs/tmp land in the clone.
- "As it does today" is inaccurate. On `main`, `lifecycle.go:575` also called `EnsureSetup` from the hook, but hooks were only ever installed into `&lt;repo&gt;/.claude/settings.json` (main `agent/claudecode/hooks.go:60-70`) — i.e., the clone had to ship Claude hook config *and* the user had to accept Claude Code's project-hook trust dialog. This branch adds `InstallUserHooks` → `~/.claude/settings.json` (`agent/claudecode/hooks_user.go:20-43`), installed by `globalPostRun` whenever `global.enabled` (`global_warn.go:125`). User-scope hooks are not gated by Claude Code's project trust, so the precondition drops from "user trusted this project's hooks" to "user opened an agent in the folder they excluded."

**Leg 3 — egress under `trust_all` (holds; conditional)**

- `trust.go:65-68`: `if global.TrustAll { return TrustDecision{Allowed: true, ...} }` — evaluated on any `Active` policy, no exclusion check. `manual_commit_push.go:63-66`: `gateCheckpointEgress` passes when `CheckpointEgressAllowed`.
- Without `trust_all`: TTY push prompts (`trust_prompt.go:83-115`), non-TTY holds (`trust_prompt.go:35-37`). So exfiltration requires `trust_all` or a "Yes" answer.

## Mitigations found (and why they don't close it)

- SessionStart banner "Entire is capturing this repo locally…" (`lifecycle.go:294-306`) fires only when egress is **held** (`CheckpointEgressHeld`), so a `trust_all` user gets no indication at all.
- `entire trust` refuses excluded repos (`trust_cmd.go:107-135`), but it checks `IsActiveForRepoWithReason`, which reports Local/active here — the refusal is unreachable in this scenario.
- `entire status` renders `globalInactiveHereText` only for inactive repos (`status.go:336-350`); the excluded-but-captured repo shows as a normally enabled repo.
- Tracked `settings.local.json` is rejected (`activation.go:55`) — right threat model, applied to the wrong file only.
- `trust_all` is an explicit opt-in labelled "trust every repo on this machine" — a partial mitigation, but `types.go:170-171` says "enrollment stays with Enabled and the exclude lists," so users reasonably read "every repo" as "every repo the tier tracks."

## Recommended minimal fix

In `ClassifyRepoPolicyAt` (`policy.go`), when `userSettings.GlobalEnabled()` and activation comes from the **project** file (not an untracked, user-authored `settings.local.json` with `enabled: true`, which is the user's own action and should keep overriding), evaluate the exclusion lists before granting `ActivationLocal`; on a match return inactive with `InactiveReasonGlobalExcluded`. This keeps the `enabled:false` veto and `entire enable --local` semantics intact and makes exclusion symmetric with the existing veto. Additionally: have `EnsureSetupForHook` apply the same `HooksDirIsWorktreeResident` guard (or route through `MaybeEnsureGlobalSetup`) when the tier is on, and add a `TestPrepareHookPolicy_CommittedProjectFileCannotBypassExclusions` case mirroring the existing local-file test. Update `global-tracking.md:57-63` accordingly.</result>
