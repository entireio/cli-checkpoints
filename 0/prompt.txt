### 2. `checkpoint_remote` vs `strategy_options.checkpoint_push_remote` — the mismatch

Both live under `strategy_options`. Definitions in `/home/toby/projects/cli/cmd/entire/cli/settings/settings.go`:

**`strategy_options.checkpoint_remote`** — `CheckpointRemoteConfig` (line 1827), accessor `GetCheckpointRemote` (line 1886). It is a **structured object**, not a remote name:

```go
val, ok := s.StrategyOptions["checkpoint_remote"]
...
m, ok := val.(map[string]any)
provider, providerOK := m["provider"].(string)
repo, repoOK := m["repo"].(string)
if !providerOK || !repoOK || provider == "" || repo == "" { return nil }
if !strings.Contains(repo, "/") { return nil }
```

It selects a **dedicated separate repository** whose URL is derived from the push remote's protocol (`checkpoint/remote/util.go:194 PushURL`, consumed by `strategy/checkpoint_remote.go:89-106 resolvePushSettings`). It never names a git remote. Related: `HasCheckpointRemoteKey` (1847), `CheckpointRemoteIsLocalOnly` (1872).

**`strategy_options.checkpoint_push_remote`** — `GetCheckpointPushRemote` (line 1914), a plain string:

```go
// GetCheckpointPushRemote returns the configured checkpoint push remote name.
// Stored in strategy_options.checkpoint_push_remote as a plain git remote
// name (e.g. "origin", "private"). This selects WHICH configured remote
// carries checkpoint data — distinct from checkpoint_remote, which derives a
// dedicated URL. Returns "" if unset, empty, or not a string.
```

This is the **only** setting the election consults (`strategy/checkpoint_sync_remote.go:83`).

**Why the warning's advice does not work.** The message at `remote_topology.go:177-178` names `checkpoint_remote` for a problem whose fix is `checkpoint_push_remote`. Four concrete failure modes:

1. **Wrong key for the stated goal.** `ResolveCheckpointSyncRemote` reads only `GetCheckpointPushRemote()`; the resolver's doc comment says so explicitly (`checkpoint_sync_remote.go:44-46`): *"It knows nothing about the checkpoint_remote URL feature; callers exempt that case themselves."* Setting `checkpoint_remote` changes nothing about which of several remotes is elected.
2. **Nesting omitted.** The message says "set checkpoint_remote in .entire/settings.json"; the real path is `strategy_options.checkpoint_remote`. A top-level `checkpoint_remote` key is read by nothing.
3. **Wrong value shape.** A user who follows the advice literally with a remote name (`"checkpoint_remote": "upstream"`) hits `GetCheckpointRemote`'s `val.(map[string]any)` type assertion → `nil`, silently ignored. (`HasCheckpointRemoteKey` would report intent, but nothing in the election path consults it.)
4. **Even a well-formed value can be vetoed.** A correct `{"provider","repo"}` object only takes effect if `checkpointremote.PushURL` returns `enabled == true`; the ownership/inheritance check (`checkpoint/remote/util.go:212-240`, `settings.CheckpointRemoteIsLocalOnly`) rejects it when it looks inherited from an upstream. Committing it to `.entire/settings.json` — precisely what the message recommends first — is the inheritance-prone location. When vetoed, `ps.hasCheckpointURL()` is false and the ordinary single-remote gate applies again, so the user's chosen repo is not used.

Contrast: `hintGatedCheckpointSync` (§1) gives the correct advice — `strategy_options.checkpoint_push_remote` in `.entire/settings.local.json` — with an explicit rationale at `checkpoint_sync_remote.go:155-157` for preferring the local file (a remote name is a per-clone fact; committing it fail-closes teammates). The topology note recommends the *tracked* file first, contradicting that.

README documents the correct behaviour (`README.md:516-517`, `540-552`), so the drift is in the two `checkpoint_remote` advice strings only.

### 3. The election algorithm

Tiers, in order:

0. `settings.Load(ctx)` failure → **fail-closed** error: `"cannot read settings to resolve the checkpoint sync remote: %w"`.
1. **config** — `s.GetCheckpointPushRemote() != ""`. **Fail-closed** if the name is not a configured remote: `"checkpoint_push_remote %q is not a configured git remote; checkpoint sync disabled until fixed"`.
2. **observed** (captured) — `loadCapturedSyncRemotes(ctx)`, first entry that `isConfiguredRemote`. **Fail-soft**: a renamed/removed captured remote logs `"captured checkpoint sync remote is not configured; falling through"` and falls through.
3. `len(remotes) == 0` → `CheckpointSyncRemote{}` (empty name, no error).
4. **default** — `origin` is present.
5. **sole** — exactly one remote.
6. **first** — `remotes[0]` in `.git/config` order.

Remote enumeration: `configuredRemotesInConfigOrder` → cached `readRemotesInConfigOrder` (line 216) runs `git config --local --get-regexp '^remote\..*\.url$'`; exit code 1 is the cacheable "no remotes" answer, any other error is an error (so a fork failure is not memoized as empty). ### 6. `doctor_migrate.go` — the existing migration and its UX

`/home/toby/projects/cli/cmd/entire/cli/doctor_migrate.go` — `entire doctor migrate-checkpoints` (`newDoctorMigrateCheckpointsCmd`, line 18). It converts **git-branch checkpoints → per-checkpoint git refs**: commits on `entire/checkpoints/v1` become refs under `refs/entire/checkpoints/&lt;shard&gt;/&lt;id&gt;`. Each checkpoint's current tree is wrapped in a fresh commit (branch commits are not remapped); metadata is normalized (legacy `checkpoint_version` dropped, session paths rewritten relative to the ref). Idempotent — already-converted checkpoints are skipped.

Flags: `--dry-run`, `--remote` (`"Remote to push migrated refs to (default: the checkpoint sync remote)"`).

UX flow (`RunE`, lines 39-96):

1. **Refuse if already migrated**: `checkpoint.PrimaryIsRefs(cpCfg)` → `"The git-refs store is already the primary checkpoint store — nothing to migrate."`, return nil.
2. `strategy.OpenRepository`, then `checkpoint.MigrateBranchToRefs(ctx, repo, dryRun)`. `context.Canceled` → `NewSilentError`.
3. **Nothing to do**: `result.Total == 0` → `"No checkpoints found on the v1 branch — nothing to migrate."`
4. **Summary**: `fmt.Fprintf(out, "%s %d checkpoint(s) to refs (%d already up to date, %d total).\n", verb, len(result.Migrated), result.Skipped, result.Total)` with `verb` = `"Migrated"` or `"Would migrate"` under `--dry-run`. Returns here on dry-run or nothing migrated.
5. **Non-interactive**: `!interactive.CanPromptInteractively()` → `"Refs are queued; they push on the next \`git push\` once git-refs is the primary store."` and return — it never pushes unattended.
6. **Interactive prompt**: `resolveMigratePushRemote(ctx, remote)` (line 155) — explicit `--remote` wins, else `strategy.ResolveCheckpointSyncRemote`; **fail-closed** (`"cannot determine checkpoint sync remote (pass --remote explicitly): %w"`, and `"no git remotes configured; pass --remote explicitly"`). 7. **Push**: `pushMigratedRefs` (line 112) — calls `strategy.EnsureRedactionConfigured` first (an unconfigured scanner reads as "OPF off"), then `strategy.PushQueuedCheckpointRefs`. Outcomes: `ErrOPFAbortedByUser` → `"OPF cancelled; refs stay queued for the next push."`; `pushDisabled` → `"Checkpoint pushing is disabled in settings; refs stay queued for the next push."`; `pushed == 0` → `"No queued refs to push (they may have already been pushed)."`; else `fmt.Fprintf(out, "Pushed %d checkpoint ref(s).\n", pushed)`.

### 1a. `cmd/entire/cli/gitremote/gitremote.go` (298 lines) — parsing

## 7. `docs/architecture/ref-checkpoint-backend.md` — summary

(230 lines; companion to `docs/architecture/sessions-and-checkpoints.md`.)

1. **Why**: git-branch stores every checkpoint as a subtree of one long-lived branch `entire/checkpoints/v1` — a serialization point (every condensation rewrites the tip, every push races one ref).
2. **Ref layout**: `refs/entire/checkpoints/&lt;shard&gt;/&lt;id&gt;`; each ref's commit tree root *is* that checkpoint's contents (`metadata.json`, `0/`, `1/`, `tasks/…`) — the same subtree git-branch splices under `&lt;id[:2]&gt;/&lt;id[2:]&gt;/`.
3. `&lt;shard&gt;` = `id.ShardFor()` = the **last two** characters, for both ID formats. One positional rule; suffix distributes evenly for hex (random throughout) and ULID (leading chars are a millisecond timestamp, trailing are random — so suffix sharding keeps buckets even *and* the ID time-sortable).
4. `ParseRef` validates shard-matches-ID and rejects extra path segments; `RefName` errors rather than emitting `refs/entire/checkpoints//`. The git-branch tree layout uses **first**-two-chars and the two schemes deliberately do not interact.
5. **ID formats**: git-branch primary → 12-char hex; git-refs primary → 26-char ULID. Minted only by `checkpoint.GenerateCheckpointID`.
6. **Taxonomy**: one **primary** (source of truth — all reads and writes, full lifecycle, pre-push OPF) plus zero or more **mirrors** (best-effort write fan-out only; reads never come from a mirror).
7. Registration in `checkpoint/registry.go` with a `gitBacked` capability: only `gitBacked: true` backends can be primary. `git-branch` and `git-refs` are both git-backed and registered directly; `Register()` is for mirror-only backends (test-only in practice).
8. A one-of-each-type rule permits two git-backed backends together, but the branch→refs migration deliberately does **not** run git-branch as a mirror of git-refs.
9. **Write path**: resolve tip (`refBase` for creates — missing ref ⇒ orphan commit; `refBaseForBackfill` for backfills — on-demand fetches a locally-missing ref first, and a still-absent ref is `ErrCheckpointNotFound`, never orphaned) → build subtree → commit parented on the tip → `setRef` + enqueue. Enqueue is best-effort.
10. **Push**: no single tip to push and reads can fetch on demand, so the backend tracks changes in a push-discovery queue and pushes those.
11. **Non-force, fast-forward-only, always** — no server-side ref protection, so a force push risks silently clobbering a checkpoint written elsewhere. Divergence is recovered by fetch + replay-on-top, after which the retry is still non-force and the remote commit survives as an ancestor. A genuine cherry-pick conflict leaves the ref queued.
12. **On-demand fetch**: `resolveRefMaybeFetch` distinguishes genuinely absent (→ `ErrCheckpointNotFound`) from a real failure (returned as-is, never swallowed).
13. **Read routing** (`kindRoutingStore`, `checkpoint/routing_store.go`), by ID kind: **ULID → git-refs only, never the branch** (ULIDs are only minted under git-refs); **hex under git-branch primary → branch only**; **hex under git-refs primary → refs first, then branch fallback** (a hex checkpoint may sit on the pre-migration v1 branch, or have been migrated into refs under a hex-named ref).
14. `List` unions both backends de-duped by ID (most recent kept). `firstResolved` falls through on absent *or* error for non-final stores. Creates are **not** kind-routed (they target the primary); backfills **are** (falling through only on `ErrCheckpointNotFound` — stricter than reads). All read paths inherit this via `checkpoint.Open`; no per-command knob.
15. **Migration/coexistence**: read routing is what makes the flip work — every reader (CLI, entire.io, entire-api) reads refs first with a branch fallback, so the switch is a primary flip with **no dual-write step**. An old CLI keeps writing hex to v1 and cannot read ULID refs, which is intended (fails closed, with `checkpoint_min_version` turning it into an upgrade nudge).

### D2. Hydrate
```go
type HydrateResult struct {
    RefsFetched  int   // refs fetched from the old remote
    RefsAdvanced int   // local refs set or fast-forwarded
    RefsReplayed int   // diverged local refs replayed onto the old tip (logged at Info by SafelyAdvanceLocalRef)
    V1Advanced   bool

func HydrateCheckpointArtifacts(ctx context.Context, repo *git.Repository, from string, inv CheckpointInventory, progress ProgressFunc) (HydrateResult, error)
```
- Candidates: every `inv.Refs` entry whose local ref is absent **or** whose local hash differs from the remote hash (a ref written on another machine may be ahead on the old remote; deleting it after publishing only the local tip would lose it).
- Fetch in chunks of `refChunkSize` with refspecs `+refs/entire/checkpoints/&lt;s&gt;/&lt;id&gt;:refs/entire-sync-tmp/checkpoints/&lt;s&gt;/&lt;id&gt;` via `remote.Fetch(ctx, remote.FetchOptions{Remote: from, RefSpecs, NoTags: true, NoFilter: true, Dir: worktreeRoot})`. `NoFilter: true` is mandatory — see the doc at `checkpoint_remote.go:169-181`: filtered fetches leave refs whose blobs are missing, and the ref's existence then suppresses recovery forever.
- Promote each tmp ref with `SafelyAdvanceLocalRef(ctx, repo, localRef, tmpHash)` (`common.go:162`), then `repo.Storer.RemoveReference(tmp)`. Do not use `PromoteTmpRefSafely` (`:138`): it re-opens the repo from cwd; the engine takes an explicit `repo`.
- v1: if `!inv.V1Branch.IsZero()`, fetch `+refs/heads/entire/checkpoints/v1:refs/entire-sync-tmp/heads/entire/checkpoints/v1` (same options) and `SafelyAdvanceLocalRef(ctx, repo, checkpoint.ResolveRefs(ctx).Primary, tmpHash)`.
- **Why this does not violate "only the elected remote may advance local refs"** (CLAUDE.md:1433): that rule protects the automatic read paths from a stale legacy tier silently replaying onto local state during a hook or a resume. Here (1) the user issued a foreground command and consented, (2) the source is the remote *being migrated from*, whose data we are about to delete — hydrating it into local refs is the only thing that makes deletion safe, and (3) promotion goes through the same non-destructive `SafelyAdvanceLocalRef` (ahead → untouched, diverged → replay + Info log). The tmp namespace keeps the fetch itself from ever writing a canonical ref directly, matching the `fetchURLIntoTmpRef` + promote shape the codebase already uses (`checkpoint_remote.go:143-160`). Document this in the function comment and reference the CLAUDE.md rule.

### D3. Convert
Engine exposes nothing new: the CLI calls `checkpoint.MigrateBranchToRefs(ctx, repo, false)` after D2 when the local v1 branch exists (`repo.Reference(checkpoint.ResolveRefs(ctx).Primary, true)` succeeds). Idempotency verified (`migrate.go:104,148`; tests `:207`, `:452`). It enqueues every checkpoint — which is exactly the D4 requeue for the converted set. Ordering constraint: hydrate → convert → **backend flip** (`applyCheckpointBackend`, `checkpoint_backend.go:61`, CLI half) → requeue+publish → verify → remove. The flip must precede publish so `CountUnpushedCheckpoints`/status read the queue, and must precede the user's next `git push` so the pre-push takes the refs path (`primaryIsRefs`, `manual_commit_push.go:115`). Note `doctor migrate-checkpoints` refuses when refs is already primary (`doctor_migrate.go:46-49`); `MigrateBranchToRefs` itself does not, so the new command can convert first and flip after.

### D4. Requeue + publish
```go
// RequeueAllCheckpointRefs enqueues every local refs/entire/checkpoints/* ref
// so the next flush publishes the whole backlog, not just the refs the hook
// recorded. Returns the number of refs enqueued.
func RequeueAllCheckpointRefs(ctx context.Context, repo *git.Repository) (int, error)
```
- Iterate `repo.References()`, keep names where `checkpoint.ParseRef(name)` is ok (`refs_naming.go:41`).
- Add `func (q *PushQueue) EnqueueAll(refs []plumbing.ReferenceName) error` to `checkpoint/pushqueue.go`: one lock, one appended buffer. `Enqueue` per ref takes a flock and reopens the file each time — fine for one checkpoint, wasteful for thousands. `Drain` (`:105-132`) already dedups against whatever `MigrateBranchToRefs` enqueued.
- Publish: CLI calls `strategy.EnsureRedactionConfigured(ctx)` (`common.go:442`) then existing `strategy.PushQueuedCheckpointRefs(ctx, repo, newRemote)` (`manual_commit_push.go:464`). This reuses the policy gate (`:469-472`), OPF gate (`:473-480`), fast-forward-only batch + per-ref recovery, and queue removal semantics. The CLI must handle `ErrOPFAbortedByUser` like `pushMigratedRefs` does (`doctor_migrate.go:136-139`).
- **Required fix**: chunk `batchPushRefs` (`push_common.go:58-70`) at `refChunkSize` per `git push`. Today the whole queue goes in one argv; a migrated backlog of a few thousand refs (~110 bytes/refspec) overruns macOS ARG_MAX. Behavior on a rejected chunk is unchanged (return error → per-ref recovery loop at `:572-590`). Add a test (E).
- Progress: `flushCheckpointRefsQueue` writes `[entire] Pushing N checkpoint ref(s) to …` with dots straight to `os.Stderr` (`:535-536`). Add a package var `refsPushProgressWriter io.Writer = os.Stderr` (mirroring `opfPrePushProgressWriter`, `manual_commit_push.go:34`) and route those `Fprintf`s through it, so the CLI can set it to `io.Discard` while its own spinner runs, or leave it. Not more than that — a callback plumbed through `flushCheckpointRefsQueue` would touch the pre-push hot path for no gain.

### D5. Verify
```go
// VerifyCheckpointArtifacts lists newRemote and reports what from the old
// inventory has not landed: a ref is verified only when newRemote has it at
// the LOCAL hash (publish is fast-forward-only, so after a successful flush
// new == local, and local already contains the old tip via hydration).
func VerifyCheckpointArtifacts(ctx context.Context, repo *git.Repository, newRemote string, old CheckpointInventory) (verified []plumbing.ReferenceName, missing []plumbing.ReferenceName, v1Verified bool, err error)
```
Uses D1 against `newRemote`. v1 is "verified" for deletion when either (a) `MigrateBranchToRefs` ran and every checkpoint on the old v1 is among `verified` refs — i.e. `old.V1Branch` is zero or the local v1 branch tip equals/contains it (hydration guarantees this) *and* the conversion result reported `Total == Migrated+Skipped` — or (b) there was no old v1. The CLI passes the `MigrateResult`; keep this as an explicit bool parameter `convertedAll bool` rather than re-deriving it.

### D6. Remove
```go
type RemoveResult struct{ RefsDeleted int; V1Deleted bool; AlreadyAbsent int }
func RemoveCheckpointArtifacts(ctx context.Context, oldRemote string, refs []plumbing.ReferenceName, deleteV1 bool, progress ProgressFunc) (RemoveResult, error)
```
- Shared helper in `checkpoint/remote/git.go`:
  ```go
  // DeleteRefs runs `git push --no-verify --porcelain --delete &lt;target&gt; &lt;refs...&gt;`.
  // A ref that is already absent is reported in absent rather than failing the call.
  func DeleteRefs(ctx context.Context, target, dir string, refs []string) (absent []string, err error)
  ```
  built on `PushWithOptions{Remote: target, ExtraArgs: []string{"--delete"}, RefSpecs: refs, Dir: dir}` (`:428-449`). Git validates `--delete` refspecs before transferring, so one absent ref fails the whole invocation with `remote ref does not exist`; on that error `DeleteRefs` re-runs `ls-remote` for the chunk, drops the absent names, and retries once. Generalize `deleteBranchFromRemote` (`trail_cmd.go:2590`) to call it with one ref (behavior preserved: absent → nil).
- **Target must be the old remote's URL, not its name.** `resolvePushCommandTarget` (`git.go:726-739`) rewrites a remote *name* to the dedicated `checkpoint_remote` `PushURL` when one is configured — a `--delete` aimed at "origin" would then delete from the dedicated checkpoint repo. Resolve with `gitremote.GetPushURLs(ctx, oldRemote)` (`gitremote.go:156`) and refuse (`error`) when it returns more than one URL (a fan-out remote has no single "old" to clean). `IsURL`/`isLocalPath` targets bypass the rewrite (`:727`). Belt and braces: the CLI should also refuse the whole command when `settings.GetCheckpointRemote() != nil` (a dedicated store is authoritative; this feature is about the default election) — **open question D6**.
- Chunk at `refChunkSize`; only refs in `verified` are ever passed in.
- v1: `DeleteRefs(ctx, url, dir, []string{"refs/heads/"+paths.MetadataBranchName})` when `deleteV1`. Then prune the stale local tracking ref `refs/remotes/&lt;old&gt;/entire/checkpoints/v1` (`repo.Storer.RemoveReference`); otherwise `metadataTrackingRefExists` (`git_operations.go:464-471`) and `countUnpushedV1Commits` (`unpushed_checkpoints.go:58`) keep seeing a branch the remote no longer has.
- `EnvWithoutRepoOverrides`: **not required**. The rule (CLAUDE.md:1160-1166) targets subprocesses that can run inside a git hook; this engine runs only from a foreground command in the user's cwd, where an exported `GIT_DIR` is an instruction. Say so in the file header, and note that if any of these functions is ever wired into a hook, `remote.Fetch/PushWithOptions` do not scrub the environment (`newCommand`, `git.go:544-557`).

### D7. Legacy read tier after removal
`CheckpointReadRemotesWithElection` (`checkpoint_read_remotes.go:58-74`) yields `[entire, origin]`. After removal: `ListCheckpointRefsOnRemote` unions per-candidate listings (`git_operations.go:662-697`) — origin contributes nothing, fine. `FetchCheckpointRefFrom` (`checkpoint_ref.go:219-296`) asks the entire remote first (authoritative via `LeadReadRemote` → `fetchURLAuthoritative`, `util.go:113-124`), falls to origin only on positive absence, and returns `ErrReferenceNotFound` on absence everywhere; nothing persists an "absent" verdict across processes. The git-refs store's per-process failure memo is scoped to one process. The checkpoint policy ref `refs/entire/policies/checkpoint` (`checkpointpolicy/store.go:22`) on origin is left alone (harmless, read-only tier; the hook writes the policy to `pushTarget()`, which is now the entire remote). The election cache (`git_remote_cache.go`) memoizes only `.git/config` reads; the CLI half must call `strategy.InvalidateGitRemoteCache(ctx)` if it adds or renames a remote (e.g. `--to` accepting a URL).

### D8. Ordering constraints (engine-level)
1. Inventory(old) → 2. Hydrate(old) → 3. Convert (if local v1) → 4. *CLI flips backend* → 5. RequeueAll → EnsureRedactionConfigured → PushQueuedCheckpointRefs(new) → 6. Verify(new, old inventory) → 7. Remove(old, verified only) → 8. `MarkEntireSyncMigration(done|declined, old)`. If step 5 pushes 0 with `pushDisabled` (`push_sessions: false`), the CLI must stop before 7.

## Risks and open questions

- **D1** pushurl: adopt the safe rule (read `(url|pushurl)`, require all entire://)? Recommended yes.
- **D2** (the recommendation in C): redirect ANY push to the entire remote. Consequence worth stating: a user with `remote.pushDefault=github` never pushes to `entire` yet checkpoints go there on every push, and the SSH/auth for the entire helper runs inside every `git push`. Helper auth failure is fail-soft for refs (`:444-449`) but the v1 path's `doPushRef` is fail-soft too; `BatchMode` SSH does not apply (HTTPS helper). Fine, but the first-push latency is new.
- **D3** skip the empty-remote defer under redirect: relies on Entire never adopting `entire/checkpoints/v1` as the mirror's HEAD. Needs server-side confirmation.
- **D4** captured tier outranks entire: a repo that captured `origin`/`fork` before adding the Entire remote never reaches the tier. Options: (a) leave, and have `entire checkpoint sync --to &lt;entire&gt;` clear the capture file (expose `ClearCapturedSyncRemote(ctx) error` in `checkpoint_sync_capture.go`), or (b) place the entire tier above captured. The product order given says (a); recommend exposing the clear helper so the CLI can make the election land on `entire` without writing `checkpoint_push_remote`.
- **D5** `checkpoint_remote` configured *and* an entire remote: `hasCheckpointURL()` still wins in `prePush` (`:99`), so dedicated mode is unaffected and the entire tier is irrelevant there. Should `entire status` say so? Current `computeCheckpointSyncInfo` probes `PushURL(elected.Name)` with an entire:// elected remote (`util.go:312-324` provider fallback) — same as today for any remote.
- **D6** the delete step must never reach a `checkpoint_remote`: engine resolves the old remote to its URL (bypasses `resolvePushCommandTarget`) and the CLI refuses when `checkpoint_remote` is set.
- **Ref-per-push argv limits**: pre-existing latent bug in `batchPushRefs`; the backlog publish makes it real. Chunking is part of this plan.
- **Hydration cost**: an old remote with thousands of checkpoint refs is fetched with blobs (`NoFilter`); budget is per chunk under `migrateRemoteTimeout`, and the CLI should show progress.
- **Concurrency**: a `git push` pre-push hook running mid-migration flushes the same queue; `flushCheckpointRefsQueue` removes only landed refs, so both drain safely to the same elected remote. The remove step only deletes verified refs, so a concurrent hook cannot cause loss.

- `Use: "sync"`, `Short: "Move checkpoints to a single remote and bring older ones with them"`.
- `Long` (human reference, no agent guidance):

```
Choose the one git remote that carries this repository's checkpoints and bring
the backlog over to it.

When one of your remotes is an Entire remote (entire://…), it is the destination:
Entire keeps checkpoints alongside your code, and pushes to an Entire mirror stay
```

### 2.2 Decision order (pure)

1. `len(in.Remotes) == 0` → `no_remotes`, Reason `This repo has no git remotes, so there is nowhere to sync checkpoints to. Add one with git remote add, then rerun.` exit 0.
2. `in.DedicatedRemote` → `dedicated_remote` (h). Stop.
3. `in.ElectionErr != nil` and `Opts.To == ""` → `fail_closed` (g), exit 1. With `--to` valid → continue with `Destination = Opts.To`, `WriteDestinationSetting = true`.
4. Destination resolution:
   - `Opts.To != ""`: must be a configured remote (else `ExitError: --to %q is not a configured git remote`). `WriteDestinationSetting = Elected.Name != Opts.To || ElectionErr != nil`. Source `"flag"` (or the election source if it already matches).
   - else `len(EntireRemotes) &gt;= 2` and elected source is not config/observed → `choose_destination` (f). Interactive: picker; non-interactive: `ExitError: several Entire remotes (%s); pass --to &lt;remote&gt;`.
   - else `Elected.Source == SyncRemoteSourceEntire` → Destination = Elected.Name, source `entire`.
   - else `len(EntireRemotes) == 0` and `len(Remotes) &gt; 1` and source is default/sole/first → `choose_destination` (b). Interactive: picker with current election first; non-interactive: Reason + `entire checkpoint sync --to &lt;remote&gt;` and settings advice, exit 0 (it is advisory, nothing is broken; mirrors doctor REVIEW).
   - else Destination = Elected.Name (single remote, or config/observed).
5. `--from` validation: every name must be configured and `!= Destination`; else `ExitError`.
6. Sources: `Opts.From` if given, else every non-destination remote whose `Inventory.holdsArtifacts()`; inventory errors go to `UnknownSources`. Decision for several holders: **migrate from all** (hydrate is a union; there is no "wrong" data to bring, and leaving artifacts on any remote defeats the durability goal). Removal stays per-remote with its own confirmation and URL. `--from` narrows when the user wants otherwise.
7. Steps:
   - `!PrimaryIsRefs` → `convert_backend` (i). Skip writing when `BackendEnvOverride`.
   - each Source → `hydrate`.
   - `PrimaryIsRefs &amp;&amp; QueuedRefs == 0 &amp;&amp; LocalCheckpoints &gt; 0` → `requeue` (already-pushed refs are no longer queued; migration re-enqueues on its own, `migrate.go:117-123,167`).
   - `publish`, `verify` always when `LocalCheckpoints &gt; 0 || len(Sources) &gt; 0`.
   - `remove` when `len(Sources) &gt; 0` (consent gathered at run time; the planner only says it is on the table).
   - `record_marker` always at the end.
8. State assignment: `WriteDestinationSetting`-only with zero checkpoints and no sources → `set_destination` (e); no sources and `LocalCheckpoints &gt; 0` and (`QueuedRefs &gt; 0` or destination inventory lacks refs) → `publish_only` (d); no sources, refs all present on destination (destination inventory ⊇ local refs) → `already_home` (a/n); otherwise `migrate` (c/i).
9. `PushSessionsDisabled` (l) does not change the state; it adds `Reason` suffix and the executor knows `Push` will report `pushDisabled`.

### 2.4 Old-remote auto-detection rule

Preference for messaging (which remote is "the old one" in prose and in the status nudge): `legacyElectedRemote(in)` = `origin` if configured and not entire, else the sole non-entire remote, else the first non-entire remote in config order — the election without the entire tier. For *action*, every non-destination remote whose inventory holds artifacts is a source (Section 2.2 step 6). Non-interactive `--remove` applies to all sources; `--from` narrows. Justification: hydrating from all is monotone (more data, never less); removal is the only irreversible act and it stays per-remote with its own consent line naming the URL.

## 9. Risks and open questions

1. **Marker API shape** — I assumed `strategy.LoadCheckpointSyncMigration/SaveCheckpointSyncMigration` with `State` and `Announced`. Confirm names, the file name in the git common dir (for the status test to write it), and whether `Announced` is set by status or by the command (proposal: status sets `Announced` the first time it prints the nudge so `enable` can suppress its pointer once status has nagged — or drop `Announced` entirely; simplest is to keep nagging until `done|declined`).
2. **Raw vs effective URLs** — `EntireRemotes` must classify from raw config (`git config --local --get remote.&lt;n&gt;.url`), not `git remote get-url`/`-v`, or the insteadOf test technique cannot work and real users with insteadOf rewrites get misclassified. The CLI gatherer will also classify from raw config for consistency; display URLs may legitimately differ.
3. **`Verify` semantics** — `VerifyCheckpointArtifactsOn` takes `expected` refs; I will pass the union of local refs after publish (not only hydrated ones) so (d) is verified too. Confirm it is a single `ls-remote` (bounded cost) and honors `GIT_TERMINAL_PROMPT=0` so a non-interactive run cannot hang on credentials.
4. **Double progress output** — `PushQueuedCheckpointRefs` writes `[entire] Pushing …` plus dots to `os.Stderr` (`manual_commit_push.go:535-536`), which will interleave with my spinner. Options: run the spinner on stdout and accept the stderr line; or ask the sibling for a quiet variant/`io.Writer` parameter. Recommend the latter; fallback is no spinner around publish.
5. **OPF prompt inside push** — `strategy.ErrOPFAbortedByUser` (handled in `doctor_migrate.go:136`) must map to "nothing shipped, refs still queued" and exit 0, same as declining.
6. **Hook `checkpointSyncAllowedForRemote`** — with the entire tier, a `git push origin` no longer carries checkpoints and `hintGatedCheckpointSync` (`:159`) will print the settings.local.json hint on every push to origin whose declared destination is origin. Sibling should suppress the hint when the elected source is `entire` (analogous to the `config` suppression at `:164`), otherwise the CLI's positive story contradicts the hook.
7. **git-branch conversion when only origin holds the v1 branch** — `MigrateBranchToRefs` reads the v1 tree via `getSessionsBranchTree`, which falls back to origin's tracking ref (`migrate.go:63-66` comment: "No v1 branch locally or on origin"). If the old remote is not `origin`, `hydrate` must run before `convert_backend` for that source; planner order must therefore be `hydrate(v1)` → `convert` → `hydrate(refs)` → … Simplest: run `hydrate` for all sources first, then convert. I will order steps that way and document it.
8. **Requeue cost** — `RequeueAllCheckpointRefs` on a repo with thousands of refs makes the next push large; acceptable for an explicit command, but the header should show the count so the user is not surprised (`Local 4,213 checkpoints, 4,213 to push`).
9. **Exit code for (b) non-interactive** — chosen 0 (advisory). If the parent prefers a hard signal for agents, flip to 1; it is one field in the planner table.
10. **`settingsTargetFile` in a local-only repo** — `updateCheckpointBackend` writes to `settings.local.json` when no project file exists; the "Commit .entire/settings.json" line must then be omitted (check `configDisplay`).
