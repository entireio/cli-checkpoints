## Important (80-89)

**1. The non-interactive `--body` etag fetch protects nothing, and buys a new failure mode. (85)**
[cmd/entire/cli/trail_cmd.go:1468](vscode://file/Users/alex/workspace/cli/.worktrees/alex-ent-1741-trail-body-write/cmd/entire/cli/trail_cmd.go:1468)–1478

Optimistic concurrency is only meaningful when the etag describes *the document the writer read and based their edit on*. In the interactive path it does — `resolveTrailUpdateBody` seeds the form from that read, so If-Match genuinely means "nobody changed the text I was shown." In the `--body` path the caller supplied replacement text without reading anything, and the CLI then fetches an etag microseconds before the PUT purely to have one to send. That window catches nothing a human or web editor could realistically hit, while the costs are real:

- an extra HTTP round trip on every `entire trail update --body`, the agent-driven hot path;
- a new 412 that tells the caller to "re-run to see the current text" — but they never asked to see it; they named the replacement. Against a yjs-backed document with a live web editor open, the etag can move often enough that agents start needing `--overwrite` routinely, which is the old clobbering behaviour plus a wasted request and a confusing error.

The honest options are to keep `Overwrite: true` for `--body` (the flag's existing meaning: "the caller named the text"), or to give the caller a way to supply an etag they actually read — e.g. surface it in `trail show --json` and accept `--if-match &lt;etag&gt;`. Fetching it on the caller's behalf is the one option that looks like a guard without being one.

**2. That same block turns a warned-about blind edit into a silently "protected" write. (82)**
[cmd/entire/cli/trail_cmd.go:1468](vscode://file/Users/alex/workspace/cli/.worktrees/alex-ent-1741-trail-body-write/cmd/entire/cli/trail_cmd.go:1468)

Outcome is no worse than before the PR (which always overwrote), but the mechanism now reports success as though the concurrency check held. ## Suggestions
