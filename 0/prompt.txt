i own it, so we can just scope a fix for subagents, or what do you then think about the 2013 case? here is exactly wht happened Why it exists

It was born from an incident in this very session. While we were working on the checkpoint-sync fixes, I made commits in sibling worktrees (.worktrees/checkpoint-capture, later .worktrees/session-identity) while my agent session was registered to .worktrees/pr-review. Entire's commit hooks decide which session a commit belongs to by comparing paths — "which session's recorded worktree_path equals the directory this commit is happening in?" — so those commits either got no session linkage at all, or worse: one commit got linked to sessC, a leaked test fixture session sitting in the real .git/entire-sessions/ directory, producing a trailer pointing at a checkpoint that never existed. Each time, the repair was manual surgery: edit the session's JSON to repoint its worktree, replay the commit, restore, force-push. Digging into history showed this wasn't new — the same manual repair had been needed twice before (during the work behind PRs #1647 and #1287).

When you saw it happen — "how funny no session was attached" — the diagnosis went one level deeper than "fix the matcher": path-matching is inference from bookkeeping, and bookkeeping drifts. You pushed on that ("this is how you should normally be operating"), and the conclusion was that a commit's session shouldn't be guessed at all — it's a fact about who ran the commit. Entire's whole premise is that commits carry their session context; an agent's commit failing to link breaks the product's core promise.

What it does

The insight: when an agent commits, the git hook process is a descendant of the agent's process. The answer was in the process tree all along. So:

1. At turn start, the session records its agent process's identity (PID + start-time fingerprint, so a recycled PID can't impersonate).
2. At commit time, the hook walks its own process ancestry — git ← shell ← agent — and asks: is any recorded agent an ancestor of me? If yes, that session made this commit, regardless of worktree. No inference, no drift.
3. The identity match is unioned with the old worktree matching (which still handles human commits and concurrent sessions), and a commit matched outside the session's home worktree is "guest-linked" — transcript captured, trailer stamped, but the session's worktree-coupled state (shadow branches, base commits) left untouched.
4. Alongside it, the root cause of the sessC incident got sealed: the test-fixture leak fixed at the source, imported sessions banned from linking, and the session store made to fail loudly under go test when a test escapes isolation.

How it evolved through review

Three rounds reshaped it, each making it smaller or safer. Cursor bugbot caught that recording multiple ancestor levels captured the user's terminal shell — so a human commit in the same terminal could falsely match; fix: record only the agent. The four-agent toolkit review caught two criticals (guest-linked condensation could corrupt the home worktree's shadow state; a misleading "none was linked" hint) plus resume support and diagnostics. Finally, the trail-1061 review delivered the humbling one: my new internal/proctree package duplicated an existing package (proclive) whose identity fingerprint was already being persisted on every turn start for liveness checking — and my Windows code had never actually run in CI. So the final commit deleted my entire platform package, added one function to proclive (HasAncestor — "was this process spawned by that recorded owner?"), and pointed matching at the already-existing SessionState.Owner. The PR ended up lighter than its first draft, with host/boot guards it originally lacked.

Net effect once merged: agent commits link to their sessions automatically in any worktree, session adopt shrinks from a repair tool to its intended migration role, and the class of dangling-trailer incidents that cost three manual repairs becomes structurally impossible — with the residual cases (human commits amid multi-worktree ambiguity, Windows) falling back to hardened worktree matching that says so out loud instead of failing silently.

<result>Based on comprehensive documentation review, here are the precise, documentation-backed answers to your six questions about Claude Code's hook behavior for subagents:

## 1. **SubagentStop Hook Event Timing &amp; Payload**

**When it fires:** SubagentStop fires when a **subagent completes**, regardless of whether it ran foreground or background. For background agents that finish after the parent turn has ended, the hook fires at that later time — it is **not** tied to the parent's turn boundary.

**Payload fields** ([documented in Agent SDK hooks reference](https://code.claude.com/docs/en/agent-sdk/hooks), lines 519–557):
- `agent_id` (required) — identifier for the subagent
- `agent_transcript_path` (required) — file path to the subagent's own transcript (e.g., `.entire/session-&lt;id&gt;/subagents/agent-&lt;agent_id&gt;.jsonl`)
- `session_id` — parent session ID
- `stop_hook_active` — boolean indicating if the stop hook machinery is active
- `tool_use_id` (from callback signature) — correlates to the Agent tool call that spawned it
- `cwd`, `hook_event_name` — standard fields

**Blocking behavior:** **Notification-only, cannot block.** The documentation states hooks use `blocking?: false` by default to prevent loops, and SubagentStop "send[s] feedback but don't[t] prevent termination" ([GitHub issue #20221](https://github.com/anthropics/claude-code/issues/20221)). A SubagentStop hook can return `systemMessage` to notify the user, but cannot change the outcome.

**Default timeout:** 600 seconds (stated for most events; SubagentStop is not listed as an exception, so uses the general default).

---

## 2. **PostToolUse for Agent/Task Tool with Background Tasks**

**Documented behavior:** Your observation aligns with the design: **PostToolUse fires when the tool *result* is produced**. For `run_in_background: true` on the Agent tool (the tool `Agent` launches subagents), PostToolUse fires at the launch acknowledgment with a stub result (the task ID / agent reference), **not** at actual background completion.

The documentation does not explicitly name a "stub" payload field for background launches, but [tools reference § "Agent tool behavior"](https://code.claude.com/docs/en/tools-reference), lines 96–122, states:

&gt; The Agent tool spawns a subagent in a separate context window… returns a single text result to the parent conversation… the parent doesn't see the subagent's intermediate tool calls or outputs, only that final result.

For foreground agents, the "final result" comes when the subagent completes and control returns. For background agents, the result is the stub announcing the task launched. **There is no second PostToolUse at background completion** — the only event marking actual completion is **SubagentStop**.

This is the only documented behavior for PostToolUse on background agents. No follow-up hook at task-completion delivery is documented.

---

## 3. **Do Subagent-Internal Tool Calls Fire Parent Hooks?**

**Ambiguity / Not Documented:** The hooks documentation does not explicitly state whether tool calls **inside** a subagent's execution (e.g., a subagent running Bash, Read, Write) trigger the parent session's PreToolUse/PostToolUse hooks.

**What is documented** ([hooks reference, line 244](https://code.claude.com/docs/en/agent-sdk/hooks)):

&gt; `agent_id` and `agent_type` are populated when the hook fires inside a subagent. In TypeScript, these are on the base hook input and available to all hook types. In Python, they are optional fields on `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, and `PermissionRequest`, and required fields on `SubagentStart` and `SubagentStop`.

This confirms that these fields **exist** on PreToolUse/PostToolUse when fired inside a subagent, suggesting subagent tool calls **do** fire the hooks. But the docs do not explicitly confirm or deny parent-session hook firing, nor explain whether `agent_id` fields are visible to parent-registered hooks.

**Recommendation:** Treat this as underdocumented. Test locally: register a parent PreToolUse hook and check if `agent_id` is populated when the subagent runs Bash. If it is, subagent tool calls are visible to parent hooks and tagged with `agent_id`.

## 4. **Do Subagents Trigger Session-Lifecycle Hooks?**

**SessionStart / SessionEnd:** Per the documentation, these are **not** available in the Python SDK as callback hooks, only as [shell command hooks from settings files](https://code.claude.com/docs/en/agent-sdk/hooks), lines 825–842. The TypeScript SDK allows them, but there is **no documented statement** that they fire for subagent lifecycle.

**Stop hook:** The key finding: a subagent does **not** fire the main session's `Stop` hook when it completes. Instead, `SubagentStop` fires (a separate, subagent-focused event). The parent's `Stop` hook fires only when the parent's own turn ends.

**Documented behavior** ([tools reference, line 118](https://code.claude.com/docs/en/tools-reference)):

&gt; Where you see a subagent's permission prompts depends on whether it runs in the foreground or the background. Claude Code runs subagents in the background by default...
&gt; 
&gt; Foreground subagents show the same permission prompts you would see in the main conversation, at the moment each tool call happens. Background subagents surface permission prompts in your main session as of v2.1.186...

This implies subagents have their own execution context with their own hook/permission lifecycle, not a shared one with the parent.

## 5. **Subagent Transcript Files &amp; Agent ID**

**On-disk layout:** Not explicitly documented in the search results, but the SubagentStop payload includes `agent_transcript_path`, which the code example ([lines 524–527](https://code.claude.com/docs/en/agent-sdk/hooks)) logs directly:

print(f"  Transcript: {input_data['agent_transcript_path']}")

**No formal spec in the docs for the file layout.** Based on the field name and the Entire CLI codebase context (you're in `cli/.worktrees/claude-hooks`), the likely pattern is `.entire/session-&lt;session_id&gt;/subagents/agent-&lt;agent_id&gt;.jsonl` or similar, but **the Claude Code documentation does not specify this path structure.**

**Agent ID correlation:** The SubagentStop hook payload includes `agent_id`, and `agent_transcript_path` is delivered in the same event, so you can resolve the transcript deterministically from the hook. Whether the `agent_id` from SubagentStop matches the filename component is **not documented**. Treat that as an implementation detail to verify locally.

## 6. **SubagentStop with Multiple / Parallel Background Agents**

**Fire once per agent, no coalescing:** The documentation does not explicitly address parallel background agents, but the pattern is clear from the hook semantics: **SubagentStop fires individually for each subagent that completes**, at the time each finishes. There is no batching or coalescing documented.

The example ([lines 522–557](https://code.claude.com/docs/en/agent-sdk/hooks)) shows a single subagent handler, not a multi-agent pattern, so the docs are silent on ordering guarantees.

**Inference:** With five parallel background agents finishing at different times, expect **five separate SubagentStop events**, one per agent, unordered. No single event marks "all background agents done."

**Critical**

## Type: `session.InFlightTask` (+ `State.AddInFlightTask` / `RemoveInFlightTask` / `FindInFlightTask`)

`cmd/entire/cli/session/state.go`

### Invariants Identified
- **ToolUseID uniqueness** within `State.InFlightTasks` — enforced by `AddInFlightTask` (replace-on-match), and load-bearing: `RemoveInFlightTask` removes only the first match, so a duplicate entry would leak a stale marker.
- **Marker lifecycle**: added at background launch; cleared only by a Final capture (`claimInFlightTask` in lifecycle.go); turn-end incremental snapshots must never remove it.
- **Field ownership split**: the first five fields (`ToolUseID`, `AgentID`, `StartedAt`, `SubagentType`, `TaskDescription`) are immutable after launch; the last two (`LastCapturedTranscriptBytes`, `LastSnapshotAttempt`) are mutable cursors owned exclusively by the turn-end incremental path — the doc comment on `LastSnapshotAttempt` explicitly states the SessionEnd path never reads or writes it.
- **`LastCapturedTranscriptBytes` accounting invariant**: must only advance when the transcript at that size has been *fully accounted for* (either saved or confirmed zero-changes) — `captureInFlightTaskIncremental` deliberately skips persisting it on analyzer failure so the scan retries.
- Zero-value semantics: `LastCapturedTranscriptBytes == 0` means "never captured" and always triggers first capture (documented assumption: a resolved transcript is never zero bytes).

### Ratings
- **Encapsulation**: 5/10

But the methods coexist with direct slice access: `captureInFlightTasks` reads `state.InFlightTasks` raw, and `stampInFlightSnapshotAttempts` mutates elements via index in its own loop rather than through any `State` API. The immutable-after-launch vs. mutable-cursor split, however, is expressed only in prose; the flat struct makes all seven fields look equally mutable.

- **Invariant Usefulness**: 9/10

Each maps to a real failure mode, several of which the comments say were caught during design.

- **Invariant Enforcement**: 5/10

Lifecycle ("cleared only by Final"): enforced by convention plus a single choke point (`claimInFlightTask`) — enforcement-by-construction in lifecycle.go, but `RemoveInFlightTask` is public and nothing in the type prevents a non-Final caller. The comment reasons only about condensation triggers, but `StepCount` is the SaveStep checkpoint counter and has three other consumers in `SaveStep` (same file):

- `manual_commit_git.go:81` — `isFirstCheckpointOfSession := state.StepCount == 0`, passed as `checkpoint.Step.IsFirstCheckpoint`.
