### Medium finding

**Location:** `cmd/entire/cli/setup_search_skill.go:114`

**Compact session hits can't be drilled down, and the one command that bridges is now banned from the template**

Workflow step 2 says "session hits are projections of the same checkpoints, so drill down through the checkpoint", and step 3 says to explain hits with `entire checkpoint explain <id>`. But a compact session hit's only identifier is `id` = the session ID, and that doesn't resolve:

```
$ entire checkpoint explain 01KZEJWM1B2ARZX2J9910V5VQX
no checkpoint or commit found matching "01KZEJWM1B2ARZX2J9910V5VQX"
```

`explain`'s positional arg is documented as "checkpoint ID or commit SHA" only. The command that *does* bridge session → checkpoint is `entire checkpoint explain --session <id>`, which returns the owning checkpoint:

```
$ entire checkpoint explain --session 01KZEJWM1B2ARZX2J9910V5VQX --json
[{"checkpoint_id": "01KZEJHKE3BSTVGGXPT18HE5P9",
  "session_id": "01KZEJWM1B2ARZX2J9910V5VQX", ...}]
```

Commit `3ee291f83` was right that `--session` is a list filter and not a detail view. But removing it entirely leaves step 3 unreachable for session hits, and `setup_search_skill_test.go:241` now asserts the template must not contain the string `--session` at all. Session rows are a live, frequent result type — 24-26 of them per 100-hit query in my runs — so agents will hit this in practice.

Two ways out:

1. Name the bridge in step 2/3: "for a session hit, `entire checkpoint explain --session <id>` lists its checkpoints, then explain one of those."
2. Carry the checkpoint ID on session compact hits. The backend can't help with this today — `searcher.SessionResult` (`entire-search/internal/searcher/types.go:142-154`) has no checkpoint ID. Only the reverse direction exists, added in `adf6b67` as `CheckpointResult.sessionId`.

Separately, `strings.Contains(content, "--session")` is over-broad as a negative assertion: it will also fail on any future mention of `--session-index`. Pin the phrase you actually mean to ban.
