- persistent `copyMetadataDir`: `relPath = filepath.Rel(metadataDir, path)` = `full.jsonl` — one global slot shared by every session, and OS-separator rather than slash-normalized.

The only thing that keeps that safe is the `SourceHash` check, i.e. correctness is preserved by the fallback rather than by the key. Concurrent sessions (explicitly supported) would drive that slot to a 0% hit rate.

Deeper place: the key should be a caller-declared identity (session ID + file role), not "whatever string happened to be passed as tree path". Until then, drop the `treeWriter` wiring — it's unreachable.

**4. Sharding is gated on *which exported function you call*, not on whether the redactor is pure**

`redact/redact.go:566` routes `JSONLContent` → `jsonlContentConcurrent`, so the property "this redactor is goroutine-safe" is encoded in a function name. `redact/batch.go:156` (`applyRegexLayersToBlobs`) calls `jsonlContentImpl(..., String)` — the *same pure `String` redactor*, over whole `full.jsonl` blobs of every unpushed commit — and gets no sharding. That's the OPF-disabled/breaker-tripped fast path of `BatchBytesWithPrivacyFilter` (`batch.go:47,51`), reachable in production. `batch.go:121` (`collectLeaves`) and `batch.go:193` (`SumProseLeafBytes`) correctly *must* stay sequential — their closures mutate a shared map / accumulator — but nothing in the code says so; it's inferred from the call chain.

On the "should concurrency be the caller's choice" question: I checked every `JSONLContent`/`JSONLBytes` caller (doctor_bundle.go:283, attach.go:346, explain.go:1164, ephemeral.go:375/446, persistent.go:496/555/1064/2442, condensation.go:120, hooks.go:2907, agentimport.go:265). None is already inside a parallel loop — the repo's only other `errgroup` users are activity_cmd.go, repo_mirror_create_wizard.go, dispatch/mode_local.go, none near redaction. So unconditional sharding is not currently harmful, and making it a caller flag would be over-engineering. The real defect is the implicit safe/unsafe split.

Deeper place: `jsonlContentImpl(content, redactor, concurrencySafe bool)` (or two explicitly named internal wrappers). Then `applyRegexLayersToBlobs` opts in and the three collector closures declare themselves unsafe at the call site.

## Reasonable scoping choices, with caveats

**5. The `.jsonl` suffix gate is safe today but is a guess about the producer expressed in the consumer** — `redact_cache.go:171`

Verified: `.entire/metadata/&lt;session&gt;/` on disk contains only `full.jsonl` (written whole each Stop at `lifecycle.go:761-762`) and `prompt.txt` (line 790). `transcript.jsonl` is written **straight into the git tree** (`persistent.go:1131`, `writeCompactTranscript`) and never lands on disk, so the regenerated file never reaches this gate.

Applying the cache to a regenerated `.jsonl` would be **merely wasteful, not wrong-shaped**: the reuse test is `sha256(content[:SourceBytes]) == entry.SourceHash` (redact_cache.go:~188) and it runs *before* the blob read, so a changed prefix costs one SHA-256 and falls back to a full redaction with correct output. But the hit rate then silently depends on the producer's behaviour with no signal — no metric, no log distinguishing "eligible and hitting" from "eligible and never hitting".

The right gate at identical cost: `filepath.Base(treePath) == paths.TranscriptFileName`. That matches what the doc comment already claims ("append-only transcripts"), makes the `transcript.jsonl` question moot permanently, and is the caller's own constant. Note also `agent.ChunkFileName` (`agent/chunking.go:122`) produces `full.jsonl.001`, which the suffix gate misses — irrelevant on disk today, but it's the first shape that would slip through.

**6. `gitrepo.CommonDir` is the right home — but it's now the third resolver**

`gitrepo/repository.go:67` composes `resolveDotGitPath` + `resolveCommonGitPath`, both already private to `gitrepo`, and resolves from the repo object rather than `os.Getwd()` + a `git rev-parse` subprocess. For a store bound to a specific repo on a hook path, that is strictly better than `session.GetGitCommonDir` (state.go:791, cwd-keyed cache + subprocess) — and `strategy.GetGitCommonDir` (common.go:1102) is already a third, uncached copy of the same subprocess.

Import cycles did **not** force this: `go list -deps ./cmd/entire/cli/checkpoint` already includes `session`, and `gitrepo` imports only `paths`. So it was a free choice, and the right one. Deeper cleanup available (out of scope for this diff): expose `gitrepo.CommonDirForPath(root)` and have `session`/`strategy` delegate, deleting two subprocess implementations.

**7. The fingerprint split is defensible in shape, but its stated justification is half wrong**

`redact/fingerprint.go:30` says the betterleaks ruleset version is something "the library does not expose", so the caller must mix in the binary version — and `redact_cache.go:97` does. But `github.com/betterleaks/betterleaks v1.5.0` is a plain module dependency (go.mod:12, no `vendor/`, no `replace`), so `debug.ReadBuildInfo().Deps` yields its version and `h1:` sum at runtime. `redact` can own that half itself, with no caller cooperation and no manual bump on dependency upgrades.

That matters because of what's left: `configFingerprintVersion` (fingerprint.go:17) is a hand-bumped constant, and the caller's `versioninfo.Version+Commit` mixin already subsumes it for *released* binaries. So the constant only bites in local builds — where `versioninfo.Version` stays `"dev"` and `Commit` is the unchanged HEAD sha even with a dirty tree (`versioninfo.go:39-56`). In other words the one population that needs the manual bump is exactly the developer editing `redact/`, and nothing enforces it. Moving the dep-version half into `redact` shrinks the manual constant's remit to "changes to redact's own source", which is the genuinely un-introspectable part.

The OPF exclusion is handled correctly *by construction* (this path always passes `usePrivacyFilter=false`, `persistent.go:2393`), but neither the key nor the fingerprint carries a pipeline discriminator, so nothing stops a future OPF-enabled caller from sharing the cache dir. Worth a discriminator byte in the key while it's cheap.

## Minor

**8.** `entire-redact-cache` isn't registered with cleanup — `strategy/cleanup.go:25-28` knows only shadow-branch / session-state / checkpoint. One ~200-byte JSON per session accumulates in the git common dir forever and `entire clean` won't touch it. It shadows session-state 1:1, so it belongs as a `CleanupType` next to it.

**9.** Two independent 1MiB thresholds for the same phenomenon in two packages: `redact_cache.go:54` and `redact/redact.go:626`.

**10.** Single-JSON-value transcripts (OpenCode export) get *neither* mechanism: `redactSingleJSONValue` (redact.go:590) short-circuits before the shard split, and the trailing-newline requirement (redact_cache.go:~178) excludes them from the prefix cache.
