`checkoutTrailWorktree` anchors the new worktree path at `paths.WorktreeRoot(ctx)` (line 1349), but that function's own doc says it returns the *current* worktree's root, not the main repository root, when invoked from inside a linked worktree. Since the command prints a `cd` hint into the newly created worktree and agents are expected to follow it, running `entire trail checkout --worktree` again from inside that worktree will nest the new worktree under `.entire/worktrees/<prev>/.entire/worktrees/<new>` instead of placing it alongside the first one at the main repo root, defeating the feature's purpose of predictable, sibling worktree locations.
