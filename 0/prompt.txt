In explicit-target mode, `runAttach` still calls `saveAttachSessionState`, which unconditionally sets `state.LastCheckpointID = checkpointID` (the server-minted, commit-SHA-bound review checkpoint) and, if `BaseCommit` was empty, sets it to the current HEAD. `LastCheckpointID`/`BaseCommit` are also read by `handleAmendCommitMsg` (prepare-commit-msg hook) to auto-restore an `Entire-Checkpoint` trailer on a later `git commit --amend` of the same base commit, and by the resume picker. Since the explicit-target checkpoint is deliberately *not* meant to be trailer-linked (it's bound via `commit_sha` metadata, not a trailer), this can cause a later unrelated amend to silently inject the review-provenance checkpoint ID as the code checkpoint trailer, or make `session resume`/`sessions` misreport the session's checkpoint linkage.

When `refreshCheckpoint` fails inside `ensureExplicitCheckpointFreshness` (network blip, auth failure, remote misconfig), this treats the checkpoint as "not present" and lets the caller proceed to write a brand-new checkpoint under the caller-supplied ID. `FetchCheckpointRef`'s own doc says a fetch failure is indistinguishable from "ref doesn't exist" ("the caller treats a fetch failure as 'checkpoint not found'"), so a transient fetch error on a retry — exactly the scenario this function exists to guard against per its own docstring — silently takes the risky path and can rebuild the ID as an orphan that clobbers the original checkpoint on push. Compare with the sibling `ensureCheckpointAvailable`, which on the same fetch failure falls through to `missingCheckpointError` and refuses rather than assuming safety. This branch should likewise propagate the fetch error instead of returning `(repo, false, nil)`.
