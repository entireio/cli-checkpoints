Instrument search telemetry in the Entire CLI. From the ENT-2073 search pipeline audit.

THE PROBLEM: we cannot measure real-world search quality because two of our three search surfaces emit no telemetry at all.

Verified against PostHog (project "entire.io", id 102418), 30-day window:
  - search_executed          455 events, 46 users
  - search_filter_applied    448
  - search_result_clicked    135
  - list_search_used           3
All of the above are WEB APP events. There is NO CLI search event and NO MCP search event anywhere in the project taxonomy. This is zero instrumentation, not low volume.

Note: the original audit ticket cites an event called `cli_search_completed` with 41 events in 30 days. That event does not exist in the taxonomy — PostHog flags it as unknown, and the figure could not be reproduced. Do not assume it exists.

YOUR JOB: add telemetry to the CLI's search command so we can actually measure search quality and usage from the CLI surface.

BEFORE BUILDING — one thing to rule out (5 minutes): a separate PostHog project could already hold CLI telemetry. Only the org's active project was checked. Confirm there isn't existing CLI search instrumentation somewhere before adding new events.

WHAT TO CAPTURE — think about what would actually let us answer "is search any good?": at minimum whether a search ran, how long it took, how many results came back, and whether the user acted on a result. Follow whatever telemetry conventions the CLI already uses for other commands — match the existing event naming and property style rather than inventing a new one.

CONSTRAINTS:
  - Do NOT log or transmit the user's raw query text. The same audit flagged query-text leakage as a privacy issue on the server side; do not introduce it here.
  - Respect whatever telemetry opt-out the CLI already honours.

Prefer Entire search — `search_entire_code` to locate the CLI's existing telemetry helpers and the search command across repos, and the `entire search` skill for prior work on CLI telemetry — over grepping and reading whole files.

A parallel agent is doing the equivalent work in the `mcp` repo. Keep event naming consistent with what that surface will emit; if you settle on a naming scheme, say so in your PR description.
