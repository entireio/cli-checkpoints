⏺ The web-click analog exists here — you just have to force the funnel to have two steps and correlate them. A few approaches, roughly in order of signal quality:

  1. Make "fetch detail" the click (best signal)
  Design search to return snippets + stable IDs, and require a second call (entire checkpoint explain <id>, show <id>, MCP get_checkpoint) to get full content. That fetch is the click. Then:
  - Attach a search_id to every search response, and log (search_id, query_hash, result_id, rank_position) for each result served.
  - When the CLI sees a detail fetch for an ID that was served in a recent search in the same session (you already have session state in .git/entire-sessions/ to correlate), emit a "click" event with
  the rank position via the existing __send_analytics path.
  - Now you can compute CTR-by-position, MRR, etc. exactly like web search.

  The key design constraint: don't return full content inline in search results, or there's never a second observable action. Snippet-only results aren't just a tracking hack — they're also better for
  agent context economy, so it's aligned incentives.

  2. Query reformulation as negative signal
  If the same session issues another search within N seconds/turns without fetching any result, that's an abandonment/reformulation — strong "ranking failed" signal. Chains of reformulated queries
  ending in a fetch tell you which query finally worked, useful for query rewriting training data too.

  3. Downstream conversion (unique to your position)
  You own the checkpoint transcripts. After a session ends, you can check whether files/checkpoints surfaced in search results actually got read, quoted, or edited later in the transcript, or whether
  searched-for code paths appear in the eventual diff. That's a "purchase" signal web search rarely gets. More expensive (offline batch job over transcripts), but much higher fidelity than the click.

  4. Explicit self-report (cheap, biased)
  An MCP tool param or --used <ids> feedback verb, with agent-help/context-injection nudging agents to report which results helped. LLMs will comply inconsistently and sycophantically — treat as
  supplementary, not primary.

  Recommendation: ship #1 + #2 first — they're purely structural (IDs, snippet-only results, session-correlated analytics events) and require zero cooperation from the agent. #3 is the moat later,
  since nobody doing web search can see what the user did after the click the way you can with transcripts.

  One caveat for #1: agents batch tool calls and sometimes fetch several results in parallel regardless of relevance. So also log which fetched result the agent kept working with (repeat fetches,
  follow-up explains on the same ID) to separate "opened the top 3 defensively" from actual usefulness.

⏺ Yes — ENT-1527 is the structural half of #1. Compact-by-necessity output means agents fetching the full prompt via checkpoint explain becomes the mandatory second step, and that step is your click.
  You get the tracking almost for free by riding two things the issue already depends on:

  - ENT-1527 (compact mode) removes the full prompt from results → the agent must call explain for the hit it cares about. Today that fetch never happens because everything is inlined, which is exactly
   why you have no click signal.
  - ENT-1523 (cross-repo resolvable IDs) makes the IDs in search results directly explainable — the "URL" the agent clicks.

  What I'd add to the ENT-1527 scope to close the loop:

  1. search_id on every search response (a ULID in the JSON envelope, one line). Server/CLI logs the impression set: (search_id, query_hash, result_id, rank, score).
  2. Correlation at explain time. Two options:
    - Zero-cooperation: CLI stores the last-N served (search_id, result_id, rank) tuples in session state (.git/entire-sessions/ already exists for this); when checkpoint explain <id> runs and the ID
  matches a recent impression in the same session, emit a click event through __send_analytics with the rank. Agents can't forget to do it and can't game it.
    - Explicit: include a ready-made hint in compact output like explain: entire checkpoint explain <id> — you get the click either way, but avoid requiring agents to pass --search-id; they'll drop it
  inconsistently.
  3. Reformulation signal comes free too: consecutive search calls in the same session with no intervening explain = abandonment at that ranking.

  One design detail worth deciding now: put the truncated snippet length where it forces the fetch but doesn't starve triage. Too short and agents defensively explain 3–5 hits (noisy clicks), too long
  and they never fetch (no clicks). The ~200 chars in the issue is probably right; the bench harness you already have (entire-search-bench) can measure explain-rate per snippet length if you want to
  tune it.

  So I'd frame it as: ENT-1527 + ENT-1523 + a small analytics rider (search_id, impression log, explain-time correlation) = full CTR/MRR pipeline for agent search. Worth a linked issue for the
  analytics rider so it ships with compact mode rather than after — retrofitting the impression log later means losing the baseline data from launch. Want me to draft that issue?
