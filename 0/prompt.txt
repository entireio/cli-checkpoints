## Summary

The cluster's `/.well-known/entire-cluster.json` `core_urls` **are** the candidate login servers. A context's `CoreURL` is the JWT `iss` of the login server it was created against, and cluster resolution matches those two. So the "region / login server" for a cluster is obtained by a **network well-known fetch** of the cluster host; there is no static host-naming derivation. The data (`core_urls`) is available at the no-eligible-context error site but is **not currently surfaced** in the login hint, and no existing code feeds a cluster-discovered core into `entire login --server`.

### 1. `internal/entireclient/clusterdiscovery/` — the API and schema

**Well-known schema** — `internal/entireclient/clusterdiscovery/discovery.go:29-42`. `Response` has exactly three consumed fields:
- `core_urls []string` — the trusted entire-core URLs the cluster accepts JWTs from (the JWT issuers). Comment (discovery.go:18-19): "the cluster advertises which entire-core URLs it accepts as JWT issuers."

## 3. What login actually fixes it — the key relationship

A context's `CoreURL` is **not** the URL you typed for login — it is the token's signed `iss` claim:
- `contexts.Context.CoreURL` doc (contexts.go:36-38): "CoreURL is the JWT issuer URL — what STS exchanges hit. Set from the access token's signed iss claim, not the typed login URL."
- `auth.RecordLoginContext` (`/Users/gtrrz-victor/wks/cli/fix-conflicts/cmd/entire/cli/auth/contexts.go:64`): `coreURL := claims.Issuer`.

But login **enforces that the token's `iss` equals the `--server` origin** you logged into:
- `login.go` → `persistLogin(outW, baseURL, token, ...)` where `baseURL = client.BaseURL()` = the login `--server` (login.go:109,211,328).
- `persistLogin` → `validateReceivedToken(token, baseURL, ...)` (login.go:335) → `issMatches(claims.Issuer, issuerURL)` rejects any token whose `iss` origin ≠ the login server (login.go:397-399,414-421).

**Therefore `CoreURL == iss == the login `--server` origin`.** For a context to become eligible for a cluster, you must `entire login --server &lt;X&gt;` where `&lt;X&gt;` is (origin-equal to) one of that cluster's advertised `core_urls`.

So **yes, the well-known directly exposes the servers to log into**: the `core_urls` array *is* the list of trusted auth/issuer origins. To fix `aws-eu-central-1.entire.io`, read `https://aws-eu-central-1.entire.io/.well-known/entire-cluster.json`, take a `core_urls` entry, and run `entire login --server &lt;that URL&gt;`.

**Region/federation is a property of the auth server (the core/issuer), not the account.** Evidence:
- The default login server is `https://us.auth.entire.io` (`/Users/gtrrz-victor/wks/cli/fix-conflicts/cmd/entire/cli/api/base_url.go:18-20`), and the `--server` flag help says "rarely needed; the default serves all standard accounts" (login.go:87-88). A region-fronted cluster (e.g. an EU cluster) that does not trust `us.auth.entire.io` will therefore reject the default-login context and require logging into its own regional core (e.g. an `eu.auth…`-style origin) — whatever its `core_urls` names.
- The env-token path corroborates the same trust model: it validates the token's issuer against `cluster.CoreURLs` via `coreTrusted` (main.go:419-446), rejecting a token "belong[ing] to a different cluster".

Fields that carry this: `Response.CoreURLs` (`core_urls`) in discovery.go:32; read by `resolveClusterCores` (resolve.go:214-216) and matched in `selectContext`/`eligibleContexts` (resolve.go:228,255-267). (The data-API analogue is `trusted_issuers` in `/.well-known/entire-api.json`, api_discovery.go:20-30.)

## 4. Is there a flow that auto-resolves the login server and prompts?

**No — not for a cluster host with no eligible context.** Concretely:

- **The full-URL clone path never prompts.** In `/Users/gtrrz-victor/wks/cli/fix-conflicts/cmd/entire/cli/repo_clone.go`, a full `entire://…` ref short-circuits straight to `runGitClone` (repo_clone.go:120-122) — it deliberately skips `ensureCloneSession` (which is gated on the shorthand path with `cluster == ""`, repo_clone.go:136-140). So the exact command the user ran goes to `git clone` → `git-remote-entire`, whose only output is the raw `renderLoginHint` fatal + "remote helper 'entire' aborted session". The helper can't prompt anyway (main.go:9-12).

- **The interactive re-auth that does exist ignores cluster discovery.** `ensureCloneSession` (repo_clone.go:267) → `probeCloneSession` (repo_clone.go:211) resolves via `auth.ResolveControlPlaneTarget()` and re-logs into **the active context's core, or `api.DefaultAuthBaseURL` (`us.auth.entire.io`) when there's no context** (repo_clone.go:217,224) — it never fetches the cluster's `/.well-known` to pick the correct regional core. So even on the shorthand path it would log you into the default/active core, not necessarily the one the target cluster trusts.

- **The `core_urls` are computed but thrown away in the hint.** `renderLoginHint(subject string, _ []string)` discards the second (coreURLs) argument (discovery.go:154), with the explicit comment "We'll display coreURLs (2nd param) to the user as a hint at a later stage" (discovery.go:153). The caller passes them in (`renderLoginHint(subject, coreURLs)`, resolve.go:243) but they are not surfaced. No other code path renders `core_urls` to the user for login guidance (only the ENTIRE_TOKEN mismatch error at main.go:424-425 lists them, and debug logs).

**Bottom line for the user:** the CLI currently gives no automated way to discover the right login server. The manual fix is to fetch `https://aws-eu-central-1.entire.io/.well-known/entire-cluster.json`, read its `core_urls`, and run `entire login --server &lt;that origin&gt;`; that produces a context whose `CoreURL`/`iss` lands in the cluster's `core_urls`, making it eligible and clearing "no auth context for cluster."
