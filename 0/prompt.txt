## 1. `--no-optional-locks` does not stop `git diff` from rewriting the index

This is the one I'd fix before merging. Measured on git 2.50.1 (Apple Git-155), same repo, same shape, stat-stale index:

| invocation                                                 | `.git/index`  |
| ---------------------------------------------------------- | ------------- |
| `git status --porcelain`                                   | REWRITTEN     |
| `git --no-optional-locks status --porcelain`               | UNCHANGED     |
| `git diff --name-only HEAD -- <paths>`                     | REWRITTEN     |
| `git --no-optional-locks diff --name-only HEAD -- <paths>` | **REWRITTEN** |
| `GIT_OPTIONAL_LOCKS=0 git diff ...` (env form)             | **REWRITTEN** |
| `git diff-index --name-only HEAD -- <paths>`               | UNCHANGED     |

`builtin/commit.c` gates its refresh on `use_optional_locks()`; `builtin/diff.c`'s `refresh_index_quietly()` doesn't. So `worktree_diff.go:33` carries the flag but still takes `.git/index.lock` and renames a new index over `.git/index` — the exact producer CLAUDE.md's "`git status` Is a Write" section documents (#2111: the `index.lock` collision with the user's own `git add`, and the virtiofs empty-tree commit), from the post-commit hook, asynchronous to the human's terminal.

It's not always-on: a fresh index → UNCHANGED. But the rewrite needs stat-stale entries, and this code only runs when there are candidates — committed content ≠ shadow content with a still-dirty worktree. That *is* the stat-stale case.

`git diff-index` avoids the write but reports stat-dirty-yet-content-identical files as changed. In this code that direction is conservative (an extra carry-forward, never a lost one), so it may be an acceptable trade — but it's a real behavior change, so it's your call. What shouldn't ship is the current state, where the flag reads as if it handles this and nothing says otherwise.

Related: `TestGitStatusCallSitesPassNoOptionalLocks` greps `"status"` only. This is the codebase's first worktree-comparing `git diff` — `experts_cmd.go:591` and `manual_commit_hooks.go:2840` are `--cached`, `review/scope.go:222` is `base...HEAD`, none touch the index. Whatever you decide, the guard should learn about `git diff <rev>` so the next call site doesn't rediscover this.

## 1. The new guard is inert against the code it was written to prevent

I restored `f799fedc9`'s `worktree_diff.go` verbatim into the tree and ran `TestGitWorktreeDiffCallSitesDoNotRefreshTheIndex`. It **passes**.

`containsAnyMarker(rest)` requires a git-invocation marker on the same line as `"diff"`. gofmt puts a long argv on its own lines, so the file splits into:

```go
baseArgs := []string{
    "--no-optional-locks", "-C", worktreeRoot,
    "diff", "--name-only", "-z", ...   // ← "diff", no marker  → skipped
}
cmd := exec.CommandContext(ctx, "git", args...)  // ← marker, no "diff" → never grepped
```

`git grep` does see the line (`--untracked` is on) — it's the marker requirement that drops it. The single-line form is caught; I confirmed that too with a throwaway `exec.CommandContext(ctx, "git", "diff", "--name-only", "HEAD")`, which fails the guard correctly.

The status guard's documented limitation doesn't transfer, and that's the part worth internalizing. There, the flag and the word `"status"` both live on the argv line, so wrapping separates the *flag* from the word — a false positive, loud, safe. Here the marker lives on the `exec.Command` line and `"diff"` on the argv line, so wrapping separates the *marker* — a false negative, silent. Same structure, opposite failure direction.

Options: drop the marker requirement and match `"diff"` alone (noisier but sound), scan the enclosing statement rather than the line, or — matching existing precedent in this repo — an explicit `file:reason` allowlist like `entireDirCheckExemptions`, where anything unlisted fails.

Related and smaller: `strings.Contains(rest, `+"...HEAD"`)` matches one expression's exact gofmt spelling (`review/scope.go:222`). Rewriting it as `fmt.Sprintf("%s...HEAD", baseRef)`, or adding spaces around the `+`, fires the guard falsely. Loud direction, so not urgent.

## 2. Symlinks now always read as dirty

`git hash-object` follows the link and hashes the target's *content*; git stores a symlink blob as the target *path string*. Measured:

```
hash-object link.txt        → 9230cd37…   (content of real.txt)
git rev-parse HEAD:link.txt → c9c61fe1…   (hash of the string "real.txt")
```

So a symlink candidate can never compare clean — permanent carry-forward, the same phantom-loop class this branch exists to remove, for a narrow trigger. Not a regression against `main` (the raw-byte fallback also always said dirty), but it *is* one against the intermediate `git diff` version, which handled symlinks correctly. `commitTree.File(path)` already carries `Mode`, so skipping candidates with `filemode.Symlink` before the hash call is a couple of lines.

## 3. Smaller

- The Warn text says "using filter-unaware raw hashes for failed files", but for a missing or unreadable file the fallback isn't a raw-hash comparison at all — `ReadFileNoFollow` fails and the file is treated as dirty. Worth matching the wording to both outcomes.
- If `git` is off `$PATH`, the batch fails with a non-`ExitError`, `ctx.Err()` is nil, and the per-file retry spawns once per path; `errors.Join` then puts every one of those errors into a single Warn line. Bailing out of the retry when the batch error isn't an `ExitError` bounds it — the retry exists for "one bad file in a good batch", which is precisely the `ExitError` case.
- `--stdin-paths` would delete `chunkPaths`, its test, the 8 KiB budget and the Windows argv comment. You'd still need the per-file retry — git dies at the first bad path either way (verified: rc=128, partial stdout, stderr names the file). Purely optional.

One thing worth keeping: discarding the partial stdout on failure and retrying is the right call, and the `len(fields) != len(paths)` check is what makes it safe rather than merely cautious — git really does emit hashes for the files it processed before dying.
