## What's done well (credit where due)

- The write fallthrough condition is deliberately **stricter** than the read one (`firstResolved` at `routing_store.go:66-83` falls through on *any* error; `Write` at `routing_store.go:193-207` only on `ErrCheckpointNotFound`). ## 1. HIGH — Read/write existence probes diverge: a backfill can silently land on a stale copy readers will never surface

**Location:** `cmd/entire/cli/checkpoint/routing_store.go:193-207` (fallthrough decision), driven by `cmd/entire/cli/checkpoint/refs_store.go:75-98` (`refBase`) vs `refs_store.go:272-299` (`resolveRefMaybeFetch`).

The PR's doc comment says backfills "follow the read order." They follow the read *order*, but not the read *existence probe*. Reads go through `resolveRefMaybeFetch`, which on-demand fetches a checkpoint ref missing locally when a `RefFetcher` is configured. The refs backfill path (`backfillSummary`/`backfillTranscript`/`backfillAttribution`, `refs_store.go:163-236`) resolves via `refBase`, which is **local-only** (`s.repo.Reference` at `refs_store.go:80`).

**Concrete failure scenario:** refs primary, mid-migration, multi-machine. A hex checkpoint was migrated into refs on machine B; machine A still has the pre-migration copy on its local v1 branch and hasn't fetched the ref.

- Machine A backfills (e.g. transcript finalize at stop): refs store sees no local ref → empty entries → `ErrCheckpointNotFound` (`persistent.go:292-293`) → router falls through → **writes the backfill onto the stale v1-branch copy**. `Write` returns nil. Success, apparently.
- Machine A later reads: `resolveRefMaybeFetch` **fetches the ref**, refs resolves first in `readOrder`, and serves the migrated copy — which does not contain the backfill.

The backfill reported success and is permanently invisible to every reader. No error, no log, nothing to debug from. Users will be confused when a summary they watched `explain --generate` print "Summary generated for X" for never shows up again.

**Recommendation:** the refs store's backfill absence probe must match the read probe — either route `refBase` through `resolveRefMaybeFetch` (fetch-before-declare-absent), or explicitly document and log the divergence. If fetch-on-backfill is added, note the interaction with issue 2 below: a fetch *failure* must not be classified as not-found (`resolveRefMaybeFetch` already gets this right at `refs_store.go:287-291`), and the router's strict fallthrough will then correctly abort rather than fork.

## 2. CRITICAL (by this repo's standards) — The fallthrough is completely unlogged

**Location:** `cmd/entire/cli/checkpoint/routing_store.go:198-206`.

When a backfill misses the primary and lands on a fallback store, three signals are silently discarded:

- the primary reported `ErrCheckpointNotFound` for a checkpoint the caller believes exists (that error object, possibly carrying wrapped context, is overwritten on the next loop iteration and never seen);
- the write landed somewhere other than the configured primary;
- mirrors were deliberately skipped (see issue 3).

This package logs comparable routing decisions everywhere else: mirror write failure → `logging.Warn` (`fanout.go:74-75`), on-demand ref fetch failure → `logging.Debug` (`refs_store.go:288-289`), session-ID fallback inside a backfill → `logging.Debug` (`persistent.go:377-381`). The single most consequential routing decision this PR introduces — "your data went to the other backend" — logs nothing. Six months from now, "why is this summary on the v1 branch and not in refs, and why does the web mirror not have it" is undiagnosable.

**Recommendation:** in the loop, when `errors.Is(err, ErrCheckpointNotFound)` and there is a next store, emit `logging.Debug` (arguably `Info`) with `checkpoint_id`, the store being skipped, and the request type; when the write ultimately succeeds on a non-first target, log that the backfill was served by a fallback store and that mirrors were skipped. Operational metadata only (IDs/types), consistent with the privacy rule. `routing_store.go` doesn't import `logging` yet — that's the tell that no path in this file logs anything.

## 3. HIGH — Fallback backfills silently skip mirrors, permanently forking mirror state

**Location:** `cmd/entire/cli/checkpoint/routing_store.go:225-241` (`backfillOrder`), interacting with `cmd/entire/cli/checkpoint/fanout.go:66-79`.

`fanoutStore.Write`'s logged-and-swallowed mirror errors are pre-existing and defensible (mirrors are best-effort by contract, `fanout.go:10-17`). But the PR **does** change the semantics around it:

- **Before:** every backfill went through `writer`. Mirrors either got the backfill (primary success) or the whole operation failed loudly (primary not-found → error to caller, per the old regression this PR fixes).
- **After:** a backfill that falls through to a fallback store succeeds **and bypasses mirrors entirely** — by design, per the comment and the test at `routing_store_test.go:319-333`. There is no log line (issue 2) and no error.

**Concrete scenario:** refs primary + an ingestion mirror (the topology used for web visibility). Pre-migration hex checkpoints on the v1 branch get their stop-time transcript finalize (`manual_commit_hooks.go:2935`): router falls through to the branch store, mirror never receives the finalized transcript or the AI summary. The web view shows the truncated condensation-time transcript forever, and nothing anywhere records why. The "mirrors follow the primary" rationale is coherent, but a mirror that received the checkpoint's *create* (mirrors are attached to the writer regardless of which read store later serves the backfill) now silently holds a permanently incomplete copy. This is exactly the "fallback masks the real problem" pattern: the real problem is "this checkpoint isn't in the primary," and the fallback makes that invisible.

**Recommendation:** at minimum, the fallback-store success path must log that mirrors were skipped (folds into issue 2). Better: consider fanning the backfill out to mirrors best-effort even on the fallback path — the mirror's own `ErrCheckpointNotFound` is already swallowed-with-Warn by `fanout.go:73-76`, so mirrors that never saw the checkpoint degrade gracefully while mirrors that did stay complete.

## 4. MEDIUM — The fallthrough "probe" has write side effects: it creates the v1 branch in refs-only repos

**Location:** `cmd/entire/cli/checkpoint/persistent.go:1696`, `1744`, `860-862` → `ensureSessionsBranch` at `persistent.go:2109-2135`.

Every branch-store backfill *starts* by creating the `entire/checkpoints/v1` orphan branch if absent ("Initialize sessions branch" commit, plus a vercel-config merge via `maybeMergeVercelConfig`). Before this PR, a refs-primary repo never sent backfills to the branch store. Now, any hex-ID backfill that misses the refs primary (including a typo'd ID to `explain --generate &lt;hex&gt;`, or a cleaned-up checkpoint) falls through and — even though the final answer is `ErrCheckpointNotFound` — **leaves a newly created v1 branch behind** in a repo that never used the git-branch backend. That branch is then live: `List` unions it, pre-push logic pushes it, doctor sees it. An existence probe that mutates the repo on a miss is a hidden failure mode; the user asked a question and got a branch.

**Recommendation:** the branch store's backfill path should check for the checkpoint's existence (or at least the branch's existence) *before* `ensureSessionsBranch`, returning `ErrCheckpointNotFound` without creating anything. A missing v1 branch trivially implies the checkpoint is absent.

## 5. MEDIUM — `subtreeObjAt` converts real failures into "absent," and the router now uses that as a write-routing predicate

The realistic scenario (stale committed list — e.g. a v1-mirror entry whose primary ref is gone, or an interrupted condensation leaving a dir without a root summary) previously produced the **lie** "no checkpoint or commit found matching %q" for a target that did match; now it produces a truthful read failure. `explain.go:735` is strictly better: the old fallback could run commit resolution *after* the summary was already persisted, reporting "no checkpoint or commit found" for a command that had a durable side effect. Verdict: acceptable truthfulness improvement, no real-user regression.

### Q2: Remote-fetch retry path

No shape regression: `matchCheckpointPrefixWithRemoteFallback` (`explain_export.go:196-244`) returns `(matches, lookup)` with **no error channel**, so every internal failure collapses to zero matches → temp check → typed miss → fallback still runs. But see HIGH-2 below — that collapse is itself a silent failure.

### Q3: Second `runExplainCheckpointWithLookup` call (explain.go:551)

Its return value is returned directly from `runExplainAuto` — it never re-enters the fallback check (no loop, no swallow). A missing trailer-referenced checkpoint errors loudly as "checkpoint not found: \&lt;cpID\&gt;". Identical to old behavior at this site. See MEDIUM-2 for a message-context nit.

## Findings

**HIGH-1 — Temp-checkpoint path can still stamp "target matched nothing" on a target that DID match.**
`explain.go:1275-1283`: after `len(matches)==1` — a temporary checkpoint **did** match the SHA prefix — an unreadable shadow commit (`:1277`) or tree (`:1282`) returns `found=false, nil` with **zero logging**, which flows to `explain.go:663` and mints `explainTargetNotFoundError` — whose doc comment now asserts "matched no committed or temporary checkpoint". That claim is false here. The user gets "no checkpoint or commit found matching %q" for a checkpoint that appears in `entire checkpoint list`, with no log trail. This is the exact inverse-conflation the PR fixes on the committed side, left intact on the temp side. Hidden errors: pruned/gc'd shadow objects, packfile corruption, filesystem IO errors. Pre-existing, but the PR's typed error hardens the semantic claim without fixing the one path that can violate it. Recommendation: distinguish "match found but unreadable" (surface an error naming the shadow SHA) from "no match", and at minimum `logging.Debug` both sites plus `:1239` (`ListAllCheckpoints` failure — an IO error listing shadow branches is also swallowed to not-found, unlogged).

**HIGH-2 — Remote-fetch failures are classified as "doesn't exist" with zero logging.**
`explain_export.go:216-217` drops `fetchErr` from `FetchCheckpointRef`; `:236-237` drops `v1Err` from `getMetadataTree`; `:219-224` and `:239-241` drop `freshErr` — none logged (contrast `refs_store.go:287-290`, which logs its on-demand fetch failure). Offline or auth-expired users asking for a checkpoint that exists remotely get "no checkpoint or commit found matching %q" — indistinguishable from a typo, undebuggable 6 months later. The PR now formalizes this bucket as the typed target-miss, so it deserves the fix: `logging.Debug` each swallow, and ideally thread "(remote fetch failed: …)" into the final not-found message at `explain.go:531`.

**HIGH-3 — The conflation bug this PR fixes survives in the JSON sibling path.**
`explain_export.go:126-132`: on prefix miss, `resolveCheckpointFromCommitRef`'s `commitErr` is dropped entirely (only `== nil` checked) and the flow reports `"checkpoint not found: &lt;prefix&gt;"`. That function has post-resolution failure modes (trailer found but `newExplainCheckpointLookup` fails at `:162-165`, commit read failure at `:154-156`) that are thereby masked as not-found — the same class of masking PR #1812 removes from the prose path. `entire explain --json &lt;commit-sha&gt;` remains inconsistent with the fixed prose behavior. Recommend a follow-up applying the same discipline.

**MEDIUM-1 — Newly surfaced errors lack the resolved checkpoint ID.**
`explain.go:688`, `:787`, `:791`, `:735` wrap without `fullCheckpointID`, and the store frequently returns the **bare** sentinel (`persistent.go:254`), so the user-visible result of the PR's new behavior can be literally `failed to read checkpoint: checkpoint not found`. A user who typed a 4-char prefix has no idea which full checkpoint matched, that prefix-resolution succeeded, or that `--commit` would disambiguate an intended commit. The spinner that displayed the ID (`explain.go:702`) is erased on stop. Recommend `fmt.Errorf("failed to read checkpoint %s: %w", fullCheckpointID, err)` at all four sites — cheap, and it makes the PR's truthfulness win actually actionable.

**MEDIUM-2 — Trailer-path miss error omits the commit the user typed.**
`explain.go:551` + `:663`: `entire explain abc1234` where the commit's trailer references a vanished checkpoint yields "checkpoint not found: 01KV…" — an ID the user never typed; the connection exists only in a Debug log (`:547-550`). Recommend wrapping at `:551`: "commit abc1234 references checkpoint \&lt;id\&gt; via its Entire-Checkpoint trailer: %w".
