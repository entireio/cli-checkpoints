**No discovery document is ever fetched.** Grepping the whole repo and the `github.com/entireio/auth-go v0.5.2` module (`go.mod:15`) for `well-known/openid-configuration` returns zero non-test hits. `provider.go:5-11` says the paths were "confirmed against us.auth.entire.io's /.well-known/openid-configuration" — i.e. they were copied by hand once, at authoring time. # 3. `--server` semantics, and refresh

**Semantics** (`login.go:106-107`, doc block `login.go:113-118`): a bare http(s) **origin** naming the OAuth authorization server. It becomes, per that comment, "the OAuth issuer, the token-exchange target, and the keyring key". Path/query/fragment/userinfo are rejected rather than trimmed (`login.go:131-142`). It affects only the login command — no other command has it, and the retired env override `ENTIRE_AUTH_BASE_URL` hard-fails every command if set (`base_url.go:38-43`).

# 4. Redirect behaviour, path by path

All OAuth calls go through `oauthhttp.HTTPClient` (`/Users/paul/go/pkg/mod/github.com/entireio/auth-go@v0.5.2/internal/oauthhttp/httpclient.go:18-23`), which sets **no `CheckRedirect`** → Go's default: follow up to 10 hops.

| Path | Redirect outcome |
|---|---|
| Discovery fetch | N/A — never happens |
| Authorize URL in browser | Fine. The browser follows the 302 itself; `openBrowser` (`login.go:511-553`) just shells out to `open`/`xdg-open`. The loopback `redirect_uri` is unaffected (`authcode.go:347`). |
| POST `/device_authorization`, POST `/oauth/token` (code exchange, device poll, refresh, STS) | **Depends on the status code.** |

Go's `redirectBehavior` (`/Users/paul/go/pkg/mod/golang.org/toolchain@v0.0.1-go1.26.5.darwin-arm64/src/net/http/client.go:507-538`):

- **301 / 302 / 303 on a POST → silently rewritten to GET with the body dropped.** The token endpoint would receive a bodyless GET and answer `invalid_request`/405. This is a real break for every one of the four POST paths.
- **307 / 308 → method and body preserved**, provided `GetBody != nil`:
  ```go
  case 307, 308:
      redirectMethod = reqMethod
      shouldRedirect = true
      includeBody = true
      if ireq.GetBody == nil &amp;&amp; ireq.outgoingLength() != 0 {
          shouldRedirect = false   // returns the 307 to the caller instead
      }
  ```
  Every POST here uses `strings.NewReader(form.Encode())` with `http.NewRequestWithContext` (`authcode.go:624`, `deviceflow.go:440`, `refresh/refresh.go:193`, `sts/sts.go:232`, `httputil/oauth.go:98-99`), and net/http populates `GetBody` automatically for `*strings.Reader`. So **307/308 would re-POST correctly.**

Two additional notes:

- The `Authorization: Basic` header in `httputil.PostOAuthToken` (`httputil/oauth.go:107`) survives a redirect from `auth.entire.io` → `us.auth.entire.io`, because Go only strips auth headers when the destination is *not* a subdomain of the origin (`client.go:1005-1030`, `shouldCopyHeaderOnRedirect` / `isDomainOrSubdomain`). `us.auth.entire.io` *is* a subdomain of `auth.entire.io`, so it is preserved. A sibling redirect (`auth.entire.io` → `eu.auth.entire.io` is still a subdomain — fine; but `entire.io` → `us.auth.entire.io` would also be fine, while `auth.entire.io` → `auth-eu.example` would drop it).
- `api.Client` (`/Users/paul/.claude/worktrees/cli/glittery-gliding-pretzel/cmd/entire/cli/api/client.go:63,72-80`) hard-**rejects** any cross-host redirect — so the clusters listing / control-plane / cell calls would error out rather than follow a regional redirect. Same for `resolveCellAPIBaseURL`'s `GET /api/v1/clusters` if it were served by a redirecting apex, though that one uses a plain client (`cell_data_api.go:348-359`).

**But the redirect question is largely moot for login**, because even a perfect 307 chain still ends with a token minted by the regional core. If that token carries `iss = https://us.auth.entire.io` while the CLI asked for `https://auth.entire.io`, `login.go:385` rejects the login outright with `iss mismatch`.

# 5. Can the default just change to `auth.entire.io`?

**Not unconditionally.** The one-line change works only if `auth.entire.io` behaves as a *real issuer* rather than a redirector. Concretely, the server side must satisfy all of:

1. **Serve `/authorize`, `/device_authorization`, `/oauth/token` at `auth.entire.io` itself** — either directly or via 307/308 (never 301/302/303, which strip the POST body). The CLI never reads a discovery doc, so it cannot learn a different endpoint host (`provider.go:12-18`, `oauthhttp/url.go:61-65`).
2. **Mint tokens with `iss = https://auth.entire.io`**, matching the dialled origin — otherwise `login.go:385` fails the login before anything is saved.
3. **Serve the whole refresh + RFC 8693 lifetime at `auth.entire.io`**, since `contexts.json.CoreURL` is `iss` (`contexts.go:64`) and every later refresh/exchange targets it (`refresh.go:124-127`).
4. **Advertise `https://auth.entire.io` in every cluster's `/.well-known/entire-cluster.json` and API host's `/.well-known/entire-api.json` `core_urls`**, or exact-match eligibility fails (`contexts.go:113`, `resolve.go:255-267`).
5. Decide the fate of the jurisdiction templates: `jurisdictionCoreURL` (`cell_data_api.go:519-534`) still builds `https://{jurisdiction}.auth.entire.io` for `entire auth token --jurisdiction` / cell routing. That regional form is not going away, so `auth.entire.io` and `us.auth.entire.io` must coexist as valid issuers.

3. GitHub calls back to `GET /api/auth/{provider}/callback` → `handleProviderGlobalCallback`, `/Users/paul/src/entirehq/entiredb/core/api/server.go:2439`. It resolves home jurisdiction and computes the geo guess — `server.go:2477-2489`:

## 3. Answer to the key question

**A CLI starting at `https://auth.entire.io` fails at step one.** `GET https://auth.entire.io/.well-known/openid-configuration` has no route in `registerGlobalRoutes` (`server.go:1365-1393`) → 404. Same for `/authorize`, `/oauth/token`, `/revoke`, `/userinfo`, `/.well-known/jwks.json`, `/device_authorization`, `/cli/login`.

The auto-select is not even "browser `/authorize` only" — it is a *separate, RP-gated jurisdiction-discovery endpoint*, usable only by a host on `JURISDICTION_HANDOFF_RETURN_TO_HOSTS`. A loopback `http://127.0.0.1:PORT/callback` can never satisfy `validateReturnTo` (`jurisdiction_handoff.go:19-42`).

**What does work today, against a regional host:** full loopback PKCE-S256 for the `entire-cli` public client. `code_challenge_method=S256` (`core/authn/oidcop/provider.go:99` `CodeMethodS256: true`), refresh_token grant (`provider.go:100`), RFC 8693 token-exchange auto-advertised (`provider.go:101-105`), pinned by `core/api/oauth_metadata_test.go:67-72`. The token endpoint's origin guard explicitly lets cookie-less clients through — `/Users/paul/src/entirehq/entiredb/core/api/oauth_origin_guard.go:142-150`:
&gt; A request carrying neither cookie is a plain OAuth exchange — its credential is the auth code + PKCE […] so its origin is irrelevant.

And a foreign-homed user logging in at a *wrong* regional host is **no longer redirected home** — they get a full local session there: `/Users/paul/src/entirehq/entiredb/core/api/foreign_juris_login_test.go:19-33` asserts `Location == /authorize/callback?id=…` and explicitly `assert.False(strings.HasPrefix(..., "https://eu.auth.example/authorize"))`; comment at `core/api/server.go:2569-2576`. So today's `--server https://us.auth.entire.io` default yields a **US-issued token for an EU-homed user**, and `cmd/entire-core/cli/cross_region_hint.go:32-57` exists precisely because such a token is rejected by other regions ("it only accepts tokens minted by its own region").

## 5. How region is determined

Two inputs only, both in `handleProviderGlobalCallback`:

1. **Existing user → recorded home jurisdiction**, by GitHub *provider user ID* looked up in the global identity store: `core/authn/router.go:41-58` (`Router.HandleCallback` → `identity.ResolveHandleByProviderID`). Requires the user to have just completed a zero-scope GitHub OAuth round-trip in a **browser**. Not email domain, not IP, not a bearer token.
2. **New user (no home) → Cloudflare geo IP**: `core/authn/geo.go:120-152` `GeoSuggestJurisdiction(country, continent, live)`. Resolution order (geo.go:107-118): country code that doubles as a live jurisdiction slug (`IN`→`in`, `AU`→`au`) → continent via `continentToJurisdiction` (geo.go:23-30: NA/SA→us, EU/AF→eu, AS→in, OC→au), with the country-derived continent used whenever the `cf-ipcontinent` header is absent *or* unmappable → `geoFallbackJurisdiction = "us"` (geo.go:101). Headers are trusted because they arrive via Cloudflare→NLB→Envoy (geo.go:11-16). Returns `""` only if even `us` isn't live → auth error page.

A `home_region` cookie exists (`core/authn/home_jurisdiction_cookie.go`, set at `server.go:2482-2486`) but it is a browser cookie and only *written* on this path — the callback deliberately does not short-circuit on it (`server.go:2459-2463` just counts `CookieAutoRedirectSkipped`).

**No-account user:** geo guess only; the account is *not* created at global (`5a2a57d4d`: *"handleRegionPickerSubmit no longer creates the account"* / *"The picker's job is now: verify signed state, validate region, hand back to the BFF […] No writes"*). The regional core creates it on its own `/authorize` callback, waitlist-gated (`server.go:2966-2968`).

## The cookie short-circuit decision: **not taken**

`handleProviderGlobalCallback`'s no-op at `server.go:2496-2500` only *counts* the skip because by then the GitHub hop already happened — the real decision is at flow start, and the reason it isn't taken is stated at `docs/superpowers/specs/2026-04-13-topology-flip-design.md:154`:

&gt; **The cookie is not an auto-routing authority.** Global always performs zero-scope OAuth to identify the user before routing... This is the only safe model on shared browsers — a stale `.partial.to` cookie set by a previous user must never be enough to route a brand-new user's signup into the wrong jurisdiction.

It is domain-compatible (`COOKIE_DOMAIN` is shared global↔regional, `serve_mode_global.go:139`), so the short-circuit would *work* — it's just wrong. Routing an unknown user by a previous user's cookie places their account and PII in the wrong jurisdiction, which is a data-residency decision, not a UX one. The cost of declining is one GitHub hop that GitHub auto-approves. I emit the same `CookieAutoRedirectSkipped` metric from the new handler (`global_oidc_dispatch.go:98`) so the metric keeps covering every entry point, and `TestHandleGlobalAuthorize_DoesNotShortCircuitOnHomeRegionCookie` mints a genuinely valid cookie with the server's own secret so it fails for the right reason if anyone adds the shortcut.

## Risks / what only the server deploy can confirm

1. **The replace directive.** Blocks merge. Release auth-go, bump the CLI's require, drop the replace.
2. **`auth-go`'s `mise run lint` fails on govulncheck** — `GO-2026-5856` (crypto/tls, fixed in go1.26.5; auth-go pins `go 1.26.4` in `go.mod`/`mise.toml`). **Pre-existing and unrelated to my change**; golangci-lint itself is clean. Needs a separate toolchain bump.
3. **Device-flow region discovery rests on `resp.Request.URL`**, i.e. on the apex actually 307-ing (307/308 preserve the POST body; a 302 would have Go re-issue as GET and break the flow). Only the real deploy proves the redirect code. If the server instead returns the region in the JSON body, `ReadAndDecodeJSON(…, strict=true)` will **reject the whole response** — worth a heads-up to whoever builds the apex.
4. **Browser flow depends on the region emitting RFC 9207 `iss`** on the loopback redirect. Verified present in entiredb (`core/api/server.go:1292-1296`, `core/api/authorize_callback.go:9-46`) but not exercised end-to-end against a live apex. If `iss` were absent the CLI would exchange at the apex and get a 404 — noisy, not silent.
5. **The subdomain rule assumes regions are always strictly below the apex.** If a jurisdiction ever lands on a host that isn't (e.g. `auth.entire.eu`), `issMatches` rejects it and login fails closed. Correct default, but it's a coupling worth knowing about.</result>
