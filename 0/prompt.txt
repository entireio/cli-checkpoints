EnsurePrivateDir’s doc says it “only clears group and other bits” (preserving stricter owner-only modes), but the implementation always chmods the directory to 0700. This can unintentionally broaden owner permissions (e.g., 0555 becomes 0700) and doesn’t match the stated behavior; consider tightening by masking off group/other bits while preserving the existing owner bits.

EnsurePrivateDir uses os.Stat/os.Chmod, both of which follow symlinks. If the config/cache directory path (e.g. ~/.config/entire, or filepath.Dir(f.path) for the token store) is ever a symlink to another directory — intentionally by the user or planted by another local user/process before first run — this will silently chmod 0700 the target directory rather than refusing to operate through the link. That's the opposite of this codebase's established stance elsewhere (.entire dir validation, readConfined) of never writing/mutating through a symlink for security-sensitive paths. Worse, since versioncheck.ensureGlobalConfigDir calls this on nearly every CLI invocation via PersistentPostRun, a symlink target not owned by the current user would make os.Chmod fail with EPERM, hard-failing every entire command until the symlink is removed. Consider os.Lstat first and skip/error out if the path is a symlink instead of chmod'ing through it.
