## 2. The trailer-driven join, and why a ref with no referencing commit is skipped

- The join that links checkpoint → commit → session is **`repo_checkpoint_commits`**, written only by:
  - `processCheckpointPayload` → `db.checkpoints.upsertSyncCommitBatch` — `git-source/checkpoint-processing.ts:235-242`, using `commit.sha` of the **user commit that carried the trailer**.
  - The reconcile re-derivation — `git-source/reconcile.ts:557-589`.
- Discovery is 100% commit-message text: `extractCheckpointIds` matches `/^Entire-Checkpoint:\s*(\S+)/gm` — `github.ts:2208-2216`.
- **Skip mechanics for a ref with no referencing commit:**
  - `processCheckpointPayload`: `discovered = commits.flatMap(extractCheckpointIds(commit.message))`; if `discovered.length === 0` it returns `{status:"ok", checkpointsDiscovered:0}` immediately — `checkpoint-processing.ts:176-181`. No trailer ⇒ nothing enqueued, nothing joined.
  - The session-branch path never even fires for a `refs/entire/checkpoints/&lt;shard&gt;/&lt;id&gt;` push: `getCheckpointSourceRefForPush` returns `null` for anything other than `refs/heads/entire/checkpoints/v1` — `checkpoint-storage.ts:7-9` — so `processSessionsPushEvent` early-returns at `processing.ts:1785-1788`.
  - Even on the v1 branch, session-side discovery keys off the checkpoint-branch commit **subject** `Checkpoint: &lt;id&gt;` (`processing.ts:1925-1942`); it produces `repo_checkpoints` but **never a junction row** (hydrator has no commit link).

So an imported checkpoint (no trailer, ref not `refs/heads/entire/checkpoints/v1`) hits **neither** discovery path → no `repo_checkpoints`, no `repo_checkpoint_commits`, no `repo_sessions`.

## 3. DB tables/models and columns a commit_sha-anchored imported checkpoint must populate

Schema: `api/src/types/database.ts`; Kysely types `api/src/lib/db/db-types.ts`; access layer `api/src/lib/planetscale/{checkpoints,sessions}.ts`.

- **`repo_checkpoints`** (`database.ts:191-300`) — metadata row, unique `(repo_id, checkpoint_id)`. Columns: `prompt, sessions(JSON), session_ids(JSON), session_count, steps, created_at, input_tokens/output_tokens/…, payload_hydration_state, storage_version`. **No `commit_sha` column** — the join lives in the junction table. Required for session materialisation and recap token/agent aggregation.
- **`repo_checkpoint_commits`** (`database.ts:301-366`) — the junction. `(repo_id, checkpoint_id, branch, commit_sha)`; `commit_sha` is **nullable**, plus denormalized `commit_author_*`, `commit_date`, `commit_message`. **This is the missing edge.** Nearly every read query drives *from* this table (e.g. `checkpoints.ts:2019`, `2278`, `sessions.ts:278`).
- **`repo_commits`** — canonical commit, `commit_author_github_id`, `commit_date`, `commit_message`. Required because `/me/recap` INNER JOINs it and filters `commit_author_github_id = &lt;user&gt;` (see below).
- **`repo_branch_commits`** — branch membership for `commit_sha`. Required for the repo `/:org/:repo/sessions` branch filter and `/commits`.
- **`repo_sessions`** — materialised aggregate (write path `sessions.ts:362-461`). Columns include `first_commit_author_username`, `last_commit_message`, `started_at`, `last_activity_at`, tokens, attribution. No `commit_sha`, **no user-id column** — cross-user attribution is via `first_commit_author_username` / the joined commit author.

**Read requirements per surface:**
- **`/me/recap`** — `recap.ts:251` → `db.checkpoints.getByUser` → `getCheckpointsByUser` (`checkpoints.ts:1982`). Query at **`checkpoints.ts:2018-2030`**: `repo_commits FORCE INDEX ... ## 4. Does ingestion read metadata.json / 0/metadata.json, and is `commit_sha` parsed or dropped?

Yes, it reads both — and **`commit_sha` is currently parsed-then-dropped** (tolerated but ignored):
- `fetchSessionDataBatch` (`github.ts:809`) GraphQL-fetches root `metadata.json` and per-session `0/metadata.json`,`1/…` (`github.ts:860-864`).
- Root parsed as `CheckpointSummary`: `JSON.parse(rootMetadata.text) as CheckpointSummary` (`github.ts:901-910`). Session parsed by `parseSessionMetadata` (`github.ts:644-683`), a hand-mapped pick of known `CommittedMetadata` fields.
- The type defs (`types.ts:237-247` `CheckpointSummary`, `types.ts:267-288` `CommittedMetadata`) have **no `commit_sha` and no `kind`** field. Because parsing is a `JSON.parse ... as` cast plus explicit field-mapping, an incoming `commit_sha`/`kind` survives at runtime in the parsed object but is **never propagated** into `SessionData` (`github.ts:591-624`) or `CheckpointData` (`buildCheckpointDataFromSessionBatch`, `checkpoint-processing.ts:41-71`). It is silently discarded — no TS error, no persistence.

## The specific gap

An imported checkpoint has **no `Entire-Checkpoint:` trailer** and its ref is not `refs/heads/entire/checkpoints/v1`. Therefore:
1. `getCheckpointSourceRefForPush` rejects the ref → `processSessionsPushEvent` returns (no `repo_checkpoints` write). — `checkpoint-storage.ts:7-9`, `processing.ts:1785-1788`.
2. No trailer → `extractCheckpointIds` returns `[]` → `processCheckpointPayload` early-returns and reconcile's DAG scan finds nothing (no `repo_checkpoint_commits` write). — `checkpoint-processing.ts:176-181`, `reconcile.ts:557-560`, `github.ts:2208`.
3. The `commit_sha` join key the CLI writes into metadata is parsed but discarded. — `github.ts:901-910`, `checkpoint-processing.ts:41-71`, absent from `types.ts:237/267`.

Result: zero rows in `repo_checkpoints` / `repo_checkpoint_commits` / `repo_sessions` → invisible in `/me/recap`, `/me/sessions`, and repo pages.

## Shortest-path insertion points for a commit_sha join

1. **Recognize the imported ref** so a push triggers ingestion: extend `getCheckpointSourceRefForPush` (`checkpoint-storage.ts:7`) — or add a dedicated imported-ref branch in `processSessionsPushEvent` (`processing.ts:1785`) — to accept `refs/entire/checkpoints/*`. Discovery for these must come from the pushed **ref/tree** (list checkpoint IDs from the ref path or its tree), not from a `Checkpoint:`/`Entire-Checkpoint` commit subject, since imported checkpoints have none.
