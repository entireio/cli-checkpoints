### 1. Is `oauthhttp.HTTPClient` the right depth? — Yes, and it is provably a chokepoint

`auth-go/internal/oauthhttp/httpclient.go:33`

Two structural facts make this the deepest correct point, and both should be stated in the PR because they are what make the placement defensible rather than merely convenient:

**A `CheckRedirect` policy cannot live below an `http.Client`.** A `RoundTripper` never follows a redirect — it returns the 3xx. So "a RoundTripper-level guard" is not a deeper altitude for *this* mechanism; it does not exist. The only construct that can refuse a redirect is the `http.Client`, and `oauthhttp.HTTPClient` is the sole place in the library that builds one.

**Nothing in auth-go's public API lets a caller inject an `*http.Client`.** Every flow exposes `Transport http.RoundTripper` and builds its own client (`sts/sts.go:168`, `deviceflow/deviceflow.go:113`, `authcode/authcode.go:138`, `refresh/refresh.go:54`), each documenting the TLS-bypass rationale. That pre-existing decision is what turns `HTTPClient` from "a helper most callers use" into a boundary a caller cannot route around. The fix leans on it without saying so; it is worth one sentence, because a future `Client.HTTPClient` field would silently un-do this change.

Verified: exactly four `.Do(` sites in the library (`sts:259`, `refresh:210`, `authcode:708`, `deviceflow:525`), all fed by `oauthhttp`.

**On `crossjuris`'s direct `Base.RoundTrip` calls — not a gap.** Both were checked:

- `crossjuris/crossjuris.go:353` (federation manifest) — GET, no body, no credential. A 3xx here is not followed at all (bare RoundTripper), fails JSON parse, returns nil hosts, and the trust gate fails closed. Correct by construction.
- `crossjuris/crossjuris.go:181` (the caller's request and its 421 replay) — the credential is the `Authorization` header, which `crossjuris` re-stamps per `RoundTrip` call. On a cross-host 307 `net/http` strips the header before the next `RoundTrip`, so `originalAuth` is empty on that hop, `lookupToken(attackerOrigin)` misses, and no header is set. No credential leaves.
- The credential-bearing request `crossjuris` does make — the RFC 8693 exchange at `crossjuris/exchange.go:161` — goes through `sts.Client`, therefore through `oauthhttp.HTTPClient`. Guarded.

So: **every request in auth-go that carries a credential in its body passes through the guarded constructor, and the two that bypass it carry no credential and follow no redirects.** No finding.

**Finding 1.1 (low, reuse):** `httpclient.go:104` compares hosts with `strings.EqualFold(req.URL.Host, via[0].URL.Host)`, while `oauthhttp/origin.go:20` already owns `NormalizeOriginURL`, which lower-cases and drops default ports. The hand-rolled comparison refuses `https://core.example` → `https://core.example:443` as a "different endpoint". The doc calls port-sensitivity deliberate, which is fine as policy — but the deeper move is to express it *through* the package's existing origin primitive (compare normalized hosts, then decide about ports explicitly) rather than beside it. Two host-comparison idioms in one 80-line package is how they drift.

### 2. The deviceflow exemption — right shape, resting on an unenforced invariant

`auth-go/internal/oauthhttp/httpclient.go:64`, `deviceflow/deviceflow.go:186`

**Verdict: the two-constructor shape is right, and I'd reject the "property of the request" alternative.** The properties that matter:

- The default is safe. A fifth flow that writes `oauthhttp.HTTPClient(c.Transport)` — the obvious thing — is guarded. Getting it wrong requires typing a 41-character name whose doc says "Do NOT reach for this anywhere else".
- The choice is already per-request, not per-client: `httpClient()` allocates a fresh client per call, and this diff moved the client to a `postForm` parameter (`deviceflow.go:508`), so the two call sites each *state* their policy at the line where the body is built. That is the per-request expression the alternative was after; the second constructor is just its spelling.
- I considered deriving the policy from the body — refuse the redirect only when the form carries `subject_token`/`refresh_token`/`code`/`code_verifier`/`device_code`/`client_secret`. It is mechanically possible via `req.GetBody` inside `CheckRedirect`, and it is the most "general" answer. **Reject it:** it fails open on any credential field nobody enumerated, which inverts the safe default. A safe default plus a loud opt-out beats content sniffing.

**Finding 2.1 (medium — the actual altitude issue):** The exemption's stated justification is "its body is `client_id` plus `scope` — neither a secret". That is true today *because the device-auth body is a closed set the library builds itself* (`deviceflow.go:293-297`, no caller extension point) — unlike `sts.ExchangeRequest.Extra` (`sts/sts.go:91`), which is exactly that extension point on the sibling flow. The invariant the exemption rests on is therefore structural, but it is asserted only in prose. The day `deviceflow.Client` grows an `Extra url.Values` for parity with `sts` — a plausible, innocuous-looking change — the exemption silently becomes a credential leak, with no red test. **Deeper:** pin it. A three-line test asserting the device-auth form's key set is exactly `{client_id, scope}` converts a comment into a tripwire, at the same altitude as the exemption itself.

**Finding 2.2 (medium — inconsistent depth inside one module):** `HTTPClientFollowingCrossHostRedirects` follows a *server-chosen* cross-host target with no trust gate of any kind, and that target then picks the `verification_uri` shown to the user and the origin later polled with the device code. `validateVerificationURI` (`deviceflow.go:369`) is shape-only — https, no userinfo, no control chars, ASCII host — so an attacker-chosen origin's phishing URI passes. Meanwhile the *same module*, for the structurally identical decision, gates: `crossjuris` will not follow a `home_core_url` unless its host appears in the responding core's federation manifest (`crossjuris.go:275`), and the README advertises "Server-supplied redirect targets are gated" as a library property. Device flow is now the one place that claim is false, and the obligation is exported to the caller as documentation ("validate `DeviceCode.ResponseOrigin` before assigning it to `TokenBaseURL`") — i.e. *after* the hop, after the response was parsed.

**Deeper alternative:** parameterize instead of exempting. `deviceflow.Client.AllowRedirectTo func(host string) bool`, nil meaning refuse, wired into a `CheckRedirect` that consults it. The exemption constructor disappears; the trust decision moves from post-hoc advice to a pre-hop gate; and a fifth flow needing regional routing gets the mechanism rather than a second copy of the opt-out. Worth noting this is not hypothetical rigor: the CLI *already implements the predicate* — `adoptIssuer`/`issMatches` (`cli/login.go:625`, `:563`) enforces an https-only, same-port, strict-subdomain delegation rule on `ResponseOrigin`. Today that runs one layer too late. Handing it to auth-go would make it run at the hop.

(To be clear: this preserves the status quo rather than regressing it — device auth was never guarded. The finding is that the fix drew the line at "credential in body" and left the sibling trust question at a shallower depth than the module's own neighbouring code.)
