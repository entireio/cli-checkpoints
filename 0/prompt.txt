## Verdict

The core of this change is at the right altitude. Collapsing two ad-hoc confirmations into one mode decision, and making `-y` mean "yes to everything", fixes the actual root cause — consent was previously scattered across two functions in two files, each deciding independently whether it was allowed to act. `resolveRunnerSetupMode` is the right shape and the right size. The extraction of `runTuning` / `classifyTuneProposals` / `applyTunedRunners` out of the old `applyTuneWithAgent` is also a real depth improvement, not a shuffle: the accept/reject rules are now testable without a provider call, which is why the new test file can pin them.

Three findings, one of which I'd change now.

---

### 1. SHOULD CHANGE NOW — the mode's write authority is asked three times, in three spellings, and its zero value authorizes the most invasive path

- **file**: `cmd/entire/cli/runner_setup.go` lines 143, 165–168, 196–200; `cmd/entire/cli/runner_init.go` lines 22–27
- **summary**: "may this invocation write?" is spelled `mode != setupModeDryRun`, then `mode == setupModeDryRun`, then implicitly as "everything that reached the tail applies" — and an unknown mode passes all three as *write*.
- **concrete cost**: `runnerSetupMode` is a string with no valid zero value. Trace `mode == ""` through `runRunnerSetup`: line 143 `!= setupModeDryRun` → scaffolds; 154/183/196 all miss → line 200 `applyTunedRunners` → writes the runner files. The zero value of the consent token is the full destructive action. That is the hole the `ensureRunnersPresent` doc comment ("Callers must not reach here without it.") is currently plugging with prose, and it is also why a fifth mode has to be remembered at three sites, two of them phrased negatively.
- **deeper change**: put the authority on the type and gate at the writing layer, not the call site.
  1. `func (m runnerSetupMode) writesRunnerFiles() bool` as a `switch m` with `default: return false`. This repo already has the precedent — `session.Phase` is a string enum with predicate methods (`IsActive()`) and a fail-safe normalizer (`PhaseFromString`, `session/phase.go:29`) — and `exhaustive` is enabled in `.golangci.yaml:25` with no `default-signifies-exhaustive`, so a `switch` over the mode gets *machine* enforcement that a fifth mode is handled. The current `if` chain is invisible to that linter.
  2. Pass the mode into `ensureRunnersPresent(w, repoRoot, mode)` and let it return `nil, nil` when `!mode.writesRunnerFiles()`. That turns the comment into code, and it matches the repo's own dry-run convention: `agentimport.Run` takes `Options{DryRun: ...}` (`agentimport/agentimport.go:107`, honored at `:262`/`:296`) and `checkpoint.MigrateBranchToRefs(ctx, repo, dryRun)` takes it as a parameter — the writer honors it; the command does not gate the call.
  3. Make the tail a positive `switch mode { case setupModeDryRun: preview; case setupModeAdapt: apply; default: return fmt.Errorf("unhandled setup mode %q", mode) }` instead of `if dryRun { preview }; return apply`.
- **on the phantom-type idea from the brief**: I'd argue against it. `ensureRunnersPresent` has exactly one caller and is package-private (verified — the only non-test reference is `runner_setup.go:144`). A `consent` token type for a single-caller private helper is ceremony that buys nothing the fail-closed predicate doesn't. The mode value *is* the consent token; the defect is only that it has no invalid state.

### 2. SHOULD CHANGE NOW — `previewTunedRunners(..., haveRunners)` is the loader swap leaking upward, and the two booleans agree only by coincidence

### 3. NOTE — `runner setup` conflates two operations; two subcommands would be the deeper fix, but the current shape is defensible

- **file**: `cmd/entire/cli/runner_setup.go:62–118`, `cmd/entire/cli/runner_group.go`
- The evidence that the conflation costs something is concrete, not aesthetic:
  - The file layout has *already* found the seam the command surface hides: `runner_init.go` is the scaffold, `runner_prompt.go`/`runner_apply.go` are the tailoring. CLAUDE.md's command-layout section names exactly this convention (`&lt;noun&gt;_&lt;verb&gt;.go`, noun groups owning verbs), and `runner` is a group with one subcommand — adding a second is cheap and idiomatic here.
  - `--defaults-only` needs no provider, no network, no `--sources`, no `--limit`, no `--debug-dir`, yet inherits all of them *and is validated against them*: `runRunnerSetup` rejects `--limit 0` (line 121) and a bad `--sources` (line 124) **before** the mode is resolved at line 135. So `runner setup --defaults-only --limit 0` fails for a reason with nothing to do with what it was asked to do.
  - `chooseRunnerSetupAction` offers only 2 of the 4 modes. The picker's own question is "generic defaults, or tailored?" — i.e. the interactive path already treats this as *init vs tune*, and `--print-prompt`/`--dry-run` are flag-only variants of the tune half. That is the two-subcommand decomposition, discovered by the UI and then flattened back into one flag namespace (hence the `MarkFlagsMutuallyExclusive` at line 115 and the four-flag error string at line 220).
  - Under `runner init` + `runner tune`, the four modes become one command plus one verb with two output flags (`--dry-run`, `--print-prompt`), and both the exclusion group and the "which flag do I pass" message disappear.
- **Why the current shape is still defensible**: the modes form a genuine prefix chain (defaults ⊂ print-prompt ⊂ {dry-run, adapt}) that shares nearly all machinery, `setup` is the better onboarding affordance to type once, and the group is `Hidden`/experimental so the surface is cheap to revise later. **You asked for the four-mode shape, so I am not recommending the split.**
- **Cheap middle ground if you keep four modes**: move the `limit`/`sources` validation below the mode resolution so the offline mode isn't rejected for tailoring-only inputs. Three lines, and it removes the sharpest edge of the conflation.
