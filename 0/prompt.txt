## Verdict

The **diagnosis** in both halves of this PR is right, and the dead-pin→`GitHooksOutdated` half is at the right altitude. The **scope half is enforced one layer too high**: the gate lives in the merged loader, but both of `absolute_git_hook_path`'s real consumers — the writer and the hook installer — reach around the merged loader. I reproduced two live bypasses that defeat the PR's stated purpose.

---

### 1. The write redirect doesn't remove the project write — the flag still commits the key (reproduced)

`cmd/entire/cli/setup.go:309-320`. The comment says "Deliberately not written into s", and line 316 writes it into `s`. Line 320 then marshals the whole struct to the target scope, and the default target is the project file.

```
$ entire configure --absolute-git-hook-path     # repo has .entire/settings.json
  absolute_git_hook_path written to .entire/settings.local.json (it describes this machine)
✓ Settings updated (.entire/settings.json)

.entire/settings.json      → {"enabled": true, "absolute_git_hook_path": true}   ← committed
.entire/settings.local.json → {"absolute_git_hook_path": true}
```

Same at `setup.go:1300-1305`→`1342` (`runEnableInteractive`, and that struct is the *merged* view) and `setup.go:1982-1987`→`2014` (`setupAgentHooksNonInteractive`, which prints no notice at all). Reproduced there too:

```
$ entire enable --agent claude-code --absolute-git-hook-path --project
.entire/settings.json → {"enabled": true, "absolute_git_hook_path": true}
```

Consequence: one `configure` + one commit and every cloner's `entire doctor` prints `Git hooks: absolute_git_hook_path ignored` — a warning our own writer created. Verified end to end.

The codebase already declares this invariant, and `absolute_git_hook_path` is its canonical example: `setEnabledFlag`'s doc (`setup.go:1514-1532`) names the field in the list of local-only overrides that must not leak into the committed file, and `setup_test.go` has ~8 tests asserting exactly that (`:596` "local-only absolute_git_hook_path override leaked into project settings", `:935`, `:972`, `:1019`). All of them seed the value in the *local* file, so none covers the flag path. The one test that does — `TestConfigureCmd_AbsoluteGitHookPathFlag_PersistsAndReinstallsHook` (`setup_test.go:3673`) — asserts only against the merged view, so it passes either way.

**Deeper fix, in scope now:** make the *writer* own the rule instead of each call site. `settings.saveToFile` (`settings/settings.go:1657`) is the single choke point; zero local-only fields when the target is `EntireSettingsFile`. Then all three `if opts.AbsoluteGitHookPath` blocks lose their comment and their hazard, and `setAbsoluteGitHookPathLocal` remains just the local write. That is the general "this field always writes local" notion item 4 asks about, and it costs about as much as the three bespoke comments do.

---

### 2. The gate is bypassed for the decision it exists to control (reproduced)

`updateGlobalSettings` decides pinning from an **ungated** per-file load: `settings.LoadFromFile(targetFileAbs)` (`setup.go:271`) feeds `InstallGitHook(ctx, true, s.AbsoluteGitHookPath)` (`setup.go:325`). `LoadFromFile` never runs `enforceAbsoluteGitHookPathScope`.

Reproduced in a clone whose committed `settings.json` pins, with **no local file at all**:

```
$ entire configure --force            # note: --absolute-git-hook-path NOT passed
.git/hooks/post-commit:
  if [ -x '/…/scratchpad/entire' ]; then '/…/scratchpad/entire' hooks git post-commit …
```

So "a repository could impose path-pinning on everyone who cloned" is still reachable — via `--force` instead of passively. The other three installers are clean: `EnsureSetup`→`hookSettingsFromConfig` (`strategy/hooks.go:705`), `runEnableInteractive`, and `setupAgentHooksNonInteractive:2026` all read the merged (gated) view.

**Deeper fix, in scope now:** `updateGlobalSettings`'s `InstallGitHook` argument must come from the merged view, exactly as `setup.go:2026-2031` already does and documents. One line. More generally: `settings.LoadFromFile` is exported and ungated by design (status uses it to *display* a file), so any gated field read through it is a latent bypass — worth a sentence on `LoadFromFile`'s doc saying it is display-only.

---

### 3. Parsing what we generate: no test couples parser to generator, and it already round-trips wrong

`entireHookPinnedPath` (`strategy/hooks.go:321`) + `shellUnquote` (`:345`) reverse `gitHookCommandAvailableTest`/`shellQuote`. Two verified problems:

**No end-to-end coupling exists.** `grep 'InstallGitHook('` across all tests: **every** call passes `absolutePath=false`. Nothing anywhere installs a pinned hook and parses it back. The new tests hand-write the shape ("The exact shape gitHookCommand emits", `hooks_test.go:639`), matching the pre-existing `writeCurrentManagedHooks` (`:855`) — but that helper only fed `strings.Contains` checks, which survive generator changes. A structural parser does not. Change `[ -x ` to `test -x` and the parser silently returns `""`, dead pins go undetected, and all four new tests stay green.

**The parse is already wrong on one `shellQuote` case.** `strings.Index(rest, " ]")` finds the first `" ]"`, which can be inside the path. Verified by running the real functions:

```
input="/Users/a ]b/entire"  quoted='/Users/a ]b/entire'  parsed="'/Users/a"   ← wrong
input="/Users/John O'Brien/bin/entire"                    parsed=…            ← ok
```

A user with `]` in a path component gets a permanent false `Git hooks: OUT OF DATE` plus a futile reinstall attempt every turn-start (`writeHookFile` is content-idempotent, so it never repairs and never errors). The test suite specifically brags about covering the apostrophe case and misses the delimiter case.

**Deeper shapes, and what's feasible:**
- *Compare against a regenerated expectation* (the mechanism `writeHookFile:552` already uses) — **not feasible.** The state check would report Outdated whenever `os.Executable()` differs from a *working* pin, flipping hooks on every dev-build invocation. Rightly rejected.
- *Machine-readable marker line* — feasible and clean. `buildHookSpecs` already emits a `# &lt;marker&gt;` header; adding `# entire-pinned-path: &lt;path&gt;` (raw, no shell quoting) makes the reader a `strings.Cut`. Cost: hooks written before the marker existed can't be checked until reinstalled, so you either keep the parser as a transition fallback (coupling survives one release) or accept the gap. **Follow-up.**
- *In scope now, and cheaper than either:* one test that calls `InstallGitHook(ctx, true, true)` and asserts `entireHookPinnedPath` on the generated file equals the resolved exe. That single test converts every future generator change into a red build, which is the actual protection wanted. Plus tighten the delimiter to the last `" ]"` before `"; then"`.

Minor, same function: for a healthy pinned set the loop stats the same path 5 times (once per hook, no short-circuit) on the turn-start hot path. Trivial to dedupe.

### 4. `GitHooksOutdated` is the right axis; its own doc no longer is

I traced every consumer. Verdict: **overloading is fine, and the churn worry doesn't materialize.**

- `strategy/common.go:110` (`EnsureSetup`): dead pin → reinstall. `hookSettingsFromConfig` reads the *merged* view, so a project-only pin unpins the hooks and a local pin re-pins to the running binary. Self-heals in **one** turn and stays Current. No loop, because `EnsureSetup` runs from *agent* hooks (`lifecycle.go:574`), which are never pinned (no `os.Executable` in `cmd/entire/cli/agent/`), so the running binary is always a live PATH resolution. One reinstall per `entire` upgrade under a version-manager shim — which is the intended repair, not churn.
- `setup.go:2447` (`runUninstall`): uses `AnyGitHookInstalled` (`!= Absent`). A dead pin was `Current` before and is `Outdated` now — both non-Absent. **No change.**
- `CheckGitHookStateInDir`/`IsGitHookInstalledInDir`: test-only consumers.
- The one flip-flop case: two environments resolving `entire` to different absolute paths in one shared worktree (host + devcontainer bind mount) will re-pin against each other every turn. Each side is at least correct for itself, versus stale-and-broken before. Acceptable; the honest mitigation is "don't pin a shared worktree", which nothing says (see §5).

Two loose ends worth fixing while here:
- `strategy/hooks.go:154-155` — `GitHooksOutdated`'s doc still reads "a shape we no longer write. Today that means running Entire from the working tree". A dead pin is a shape we **do** write; only its environment changed. The enum doc is now the only place stating the old, narrower meaning. **In scope now** — it's the documentation of the very axis being widened.
- `doctor.go:538-546` prints the rejection *before* the switch, so it fires even when hooks are `Absent` and `!settings.IsSetUpAny(ctx)` — the one case the surrounding code deliberately stays silent about ("treating this as actionable would let `doctor --force` install hooks into a repo that never opted in"). Small noise inconsistency with its own neighbor.

### 5. Nothing documents that the setting is local-only

Verified: no README mention (`README.md:366,380` name the flag, not the rule), no `docs/` page, no CLAUDE.md line, and the flag help is unchanged at `setup.go:798` and `:965` — still "Embed full binary path in git hooks (for GUI git clients that don't source shell profiles)".

This is a sharp contrast with the sibling gate the change explicitly models itself on: `docs/security-and-privacy.md` gives `openai_privacy_filter.command` a dedicated **"Why `command` is local-only"** section plus inline notes at `:74` and `:131` ("**Only read from `.entire/settings.local.json`**"). |---|---|---|
| bare `entire status` | – | **no** |
| `status --detailed` | yes | yes |

### 6. Item 1 — the gate depth is right; what's accumulating is the *reporting*, not the gates

Two field-level gates is not a table's worth, and the two share almost nothing: different verification depth (deep index+HEAD vs. none), different failure policy (fail-closed vs. positional drop), different consequence (code execution vs. a fragile hook). A declarative registry now would be premature, and there's no existing seam to hang it on — `mergeScalarFields` (`settings/settings.go:1055`) is hand-written per field too. **Don't build it.**

What a fourth field would actually cost today is on the reporting side, and that's already three-of-a-kind: `LocalLayerRejection()`, `OPFSettings.CommandRejection()`, `AbsoluteGitHookPathRejection()` — each with its own unexported field, its own accessor, and its own hand-written print site in a different command, with the coverage table above showing they've already drifted apart. A small shared shape (`[]Rejection{Key, Reason, Remediation}` on `EntireSettings`, one printer used by status/doctor/`warnUser`) would collapse that and close the reach gap in one move. **Follow-up, but the right one** — that, not a scope table, is where the fourth field's cost lands.

One structural note on the new gate itself: it is purely **positional** — it verifies nothing, relying entirely on being called at `settings.go:600` before the local merge, with a second positional patch at `:637` clearing the rejection after. One field's policy now sits in three places in `loadMergedSettings`. It happens to be correct today (`applyClonePreferences` at `:607` doesn't touch this field, and clone preferences are clone-local anyway), but a reader can't tell that from the function alone. Cheap hardening, same style as the sibling: give it the raw local bytes and decide from key presence (`localSetsOPFCommand`/`rawHasKey` already exist), which makes it order-independent and lets the `:637` special case go away. **Follow-up.**
