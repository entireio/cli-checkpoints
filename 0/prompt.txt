### 1. Two unreconciled notions of "which file and which lines" — the biggest altitude problem
`cmd/entire/cli/trail_review_cmd.go:901` (`parseTrailReviewPatchTarget`) vs `:1020` (`buildTrailReviewCommentLocation`)

The command already takes `--file/--line/--start-line/--end-line` and turns them into the finding's location. The fix derives a *separate* file + line span from the patch and never compares the two. Concretely, today:

- `--patch` with no `--file`: the CLI has just parsed the exact path and hunk span out of the patch, then throws it away and sends `granularity: whole_change` (`:1043-1045`). An agent that passes only a patch gets a locationless finding — no `file:line` in the dashboard, nothing to group or navigate by — while the suggested change knows precisely where it goes.
- `--file a.go` with a patch touching `b.go`: accepted silently; finding points one place, its fix another.
- `--start-line 88 --end-line 91` disagreeing with the hunk range: both shipped, contradicting each other.

**Deeper fix:** one resolution step producing a single `(path, start, end)` that feeds *both* the location and the anchor — default the location from the patch when `--file` is absent, and reject (or let the flags win and validate the patch against them) when they disagree. That's the difference between "the command knows where the finding is" and "the command has two guesses."

**Cost of leaving it:** the server stores two conflicting anchors per finding, patch-only findings are permanently locationless, and whoever later writes "is this finding still valid?" has to pick which one to trust.

### 2. `expected_lines` and `selected_text` are the same idea computed two different ways

**The repo is opened once, not twice.** `paths.WorktreeRoot` is called twice (line 834, then again inside `gitrepo.OpenCurrent` at `gitrepo/repository.go:26`), but it caches per-cwd behind an RWMutex (`paths/paths.go:67-98`), so only one `git rev-parse` subprocess is forked; the second call costs an `os.Getwd` plus an RLock.

## Theoretically wasteful, practically irrelevant — do not change

- **`patchAnchorLines` full-file split** (`trail_review_cmd.go:988`). `strings.SplitAfter(string(content), "\n")` copies the whole file and allocates a `[]string` of every line to keep ~10 of them. A byte-offset scan with `bytes.IndexByte` is measurably better — on a 660 KB / 19k-line file: **253 µs / 967 KB / 3 allocs → 42 µs / 704 B / 1 alloc** (6× faster, ~1000× less garbage). But on a realistic source file being patched (20-100 KB) that's ~10-40 µs saved, invisible next to one HTTP round trip, and the offset version is more code with an off-by-one risk. The current form is clearer and correct. (Aside, robustness not efficiency: peak memory is 2× file size plus 16 B/line, so a pathologically large target would spike — irrelevant for the source-file flow this serves.)

- **`gitBlobHash` hashing the whole file** (`trail_review_cmd.go:1002`). Necessary by definition — `expected_file_hash` must equal what `git hash-object` prints, which is the OID over the entire content. The content is already in memory from the single `os.ReadFile` at line 849, so there is no extra I/O, and `plumbing.NewHasher(..., int64(len(content)))` seeds the object header without a second pass. Nothing to win.

- **Patch scanned once.** `parseTrailReviewPatchTarget` (line 901) makes exactly one `bufio.Scanner` pass. `strings.TrimSpace(opts.Patch)` runs twice (lines 357 and 786), but `TrimSpace` only walks leading/trailing whitespace — O(1) here, not a re-scan. `scanner.Text()` allocating per line and the one 64 KB `scanner.Buffer` are noise for patches of tens of lines.

- **`regexp.MustCompile` at package scope** (`trail_review_cmd.go:896`). This *does* run at init for every `entire` invocation including git hooks. Measured: **4.4 µs**. `cmd/entire/cli/*.go` already carries 19 package-level regexps, and hook p50 is ~3.4 s. This is 0.0001% of a hook. Non-issue.

- **No free concurrency.** The only two independent units are the object-format lookup (2.2 ms, I/O-bound) and the patch parse + file read (sub-ms). Overlapping them in a goroutine would save ~2 ms and cost error-plumbing complexity in a command that blocks on the network. Not worth it.</result>
