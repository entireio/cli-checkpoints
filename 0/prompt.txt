## 2. The trailer-driven join, and why a ref with no referencing commit is skipped

- The join that links checkpoint → commit → session is **`repo_checkpoint_commits`**, written only by:
  - `processCheckpointPayload` → `db.checkpoints.upsertSyncCommitBatch` — `git-source/checkpoint-processing.ts:235-242`, using `commit.sha` of the **user commit that carried the trailer**.
  - The reconcile re-derivation — `git-source/reconcile.ts:557-589`.
- Discovery is 100% commit-message text: `extractCheckpointIds` matches `/^Entire-Checkpoint:\s*(\S+)/gm` — `github.ts:2208-2216`.
- **Skip mechanics for a ref with no referencing commit:**
  - `processCheckpointPayload`: `discovered = commits.flatMap(extractCheckpointIds(commit.message))`; if `discovered.length === 0` it returns `{status:"ok", checkpointsDiscovered:0}` immediately — `checkpoint-processing.ts:176-181`. No trailer ⇒ nothing enqueued, nothing joined.
  - The session-branch path never even fires for a `refs/entire/checkpoints/&lt;shard&gt;/&lt;id&gt;` push: `getCheckpointSourceRefForPush` returns `null` for anything other than `refs/heads/entire/checkpoints/v1` — `checkpoint-storage.ts:7-9` — so `processSessionsPushEvent` early-returns at `processing.ts:1785-1788`.
  - Even on the v1 branch, session-side discovery keys off the checkpoint-branch commit **subject** `Checkpoint: &lt;id&gt;` (`processing.ts:1925-1942`); it produces `repo_checkpoints` but **never a junction row** (hydrator has no commit link).

So an imported checkpoint (no trailer, ref not `refs/heads/entire/checkpoints/v1`) hits **neither** discovery path → no `repo_checkpoints`, no `repo_checkpoint_commits`, no `repo_sessions`.

# Silent-failure audit: 919f7bcf5..3e4eae84a (feat/import-commit-link)

No Critical findings — the contract (best-effort, display-only anchor with a guaranteed fallback) is honest, documented at every suppression site, and none of the suppressed errors can corrupt data or drop a checkpoint. But two suppressions are Important because the decision they hide is made **exactly once and is never reproducible**: `Run` skips already-imported turns (`agentimport.go:176-178`), so re-running the import with `log_level: DEBUG` after the fact re-resolves nothing. Whatever isn't logged at first-import time is evidence destroyed.

## Important

**1. `buildAncestors` failure is indistinguishable from "no anchors matched" — and it's the whole-run failure mode.**
`/Users/peytonmontei/Documents/entire/devenv/entireio/cli/.worktrees/import-commit-link/cmd/entire/cli/agentimport/turn_anchor.go:77-95`

- `CommitObject(fallback)` error → empty set → **every** turn in the run falls back (line 79-81).
- Mid-walk `ForEach` error → partial set → turns whose commits sit past the break fall back (line 85-93).

Hidden errors: missing objects from a **shallow clone** (grafted history is the realistic, common trigger — `CommitPreorderIter` hits a missing parent and the walk breaks at the shallow boundary), a corrupted odb, or a fallback SHA that isn't actually a commit. The comment says "same as the original per-call error handling this replaces," which is true for the output but not for diagnosability: a user on a shallow CI clone whose entire import anchors to head has **nothing** in `.entire/logs` distinguishing "your clone can't see history" from "none of your commits survived squash-merges." Those demand opposite remedies (unshallow vs. accept).

This is the cheapest possible fix: `buildAncestors` runs **at most once per Run**, so it's one debug line per import, zero noise concern. Recommend:

```go
fbCommit, err := r.repo.CommitObject(plumbing.NewHash(r.fallback))
if err != nil {
    logging.Debug(ctx, "import: anchor ancestor walk unavailable, all turns fall back",
        "fallback", r.fallback, "error", err.Error())
    return ancestors
}
...
if err := iter.ForEach(...); err != nil {
    logging.Debug(ctx, "import: anchor ancestor walk truncated",
        "fallback", r.fallback, "ancestors_collected", len(ancestors), "error", err.Error())
    return ancestors
}
```

This requires threading `ctx` into `resolve`/`buildAncestors` (Run already has it at `agentimport.go:192`). Commit SHAs and counts are operational metadata — squarely within the repo's privacy convention, and the package already does exactly this shape at `agentimport.go:205`.

**2. A turn that recorded commits but fell back leaves no signal — per-turn, unreproducible.**
`/Users/peytonmontei/Documents/entire/devenv/entireio/cli/.worktrees/import-commit-link/cmd/entire/cli/agentimport/turn_anchor.go:59-71`

Three distinct causes collapse silently into fallback: hex-gate miss (line 61), `ResolveRevision` error — gc'd/rebased-away commit, or ambiguous short SHA (line 64), ancestor-set miss — side-branch or squashed commit (line 68). Users asking "why is this session anchored to head instead of the commit it made?" get nothing; the one existing log (`import_cmd.go:81`) names only the fallback, which tells them what they already see in the UI.

On the noise question: log **only the fell-back-with-candidates case**, not every turn. Turns with no candidates (the stated common case for older transcripts) never log; turns that anchor successfully don't need to. What remains is precisely the anomaly population, at Debug level (opt-in). The cleanest placement avoiding ctx-plumbing for this half is the call site, where sessionID/UUID live:

```go
// agentimport.go:192
anchor := anchorResolver.resolve(turn.CommitSHAs)
if len(turn.CommitSHAs) &gt; 0 &amp;&amp; anchor == opts.LinkCommitSHA {
    logging.Debug(ctx, "import: turn anchor fell back",
        "sessionID", sf.SessionID, "turnUUID", turn.UUID,
        "candidates", len(turn.CommitSHAs))
}
```

(Edge: a turn whose last candidate genuinely *is* the fallback commit logs a false "fell back" — harmless at Debug, or return a bool from `resolve` if you care.) I would not go further than these two logs; distinguishing the three per-candidate causes inside the loop is noise the ancestor-walk log from finding 1 mostly disambiguates anyway.

## Appropriate suppressions (no change needed)

**3. `commitSHAsInRange` unmarshal → continue** — `/Users/.../agentimport/claude.go:119-121`. Appropriate, and stronger than "matches sibling `modelInRange`" (claude.go:85): the unmarshal error here is **load-bearing flow control**, not corruption tolerance. **5. Memoization on failure is correct** — `buildAncestors` returns a non-nil empty map, so a failed walk doesn't re-walk per turn (`turn_anchor.go:56-58`). Good defensive detail.

## Minor

**6. Hex-looking ref names can silently win over SHA prefixes** — `turn_anchor.go:63-66`. `shaCandidatePattern` admits 4-64 hex chars, but `ResolveRevision` resolves ref names before hash prefixes: a branch or tag named in pure hex (`beef`, `decade`, `cafe1`) would resolve as that ref, and if its tip is an ancestor of fallback the turn anchors to the wrong commit — silently, with no error to suppress. Ancestry-gated and display-only, so impact is cosmetic mis-anchoring; not worth code today, worth a sentence in the `shaCandidatePattern` comment (which currently claims the gate stops "revision syntax" from reaching ResolveRevision — it stops `HEAD~2`, not hex-named refs).

**7. Docs name a function that doesn't exist** — `docs/architecture/sessions-and-checkpoints.md:315` references `resolveTurnAnchor` in `agentimport/turn_anchor.go`; the actual API is `turnAnchorResolver.resolve` / `newTurnAnchorResolver`. Someone debugging from the docs will grep for a symbol that isn't there — a small diagnosability paper cut in a change that's otherwise about diagnosability.

## Bottom line

The suppression *policy* is sound; the *observability* is one notch too dark given the skip-on-rerun property makes every anchoring decision a one-shot. Two `logging.Debug` additions (findings 1 and 2 — three lines of logging total, at most 1 + N-anomalous-turns lines per run, operational metadata only) close the entire "user cannot diagnose why this session anchors to head" gap. Findings 3-5 are clean; 6-7 are comment/doc touch-ups.</result>
