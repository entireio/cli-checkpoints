and then maybe this was an issue, but then not sure, 1. "Dispatch unavailable" is a 404 caused by a permission-check mismatch on our side. Generating a dispatch checks "do you have access to this repo" — passes. Viewing the dispatch additionally requires the repo to have checkpoint_count > 0 in our database — fails for their repo. So the dispatch gets created and persisted, then the very next page load 404s. That mismatch is the bug we're fixing.
2. Why is their checkpoint_count 0 despite all their activity? Because that counter doesn't count ingested checkpoints — it only counts checkpoints linked to git commits, and that link is built by our server scanning the commits on their GitHub repo for the Entire-Checkpoint-ID trailer. For their repo, zero links exist. This is also why the dispatch content itself said "no activity" — dispatch only summarizes commit-linked checkpoints on the queried branch.
3. Why zero links — that's the unconfirmed part. Their local commits have the trailers (their checkpoint list screenshot shows checkpoints paired with commits). The likely explanations: the commits on GitHub main lost the trailers (squash-merging PRs creates new commits without them), or the trailers are there but our scanning didn't run (webhook delivery, the ingestion kill switch, stale branch sync). Checking one recent commit message on their GitHub main for the trailer tells us which.
