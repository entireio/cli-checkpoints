## Concrete issues

**§3.8 — `checkpoint tokens` "sliced at that session's token window"** (blocking design gap)
Claim: totals/attribution are recomputed from stored `full.jsonl` sliced at the session's token window. Code: `SessionState.TokenTranscriptStart` (`cmd/entire/cli/session/state.go:240`) is session-state only; nothing in `api/checkpoint/metadata.go` persists a token offset (only `checkpoint_transcript_start`, line 423, which `carryForwardToNewShadowBranch` resets to 0 — per commit `c69c00337`). So a reader has no window start for post-carry-forward checkpoints; slicing at `checkpoint_transcript_start` reproduces the exact cumulative bug PR A fixed. The spec needs either a persisted `token_transcript_start` in `Metadata` (PR B addition, or a PR A follow-up) or an explicit derivation (previous checkpoint's transcript length) — and legacy checkpoints can never be sliced, so attribution there must be labelled cumulative too.

**§3.1 — `flattenTokenUsage` named as existing.** No such function anywhere (`grep -rn flattenTokenUsage cmd` → none). Existing helpers are `addCheckpointTokenUsage` (`checkpoint_tokens.go:360`), `saturatingIntAdd` (`:383`), `totalTokens` (`status_style.go:111`). §7 lists it ambiguously; mark it new.

**§3.1/§7 — `addCheckpointTokenUsage` drops PR A's fields.** `checkpoint_tokens.go:360-380` copies `Input/CacheCreation/CacheRead/Output/APICallCount` field-by-field and silently loses `ThinkingTokens`, `CacheCreation1hTokens`, `Model`. The spec says the flattening "stays in `cli` with the existing saturating helpers" — as written they would zero the subset fields the whole design depends on. CLAUDE.md explicitly calls this pattern out ("a field-by-field copy is how the nested total came to be dropped") and names `types.AddTokenUsage` as the single summing primitive. The spec should say the flatten helper is rewritten on `AddTokenUsage` (or extended and tested for the three new fields).
