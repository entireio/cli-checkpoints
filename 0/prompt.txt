# Entire CLI — auth / api / org / project / repo / grant

Architecture: a **control plane** ("core", login servers like `https://us.auth.entire.io` / `us.console.entire.io`) plus per-jurisdiction **data-plane cells** ("entire-api", e.g. `aws-us-east-2.api.entire.io`). Commands are cobra, defined in `cmd/entire/cli/*.go`. Core calls go through `internal/coreapi` (ogen-generated client); cells/session-mgmt through `cmd/entire/cli/api`.

## Cross-cutting power (the interesting bits)

- **`ENTIRE_TOKEN` bypass** (`internal/coreapi/client.go:69-113`, `cmd/entire/cli/auth/env_token.go:16`): if the env var is set (even blank), the CLI is *committed* to it — no contexts.json, no keyring. The token's own `aud` JWT claim becomes the control-plane origin dialed (`CoreURLFromEnvToken`, validated to be an https bare origin). Fail-closed: blank/malformed is fatal, never falls back. Deliberately has **no trust gate** because coreapi sends the token verbatim as the bearer (the token *is* the credential), unlike git-remote-entire which exchanges it (see the long comment at client.go:84-101).
- **Cross-jurisdiction transport / 421 follow + RFC 8693 exchange** (`internal/coreapi/cross_juris_transport.go`): every core client wraps its RoundTripper so a resource whose home jurisdiction is another region is reachable transparently. Two recovery hops per origin: a **421 Misdirected** carrying `home_core_url` → re-dial the home core; a **401** carrying `{token_exchange_url, audience}` (or a bare 401 right after a 421) → exchange the *original* login JWT at the home core's `/oauth/token` for a token that core accepts. Same-origin guard on `token_exchange_url` (transport.go:80-84); exchanged tokens cached with bounded TTL; chained exchanges rejected (the validator rejects a subject_token already carrying `foreign_iss`).
- **Contexts model**: multiple saved logins in `contexts.json`, each with its own `CoreURL`. The *active* context drives control-plane commands and `git clone entire://…`. `auth use` retargets. Tokens stored in OS keyring (or file store via `ENTIRE_TOKEN_STORE=file`). Note (auth_context.go:19): data-API commands (activity/search/trail/dispatch) still key off `ENTIRE_API_BASE_URL`, *not* the active context.
- Hidden `--insecure-http-auth` on every authenticated command relaxes TLS enforcement for local dev (`auth.go:103`).

# entire CLI — `session` &amp; `checkpoint` command families

All commands live directly in `cmd/entire/cli/` (there is no `commands/` subdir). Parent groups: `newSessionsCmd` (`sessions.go:157`, alias `sessions`) and `newCheckpointGroupCmd` (`checkpoint_group.go:13`, aliases `cp`/`checkpoints`). Both gate on being inside a git worktree via `PersistentPreRunE`.

## Core storage model (docs/architecture/sessions-and-checkpoints.md)

- **Session state**: `.git/entire-sessions/&lt;id&gt;.json`, stored in the git *common dir* so it is shared across worktrees. Records `Branch`, `WorktreeID/Path`, token usage, `LastCheckpointID`, phase, transcript path.
- **Ephemeral (shadow) checkpoints**: branch `entire/&lt;commit[:7]&gt;-&lt;worktreeHash[:6]&gt;` — full worktree snapshot + `.entire/metadata/&lt;session&gt;/` overlay. Multiple concurrent sessions interleave on one shadow branch. Auto-migrated if the base commit changes (stash→pull→apply), deleted after condensation, reset if orphaned (`sessions-and-checkpoints.md:174-198,532-537`).
- **Persistent (committed) checkpoints**: pluggable backend — `git-branch` (`entire/checkpoints/v1`, sharded `&lt;id[:2]&gt;/&lt;id[2:]&gt;/`) or `git-refs` (one ref per checkpoint). ID is 12-hex (branch) or 26-char ULID (refs); reads are kind-routed across both (`sessions-and-checkpoints.md:143-152,370-399`).
- **Checkpoint↔commit link**: `Entire-Checkpoint: &lt;id&gt;` trailer added to user commits by `prepare-commit-msg`; condensation on `post-commit` writes metadata + `full.jsonl` (raw transcript) + `transcript.jsonl` (self-contained compacted session) + `prompt.txt` (`sessions-and-checkpoints.md:199-253,404-467`).

## `session` subcommands

**`list`** (`sessions.go:324`) — all sessions across all worktrees (incl. ended), newest-first. `--json` emits an array of the shared `sessionInfoJSON` envelope (`[]` when empty).

## Audit: Are `entire` Cobra descriptions enough for an agent to self-serve?

### 1. What `agent-help` actually surfaces (from `agent_help_cmd.go`)

`renderAgentHelpCommand` (text) and `renderAgentHelpJSON` both render, per command:
- Command path + `Short`
- `Long` (trimmed; skipped only if identical to Short)
- Auto-detected repo line
- **Flags block** — `LocalFlags().FlagUsages()` + `InheritedFlags()` (hidden flags dropped). This means every `--json`/`--line`/`--compare` flag and its usage string IS shown even when the prose never mentions it.
- Advertised subcommands + a "drill in" pointer

**`cmd.Example` is NOT rendered — neither in text nor JSON.** Commands that want an example visible to agents must bake it into `Long`. ### 2. Advertisement gate — a build-dependent surface (important)

`isAgentHelpAdvertised` hides: `help`/`agent-help`, deprecated commands, and hidden commands that don't set `Annotations["entire_agent_help"]`. **Only `trail_cmd.go` sets that annotation** (nothing else in the tree).

- **`why`, `blame`, `experts` are registered via `experimental.Register`** (root.go 136-137, 155). In a shipped/release binary they are `Hidden` with no annotation → **not advertised in agent-help at all** (nor drillable). In dev builds they are advertised. ### Overall judgment

For the **core advertised commands** — `checkpoint explain`, `checkpoint list`, `checkpoint search`, `session info`, `session resume`, `session tokens` — "entry context + generated pointer + descriptions" is **good enough to self-serve**: `Long` carries when-to-use, arg format, output modes, and (for explain/info) embedded examples, and the rendered flag block always exposes `--json`. An agent could act on these without trial-and-error.

But there are **specific, structural gaps**:

1. **`cmd.Example` is dead weight for agents** — it is never rendered. Any command whose only example lives in the `Example` field (`api`, `auth`, `grant`, `repo`, `project`, `session adopt`) gives the agent no example. The reliable pattern is embedding examples in `Long`, and it's applied inconsistently.
2. **Release builds silently drop `why`, `blame`, `experts` (and `search`/`tokens`/etc.) from agent-help**, because they're `experimental.Register`-hidden and don't set the `entire_agent_help` annotation. An agent on a shipped binary can't discover the very attribution/provenance commands most useful during dev work. This is the largest gap and is invisible in dev testing (where they show up).
3. **`experts` is under-described even when visible** — no `Long`, undocumented argument contract → guaranteed trial-and-error.
4. Minor: `checkpoint tokens`, `session tokens`, `checkpoint search`, `why`, `blame` lack a literal runnable example in `Long`; `status` prose omits its output modes.
