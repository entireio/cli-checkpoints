### F5. The name tightening conflates "is this my grammar?" with "is this name valid?"
`/Users/soph/.herdr/worktrees/cli/soph-repo-clone-followup/cmd/entire/cli/repo_clone.go:91-101` and `:126-131`

Two concrete costs, both from running validation inside the grammar test:

**A message regression on the shorthand path.** `paul/.foo` used to parse as a shorthand and produce `no repo named ".foo" in that project (run entire repo list …)`. It now fails the parser, and because the dispatcher deliberately withholds the native reason from a ref that declared no token, the user gets the generic list of four accepted shapes — the PR's own test pins this (repo_clone_test.go:157). Same for `ab/dogbark` (test:93) and `paul/.dogbark` (test:100). So the length/edge/`..` rules buy a *worse* message on the bare-shorthand path in exchange for saving one HTTP call. Note that the PR's motivating case, `git@github.com:foo/bar`, is refused by the **charset alone** (`@` and `:` in the project segment) — the pre-PR rule already handled it.

**Grammar disambiguation moved from explicit to implicit.** The deleted guard was `if segs[0] == nativeCloneForge || segs[0] == "gh" { not a shorthand }` — a local, self-describing fact. It is now an inferred consequence of a transcribed server minimum ("2-char names can't be projects"), and the comment at :87-90 concedes the inference breaks for a 3-char forge token. A rule that only holds because of a number copied from another repo is a weaker mechanism than the two-line guard it replaced. `gitremote.IsSupportedForge` (gitremote.go:65) is the near-miss precedent for where a shared token list belongs; `git-remote-entire` already consults it for the same "is this segment a forge?" question.

**Deeper fix, and it is smaller than it sounds:** keep the grammar test as *2 segments + charset + an explicit forge-token guard*, and move lengths, edge characters and the `..` ban into a `validateNativeNames(project, repo) error` that runs **only when the ref declared `et/`** — the one path where its precise message is actually printed. Everything the PR won survives: `/et/paul` still says "(2 names, got 1)", `/et/foo_bar/x` still names the rule it broke, `git@github.com:foo/bar` still falls through to the shapes list — and `paul/.foo` gets its informative 404 back. It also shrinks the drift blast radius (below) from "every native ref" to "`/et/` refs only", which keep two escape hatches.

**Verdict: worth doing now.** The test table is fresh, so re-aiming ~8 rows is cheap. If the team prefers to keep the round-trip saving, the non-negotiable half is restoring the explicit forge-token guard so shorthand disambiguation stops depending on a server length constant.

### On the duplication of server name rules (drift)

Duplicating them is defensible in principle but this is the CLI's **only** client-side copy of a server name rule — `repo create` and `project create` do no such validation and let the server reject — so the precedent points the other way, and it lands on a read path rather than the write path where a pre-flight check pays best.

The pinned comment (`entiredb core/resource/project_name.go`) is sufficient for a *reader* of this file and useless as a *change detector*: nobody editing `normalizeName` will ever see it. The drift failure mode is a false local rejection with a confident message naming a rule the server no longer enforces, and there is no telemetry that would surface it. Ranked by cost-effectiveness:

1. **Shrink what's duplicated to what the CLI's own grammar needs (F5).** Removes most of the drifting surface rather than monitoring it.
2. **A reciprocal one-line comment in entiredb beside `normalizeName`** naming this file. It is the only cheap thing that fires at the moment of change. Do this whether or not F5 lands.
3. A contract test is not cheaply available — different repo, and the CLI *deliberately* deviates on case (accepts uppercase because both lookups fold), so there is no mechanical equality to assert. Don't pretend otherwise; a generated constant would require the server to publish the rules (OpenAPI or a shared module), which is the only real long-term answer if these rules start churning.
