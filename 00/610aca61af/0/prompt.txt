## Review Findings: OPF Supporting Pieces (PR #1214, branch `feat/openai-privacy-filter`)

### Critical

**1. `CleanupPushedShadowBranches` can permanently delete un-condensed checkpoint data**
`cmd/entire/cli/strategy/cleanup.go:151-159`

```go
for _, s := range states {
    if s.EndedAt != nil &amp;&amp; len(s.TurnCheckpointIDs) == 0 {
        continue // safe — session ended cleanly and finalized
    }
    shadow := getShadowBranchNameForCommit(s.BaseCommit, s.WorktreeID)
    protected[shadow] = true
}
```

The predicate treats `EndedAt != nil &amp;&amp; len(TurnCheckpointIDs) == 0` as "session ended cleanly and finalized," but that is **not** equivalent to "checkpoints reached v1 / the remote." `EndedAt` is set on the SessionStop hook (`cmd/entire/cli/lifecycle.go:1082`, `markSessionEnded`), which is entirely independent of `git commit`. Condensation from the shadow branch to `entire/checkpoints/v1` happens in **PostCommit** (`manual_commit_hooks.go` `HandleCondense`), not at session end. So a session can be ended-clean with no pending turn checkpoints while its checkpoints still live **only on the shadow branch**, never condensed and never pushed.

Sequence that loses data: agent works (checkpoints on shadow branch) → agent stops (`EndedAt` set, `TurnCheckpointIDs` cleared) → user has not run `git commit` → user pushes some other branch → pre-push fires `CleanupPushedShadowBranches` (`manual_commit_push.go:103`) → the shadow branch is deleted → the un-condensed checkpoints are gone.

The function's own doc comment ("the caller knows any condensed checkpoint data already reached the remote") is only true for data that was condensed; it provides no protection for data that was never condensed.

The codebase already has the correct safety marker and the existing post-commit cleanup uses it: `state.FullyCondensed` (`cmd/entire/cli/session/state.go:211-216`: "indicates this session has been condensed and has no remaining carry-forward files"). The existing deletion path at `manual_commit_hooks.go:981` and `:995` gates on `state.FullyCondensed &amp;&amp; state.Phase == session.PhaseEnded`. The new predicate should use the same `FullyCondensed` gate rather than substituting `EndedAt`/`TurnCheckpointIDs`. As written this is a destructive divergence from the proven safe-deletion condition.

The test `cleanup_pushed_shadow_test.go` does not catch this because its fixtures (`addSessionState`) only set `EndedAt`/`TurnCheckpointIDs` and never model the ended-but-not-condensed state — the test encodes the buggy contract rather than the real invariant.

### High

**2. Read-modify-then-delete race in cleanup against concurrent session start**
`cmd/entire/cli/strategy/cleanup.go:140-167`

`ListShadowBranches` and `ListSessionStates` are read once, then `DeleteShadowBranches` runs against that stale snapshot. The CLI explicitly supports concurrent sessions in the same worktree (per CLAUDE.md). If a new session's TurnStart writes/creates a shadow branch (or writes a session state file) in the window between the `ListSessionStates` read at line 149 and the delete at line 161, the new branch is not in `protected` and gets deleted, or the new state file is missed. The "conservative safety predicate" framing in the comment does not account for this TOCTOU window. At minimum this should be documented as a known limitation; ideally the delete should be gated under whatever lock guards session-state creation, or re-validate per-branch immediately before deleting.

### Medium

**3. Unanchored OPF trailer regex enables a privacy-filter bypass via body-injected content**
`cmd/entire/cli/trailers/trailers.go:72`, `HasOPFApplied` at `:290`

```go
opfAppliedTrailerRegex = regexp.MustCompile(OPFAppliedTrailerKey + `:\s*(\S+)`)
```

The regex is unanchored and matches anywhere in the commit message, not just the trailer block. `entire/checkpoints/v1` commit messages carry condensed session data; if any blob/summary content that lands in a commit message contains the literal `Entire-OPF-Applied: true`, `HasOPFApplied` returns true and the pre-push rewrite skips OPF for that commit while it is treated as applied — i.e. un-OPF'd content is pushed and marked filtered. The reverse direction (`false` appearing before a real `true`) is safe because `FindStringSubmatch` returns the first match and `false` re-triggers OPF, but the `true`-injection direction is a genuine, if low-probability, bypass. Consider anchoring to line start (`(?m)^Entire-OPF-Applied:`) and/or parsing only the trailer block, consistent with how a strict trailer parser would behave. The other trailers share this unanchored style, but for OPF the failure mode is specifically "privacy filter silently skipped," which raises the stakes.

**4. `TimeoutSeconds` is not validated at the settings layer**
`cmd/entire/cli/settings/settings.go:982-992` (`validateOPFSettings`)

`validateOPFSettings` validates categories and `prompt_default` but not `timeout_seconds`. A negative or zero value is accepted and silently coerced to 30s deep in `redact.ConfigurePrivacyFilter` (`redact/opf.go:56-58`). That coercion makes it non-fatal, but a user who sets `timeout_seconds: -5` (or a typo'd large/garbage value) gets no feedback that their setting was ignored, contrary to the "surface typos at parse time" philosophy stated in the same function's own comment. Consider rejecting `&lt; 0` (or at least logging) for parity with the category-validation rationale. No test covers timeout values.

### Low

**5. `readSubObject` silently discards a malformed nested object on persist**
`cmd/entire/cli/strategy/manual_commit_opf_prompt.go:166-177`

If `settings.local.json` parses at the top level but its `redaction` value is malformed (e.g. a string or array rather than an object), `readSubObject` returns a fresh empty map (`:173-174`), and the subsequent `writeSubObject` (`:154-159`) overwrites the entire `redaction` slot — silently destroying any sibling redaction config (`custom_redactions`, PII settings, etc.) when persisting `prompt_default=always`.
