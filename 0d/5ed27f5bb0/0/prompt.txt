## Root-cause report: git-refs "write-after-stop creates no checkpoint"

### TL;DR
This is **not a git-refs write bug**. Under the flow in question, **neither backend condenses a checkpoint** — the stop hook's "no files modified during session" gate skips it on both. The test's git-branch assertion *falsely passes* because it checks only that the `entire/checkpoints/v1` branch exists, which is trivially satisfied by an *inherited* checkpoint auto-fetched from origin on clone. The git-refs assertion correctly reports "no checkpoint locally." The `KNOWN BUG` comment's diagnosis (git-refs-specific write divergence) is wrong.

### 1. Exact code path in the write-after-stop flow (git-refs)
Verified empirically by un-skipping the test in a scratch worktree with debug/ref/tree dumps. Both backends produce identical session lifecycle logs:

- `UserPromptSubmit` → `TurnStart` → shadow session initialized; creates the session-metadata anchor `refs/heads/entire/checkpoints/v1` (log: "Created orphan ref … for session metadata").
- `SimulateStop` → `TurnEnd`. The clone's `clone.go` is **not on disk yet** (the test's `CreateTranscript` writes only the transcript JSONL, not the referenced files), so the stop hook logs **`"no files modified during session, skipping checkpoint"`** and transitions active→**idle**. No shadow branch, no `SaveStep`, empty `FilesTouched`, `StepCount=0`.
- `WriteFile`+`GitAdd`+`GitCommitWithShadowHooks("Clone work")` fire `prepare-commit-msg`/`post-commit`. The session is idle with no shadow branch, no tracked files, and no new content, so **nothing is condensed** — the logs show zero post-commit/condense activity and no trailer/checkpoint commit.

Key files: stop-hook skip is the `"no files modified"` gate in the lifecycle handler; the eager-condense skip is `CondenseAndMarkFullyCondensed` (`strategy/manual_commit_condensation.go:1177-1204`); post-commit condensation gating is `postCommitActionHandler.HandleCondense*` / `shouldCondenseWithOverlapCheck` (`strategy/manual_commit_hooks.go:695-808`). None of these are reached with condensable data here.

### 2. Where git-branch and git-refs *appear* to diverge (the real cause)
The divergence is entirely in the backend-aware assertion `CheckpointsPresentLocally()` (`cmd/entire/cli/integration_test/backend.go:72-78`), which checks **non-equivalent conditions**:

- **git-branch**: `BranchExists("entire/checkpoints/v1")`. In the clone this is true because the origin's **initial** checkpoint (`createCheckpointedCommit(..., "Initial work", "init.go", ...)`, which stages *before* stop and legitimately condenses) rides on `refs/heads/entire/checkpoints/v1` — a normal branch that a plain `git clone` fetches by default. Proof: the git-branch clone's v1 log shows exactly one checkpoint commit `Checkpoint: 39bb8b3fae49` (the inherited "Initial work"), and **no** commit for "Clone work".
- **git-refs**: `anyRefUnderPrefix("refs/entire/checkpoints/")`. False because (a) no new checkpoint was condensed, and (b) the origin's inherited checkpoint lives at `refs/entire/checkpoints/&lt;shard&gt;/&lt;id&gt;`, which is outside `refs/heads/*` and so is **not fetched by a default clone** (git-refs relies on the on-demand `RefFetcher` for cross-machine reads). Proof: the git-refs clone's v1 branch contains only an empty `Initialize metadata ref` commit (no tree entries), and there are zero `refs/entire/checkpoints/*` refs.

So git-branch's pass is a false positive on inherited data; git-refs accurately reports no local checkpoint.

### 3. Is data lost? No.
Nothing is lost — and in the write-after-stop scenario there is no checkpoint to lose (none is ever created, on either backend). The origin's initial checkpoint content exists on the remote in both topologies (v1 branch for git-branch; a pushed per-checkpoint ref for git-refs, per the passing `TestPrePush_*` tests) and is reachable in a git-refs clone via the on-demand RefFetcher during resume/explain. The `v1` branch under git-refs is only a session-metadata anchor and never carries checkpoint content.

### 4. Minimal reproduction
In `TestGracefulDegradation_...`, remove the `t.Skip` and observe: git-branch passes, git-refs fails. Root difference is ordering — compare the failing clone flow (stage AFTER stop) with the helper `createCheckpointedCommit` (`remote_operations_test.go:266-288`), which does `WriteFile`+`GitAdd` **before** `SimulateStop`. Reordering the clone flow to stage before stop makes the stop hook detect the change, condense a real checkpoint, and **both backends pass**: I verified git-refs then creates `refs/entire/checkpoints/DA/01KWQ7HDP3NYZQXAK1PQYCHGDA` and git-branch adds a second `Checkpoint:` commit.

### 5. Recommended fix (do not implement per instructions)
Fix the **test**, not the strategy/store code (which behaves correctly and identically). Preferred:

- In `TestGracefulDegradation_UnreachableCheckpointRemoteOnCloneIsSilent`, move `cloneEnv.WriteFile("clone.go", ...)` + `cloneEnv.GitAdd("clone.go")` to **before** `cloneEnv.SimulateStop(...)` (mirroring `createCheckpointedCommit`), then delete the `usingGitRefs()` skip and the `KNOWN BUG` comment. This makes the test assert what it claims — that the clone's session actually condenses a local checkpoint — and it passes on both backends.

Secondary hardening (optional): make `CheckpointsPresentLocally()` symmetric so the git-branch arm proves checkpoint *content* exists (e.g. at least one sharded `*/metadata.json` under the v1 tree) rather than mere branch existence. Note this alone would not have equalized this test — the git-branch clone *does* have inherited content — so the ordering fix is the essential one.

Risk: none to product code. The only behavioral question a reviewer might raise — "should a session that touched no files on disk produce a checkpoint?" — is correctly answered "no" by both backends today.
