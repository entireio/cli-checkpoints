Most of the branch is well-shaped: `mirrorCreateOptions` replacing a 7-arg helper is a genuine improvement, there is **no** async→sync fallback (a clean either/or toggle, not duct tape), and the settings field itself follows the house pattern (struct field + `mergeRawBool` + local-override test). The altitude problems are concentrated in how the async flow's *routing* information crosses the coreapi/CLI boundary, and in how the async result is squeezed into the sync DTO.

## Findings

**1. `cmd/entire/cli/repo_mirror_probe.go:160-187` — trust decision about a server-supplied URL made in the command layer, with weaker rules than the ones coreapi already owns.**
`mirrorRequestPollTarget` takes the `Location` header, and if absolute, re-points the authenticated client (carrying the login JWT) at that host via `coreapi.WithServerURL` — validating only `scheme in {http, https}`. `internal/coreapi/cross_juris_transport.go:74-92` documents an explicit trust model for exactly this class of "server tells us to go elsewhere": HTTPS-except-loopback, same-origin for `token_exchange_url`, federation-manifest membership for `home_core_url`. None of that applies here. Cost: this is only safe today because of finding 2 — the transport rewrites `Location`'s host to the host that actually served the request, so the CLI can never be pointed off-federation. That invariant lives in a different package, is undocumented on both sides, and is invisible to anyone touching either file. Deeper fix: origin pinning belongs in `internal/coreapi` (a client method or a documented `coreapi` helper that takes the raw `Location` and applies the same federation/scheme gate as `followMisdirected`), not in a `cmd/` probe file.

**2. `internal/coreapi/cross_juris_transport.go:305-317` — `canonicalizeMirrorRequestLocation` is a per-endpoint patch inside shared transport code.**
It hardcodes `apiBasePath+"/mirror-requests"` and `202`, and it is the only function in this heavily-commented file with no doc comment explaining why it exists. The real information being smuggled is "which origin actually served this request after a possible 421 follow" — a property of the transport's general redirect mechanism, not of this endpoint. Cost: the next async endpoint (or a second async flow) copies the branch; conversely a reader who prunes it as dead one-off silently breaks finding 1's safety. Deeper fixes, in order of preference: (a) have the server list `421` on `GET /mirror-requests/{requestId}` and let the existing, already-trusted 421-follow handle the poll — then both this function and the `Location`-parsing in the CLI disappear; (b) if pinning must be client-side, expose the effective origin generically (set `resp.Request` to the final hop, or an opt-in `WithEffectiveOrigin(ctx, *string)` the transport fills), so any multi-step flow can use it without a path literal.

**3. `cmd/entire/cli/repo_mirror.go:638`, `686-696` and `repo_mirror_probe.go:123-127` — the async result is fabricated into a `CreatedMirror` and then disclaimed with a boolean.**
`awaitMirrorPlacement` builds a `coreapi.CreatedMirror` with only id/url/publicURL, so `Created`, `Empty` and `Suspended` are silently zero; `createdStateUnknown` is the "don't trust three of these fields" marker. Cost: only one of the two consumers honors it. `reportOneShotMirror` branches on it, but `createOneMirror` (`cmd/entire/cli/repo_mirror_create_wizard.go:582`, `594`) still reads `outcome.created.Suspended` / `.Empty` as if they were meaningful, so in async mode `mirrorStatusEmpty` and the `--no-wait` suspended path become unreachable rather than "unknown". Every future field added to `CreatedMirror` inherits the same trap. Deeper fix: make `mirrorCreateOutcome` the real model — carry `mirrorID`/`mirrorURL` directly plus optional/tri-state lifecycle facts — instead of a struct-shaped lie plus a flag.

**4. `cmd/entire/cli/repo_mirror.go:493-498` and wizard `:310, :509, :542, :563` — the toggle is read in `RunE` and threaded as a positional bool through four signatures.**
The codebase precedent for exactly this shape is `settings.IsExternalAgentsEnabled(ctx)` (`cmd/entire/cli/settings/settings.go:1747`, consumed at the single decision point in `agent/external/discovery.go:40`). Here the inline `if settings, err := LoadEntireSettings(...); err == nil` re-implements that predicate, then `runMirrorCreateWizard`/`createMirrors`/`createOneMirror` each grow a parameter that only `createAndAwaitMirror` uses. Cost: three intermediate functions now have a signature that changes again the moment the flag is retired or a second routing knob appears; two of them already take `noWait, waitTimeout` positionally and are drifting toward the arg-list this branch just cleaned up in `createAndAwaitMirror`. Deeper fix: `settings.IsAsyncMirrorRequestsEnabled(ctx)` in the settings package, called once inside `createAndAwaitMirror` (or when building `mirrorCreateOptions`), so nothing in between knows the flag exists.

**5. `cmd/entire/cli/repo_mirror_probe.go:195-207` — hardcoded allow-list of ten failure-code strings.**
`MirrorRequestFailure.Code` is a plain `string` in the spec (no enum), so this list duplicates a server-side vocabulary with no compiler or generator backing, and the only behavioral difference is the wording "with unknown failure code". Cost: a server adding a code makes the CLI editorialize about the server being wrong; the list will silently rot. Deeper fix: either declare the enum in the spec so ogen generates the type (then a `switch` is checkable), or drop the list and always render `code: message` — the code is already documented as "stable machine-readable".

**6. `cmd/entire/cli/repo_mirror.go:590-594, 667-672` — `--wait-timeout` means two different things depending on the toggle.**
Async wraps submit + placement poll + clone poll in one `waitCtx` and then passes `pollTimeout = 0` to `awaitMirrorReady`; sync applies the timeout to the clone poll only. The flag help says "How long to wait for the initial clone to finish". Cost: the deadline semantics silently change with a settings key, and the `pollTimeout = 0` line only makes sense if you know about `waitCtx` 80 lines up. Deeper fix: one timeout policy owned by `mirrorCreateOptions` (either always a whole-operation deadline, or always per-phase), applied identically in both routes.

**7. `cmd/entire/cli/repo_mirror.go:526-535` vs `:582-588` — phase de-duplication implemented twice.**
`createAndAwaitMirror` already suppresses repeat phases via `currentPhase`, and the one-shot's `onPhase` closure does the same check again before swapping spinners. Cost: two places to keep in sync; the command-layer copy is dead logic that reads as if it were load-bearing. Keep the dedupe in the helper and let the command assume distinct phases.

**8. `cmd/entire/cli/repo_mirror_probe.go:228` (removed `onStatus`) + `repo_mirror.go:565-571` — the phase enum is a lossy re-modelling of the API's statuses, and it cost the wizard its live clone status.**
`awaitMirrorReady` lost its per-poll callback so the wizard's Docker-style line now sits on a static `cloning` instead of streaming `processing`/`ready`. Also `mirrorCreatePhase.label()` title-cases the enum's own string to produce UI text, coupling wire-ish identifiers to display. Deeper fix: keep the status stream from `awaitMirrorReady` and let the phase type carry a display label explicitly, so the CLI vocabulary and the API vocabulary can diverge without one being derived from the other by `strings.ToUpper` on a substring.

**9. Minor, same file: `classifyPlacementWaitContextErr` (`:276`) is a copy of `classifyWaitContextErr` (`:286`) differing only in the message**, and `maxConsecutivePollErrors` (`:68-73`) is now shared by two loops whose rationales differ — the comment explaining the 15/30s budget (post-create stale reads) was replaced with a vaguer one that no longer justifies the number for either caller. One parameterized helper and a phase-specific budget would be honest about the two concerns.</result>
