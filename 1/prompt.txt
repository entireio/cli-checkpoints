## 1. Both fixes work around go-git's `Status()`; the repo's own precedent says replace it

**Files:** `cmd/entire/cli/gitrepo/status.go:33-41`, `.gitignore:52-55`, `e2e/.gitignore:1-10`

Both fixes are shaped around *keeping* `worktree.Status()`. The codebase already contains two independent, documented conclusions that go-git's Status is the wrong tool:

- `cmd/entire/cli/checkpoint/ephemeral.go:1116-1122` — "Uses git CLI instead of go-git because go-git's `worktree.Status()` does not respect global gitignore… See PR #129." So the *correctness* case is already settled in-repo.
- `cmd/entire/cli/strategy/manual_commit_hooks.go:2550-2553` — "This is much faster than go-git's `worktree.Status()` which scans the entire working tree. `git diff --cached` uses native git's optimized index and filesystem monitors." So the *performance* case is already settled in-repo.

CLAUDE.md:495-514 codifies exactly this pattern ("go-git v5 Bugs — Use CLI Instead"). This change is the third instance of the same problem and it went the other way.

Measured, in this repo, right now:

```
git status --porcelain --untracked-files=all   →  0.02s
go-git Worktree.Status() (pre-fix)             →  5.25s
```

I confirmed a CLI-backed `gitrepo.Status` is a genuine drop-in, not a rewrite:
- go-git's `StatusCode` constants (`status.go:75-82`) are literally the porcelain-v1 XY characters `' ' ? M A D R C U`, so `git status --porcelain=v1 -z -uall` parses directly into a `git.Status` map with no caller changes at any of the five consumers.
- Real git prunes correctly regardless of which `.gitignore` declares the rule — verified empirically in a scratch repo: a root-level `outer/ignored/` rule prunes `outer/ignored/deep/` from `git status -uall`.

**Cost/fragility:** the current shape leaves the 5s landmine armed for every ignored directory that is not a direct child of the `.gitignore` declaring it, keeps the known global-gitignore correctness gap, and adds ~75 lines of caching machinery whose entire reason to exist is that the underlying call costs seconds.

**Deeper fix:** implement `gitrepo.Status(ctx, repo)` over `git status --porcelain=v1 -z --untracked-files=all` with `cmd.Dir = worktree.Filesystem().Root()`. Both `.gitignore` files revert to the simple root rule, the memoization becomes unnecessary (20ms), the safety constraint on the cache disappears, and the global-gitignore gap closes. Note I checked and ruled out the obvious middle path: setting `Worktree.Excludes` does **not** help — `worktree_status.go:184-189` appends `w.Excludes` *after* `gitignore.ReadPatterns` has already done the expensive walk.

## 2. The `.gitignore` placement convention has no mechanical guard, and the test that claims to guard it doesn't

**File:** `cmd/entire/cli/gitrepo/status_external_test.go:232-266`

The test's doc comment says it "guards the `.gitignore` placement that keeps go-git from walking e2e/artifacts," but it only asserts that a nested-`.gitignore` rule still *ignores* the file. That assertion passes identically whether the rule lives in `outer/.gitignore` or in the root — go-git's `ReadPatterns` (`plumbing/format/gitignore/dir.go:53-83`) returns the union of all patterns found, so matching is correct in both placements; only the *walk pruning* differs. The test cannot fail when someone moves `artifacts/` back to the root `.gitignore`.

The name/comment mismatch (`TestStatus_CachePrunesIgnoredSubtreeRule` in the comment vs `TestStatus_NestedIgnoreRuleStillIgnores` as the function) is the tell that the test drifted off the invariant it was written for.

**Cost/fragility:** the only thing protecting a 5-second regression is two prose comments in two `.gitignore` files. Nothing in CI notices when someone adds `foo/bar/` to the root `.gitignore`.

**Deeper fix (if fix 1 is not taken):** assert the actual property — build a repo with N ignored subdirectories declared from the *root*, and assert either (a) a wall-clock/`ReadDir`-count budget on `Status()`, or (b) directly that `gitignore.ReadPatterns` does not descend, by counting `ReadDir` calls through a counting `billy.Filesystem`. (b) is deterministic and CI-safe. A repo-level test that walks the actual root `.gitignore` and fails on any pattern containing a `/` before the final component would be even more direct.

## 4. Cache installed at one call site: the safety constraint is real but lives only in a comment

**File:** `cmd/entire/cli/lifecycle.go:553-558`

Opt-in-per-hook is the *correct* altitude given the constraint — a repo-keyed cache inside `gitrepo` would be actively unsafe, because `DetectFileChanges` at `lifecycle.go:879`/`1160` runs *after* the agent has edited files and must see fresh state. Installing at hook dispatch (`DispatchLifecycleEvent`, `lifecycle.go:50`) would be wrong for the same reason. So the placement itself is defensible.

What is at the wrong altitude is how the constraint is expressed: it is a prose comment at the install site, and `WithStatusCache` is an exported function on a widely-imported package with nothing but a doc comment stopping someone from installing it in TurnEnd. There is no test asserting that TurnEnd/SubagentEnd do *not* carry a cache.

**Cost/fragility:** a future "let's speed up TurnEnd too" change produces silently stale checkpoints — a data-correctness bug with no test coverage and no compile-time signal.

**Deeper fix:** if fix 1 is taken, delete this entirely — a 20ms call does not warrant a cache with a correctness precondition. If it is kept, either (a) unexport it and expose a single `gitrepo.WithReadOnlyWorktreeWindow(ctx)` used only by pre-agent hooks, or (b) add an integration assertion that the TurnEnd path observes post-agent worktree changes.

## Bottom line

`gitrepo` is the right *home* for a status entry point — it is already the sanctioned go-git chokepoint and already precedents a git-CLI-backed implementation behind a go-git-shaped API (`gitrepo/reftable.go`). The problem is the *content*: the new file adds a cache around a broken call instead of a correct implementation behind the same signature. Finding 1 subsumes findings 2 and 4 — replacing the body of `gitrepo.Status` with `git status --porcelain` makes the `.gitignore` placement trick, the cache, and the cache's correctness precondition all unnecessary, while closing a correctness gap the repo has known about since PR #129. Findings 3 and 5 apply either way.</result>
