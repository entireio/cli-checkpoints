## Swap function
```powershell
# Windows lets a running executable be renamed but not overwritten or
# deleted, so an existing binary is moved aside, the verified file copied in,
# and the old image removed if nothing holds it. Stale *.old files left by a
# previous run are removed first.
function Install-BinaryFile {
    param([string] $Source, [string] $Destination)

    $leaf = Split-Path -Leaf $Destination
    Get-ChildItem -LiteralPath (Split-Path -Parent $Destination) -Filter "$leaf*.old" -File -ErrorAction SilentlyContinue |
        Remove-Item -Force -ErrorAction SilentlyContinue          # sweep, best effort

    $retired = $null
    if (Test-Path -LiteralPath $Destination -PathType Leaf) {
        $retired = "$Destination.old"
        if (Test-Path -LiteralPath $retired) {                      # a previous .old is still running
            $retired = "$Destination.$([guid]::NewGuid().ToString('N')).old"
        }
        try { Move-Item -LiteralPath $Destination -Destination $retired -ErrorAction Stop }
        catch { throw "Cannot replace $Destination because another program holds it open. Close entire (including any running 'entire mcp') and any tool that has the file open, then rerun the installer. ($($_.Exception.Message))" }
    }

    try { Copy-Item -LiteralPath $Source -Destination $Destination -ErrorAction Stop }
    catch {
        if ($retired) { Move-Item -LiteralPath $retired -Destination $Destination -Force -ErrorAction SilentlyContinue }
        throw
    }

    if ($retired) { Remove-Item -LiteralPath $retired -Force -ErrorAction SilentlyContinue }
}
```

## Measurements (pwsh 7.6.5, local Python server: `/slow` = 3 MB at ~64 KB per 100 ms ≈ 5 Mbit/s steady, ~5 s total; `/stall` = 256 KB, then 30 s of silence, then the rest)
1. **`-TimeoutSec 3` against the 5 s steady body: NOT cancelled.** Completed in 5.28 s, 3,145,728 bytes on disk. So on 7.6 `-TimeoutSec` does not cover reading the body. Docs confirm why: "This parameter replaced the TimeoutSec parameter in PowerShell 7.4. You can use TimeoutSec as an alias for ConnectionTimeoutSeconds", and ConnectionTimeoutSeconds "specifies how long the request can be pending before it times out" — the connection/headers, not the stream. The finding's "anything below ~2.8 Mbit/s aborts" describes pwsh **7.0–7.3**, where `-TimeoutSec` was `HttpClient.Timeout`; those are EOL but our floor ("5.1 or later") admits them, so dropping the cap on the download is still right — it just fixes fewer hosts than the finding implies, and on 7.4+ it changes nothing. I could not reproduce the "The operation was canceled." text here because 7.6 never cancels the body on that parameter.
2. **Stall detector:** `OperationTimeoutSeconds` and `ConnectionTimeoutSeconds` both exist on 7.6.5 (`TimeoutSec` is the alias, not a parameter). Measured: `-OperationTimeoutSeconds 2` on the steady stream (100 ms gaps) → **completed** in 5 s, full 3 MB. `-OperationTimeoutSeconds 3` on the stalled stream → **cut after 3 s**, `System.AggregateException` wrapping `System.TimeoutException: "The request was canceled due to the configured OperationTimeout of 3 seconds elapsing"` — reads as a timeout, names the cause and the number. `-ConnectionTimeoutSeconds 3` on the steady body → completed in 5 s, so on 7.4+ it caps only the connection, as documented. Behaves exactly as advertised.
3. **Default (no timeout parameters):** against the 30 s stall it **completed** in 30 s with the full 3 MB — i.e. `ConnectionTimeoutSeconds 0` and `OperationTimeoutSeconds 0` both mean indefinite ("The default value, 0, specifies an indefinite time-out"); there is no default stall detector on pwsh. A dead connection would hang until the TCP stack gives up, which can be very long. (5.1's `HttpWebRequest` keeps its 100 s header / 5 min `ReadWriteTimeout` defaults, as you said.)

## Choice: (b)
API calls keep `-TimeoutSec 60` (on 7.4+ that's connection-only, which is still the right bound for a small JSON call; on 5.1 and 7.0–7.3 it's the whole call, also fine at 60 s for JSON). `Save-RemoteFile` passes **no** `-TimeoutSec` — removing the whole-body cap on 7.0–7.3, a no-op on 7.4+ and 5.1 — and adds `-OperationTimeoutSeconds 60` **when the parameter exists**, via a splat built from `(Get-Command Invoke-WebRequest).Parameters.ContainsKey('OperationTimeoutSeconds')`. Why (b) over (a): measurement 3 says (a) on pwsh means a mid-download dead connection hangs indefinitely with no message at all, and measurement 2 says the guard costs four lines, never fires on a merely slow link, and produces a message that names itself. Why not (c): agreed, a fixed whole-body cap is the same bug at another bandwidth. Constants: `$WebTimeoutSec` → `$ApiTimeoutSec = 60` (API calls only) and `$DownloadStallTimeoutSec = 60` (per-read gap on the download), so the two can't drift back together; comment on `Save-RemoteFile` quotes the 5.1-vs-7.0–7.3-vs-7.4+ semantics, since that's the non-obvious fact.

**Consequence check:** with (b), a download on pwsh can no longer fail by whole-body cap; it can fail only by a 60 s *stall*, and that surfaces as `TimeoutException … configured OperationTimeout of 60 seconds elapsing` through the top-level catch — an honest message. `TaskCanceledException`/"The operation was canceled." remains reachable only from the two API calls (a 60 s connection stall on 7.4+, or a whole-call stall on 7.0–7.3), where task 7's guarded catch renders it as "Could not reach GitHub … Check your internet connection" — also honest.
