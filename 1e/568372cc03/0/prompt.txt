## MEDIUM+ FINDINGS

**[MEDIUM] Case-sensitivity mismatch between server name filter and client-side `pickProject` — `cmd/entire/cli/resolveref.go` ~line 78 (`resolveProjectRef`) / ~line 116 (`pickProject`)**
`resolveProjectRef` delegates name filtering to the server via `ListProjects{Name: ...}` (documented "exact-match"), then `pickProject` re-filters with a case-sensitive Go `p.Name == name`. If the server's exact-match is case-insensitive (common for names), a query like `--project Widgets` against a project named `widgets` would be returned by the server but dropped by `pickProject`, producing a misleading "no project named" error instead of resolving. Worth confirming the server filter's case behavior; if it is case-insensitive, either normalize before comparing or drop the redundant client-side re-check and trust the server result. The same pattern applies to `pickOrg`, which filters a full `ListOrgs` client-side with `==`.

**[MEDIUM] `resolveAccountRef` assumes a non-empty `AccountId` from `ResolveHandle` — `cmd/entire/cli/resolveref.go` ~line 53**
`resolveAccountRef` returns `id.AccountId` directly after `ResolveHandle`. `ResolvedIdentity.AccountId` is a plain (non-optional) string, so if the server ever resolves a handle to an identity with no backing account (or returns 200 with an empty `accountId`), this silently forwards `""` as the owner ULID into `CreateProjectInputBody.OwnerId`, deferring failure to an opaque server-side create error. A guard — `if id.AccountId == "" { return "", fmt.Errorf("handle %q resolved to no account", ref) }` — would turn a confusing downstream error into a clear local one. Low likelihood but cheap insurance at an external boundary.

**[LOW-MEDIUM] Resolver functions (the network-branching logic) are untested despite an available harness — `cmd/entire/cli/resolveref.go` / `resolveref_test.go`**
The pure helpers are well covered, but `resolveOrgRef`/`resolveProjectRef`/`resolveAccountRef` — which contain the actual ULID-vs-name branch and the "ULID makes no network call" guarantee called out as load-bearing in the file's doc comment — have no tests. `repo_mirror_test.go` already establishes the `coreapi.NewWithBearer(httptest.NewServer(...).URL, "tok")` pattern, so a test asserting that a ULID ref issues zero HTTP requests while a name ref issues exactly one list call would be modest effort and would lock in the key invariant. Not a blocker given the helper coverage, but it leaves the most regression-prone seam unguarded.
