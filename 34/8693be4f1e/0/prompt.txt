## LOW / NITS (non-blocking)

- **Unbounded fetch with no client-side `--limit` cap** (`corecmd.go`, `fetchAllPages`). The walker fetches every page until the server returns an empty cursor; there is no `--limit` / max-pages ceiling, so `org list` / `grant repo list` on a very large tenant will pull the entire collection into memory and one slow `entire` invocation. This is the same behavior the server intends (page size is server-capped at 500) and matches the PR description, so it's acceptable, but a bounded `--limit` that stops paging early would be a reasonable follow-up for the larger collections. Not a defect in this PR.

- **`pageSize` is never sent by any caller** (all six call sites). Callers pass only `PageToken`, relying entirely on the server default page size. That's fine and arguably simpler, but it means the `pageSize` parameter the spec now exposes is dead from the CLI's side — worth a one-line code comment so a future reader doesn't think it was forgotten.

- **Two no-match code paths per resolver** (`resolveref.go`, `resolveOrgRef`/`resolveProjectRef`/`resolveRepoRef`). Each resolver handles both `isNotFound(err)` (a 404) *and* `!out.Org.Set` (a 200 with the singular field absent) with identical friendly-error messages. This defensive doubling is harmless and the duplicated error string is intentional, but if the server contract guarantees exactly one of the two on a miss, a short comment noting "server may return either 404 or 200-with-unset" would clarify why both branches exist.

- **`list_pagination_test.go` tests omit a top-of-function comment about isolation but do note it** — they correctly avoid `t.Parallel()` because they swap the package-level `activeCoreClient` seam, and each says so in a `// Not parallel:` note. Good. (No action; calling out that the convention was followed.)
