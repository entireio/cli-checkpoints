## FINDINGS (medium+)

**[MEDIUM] PR description vs. implementation mismatch — no "branch average" comparison and no "switch model" recommendation.** *(checkpoint_tokens.go, whole comparison path; session_tokens.go `recommendationRules` ~L230-300)*
The PR brief states `checkpoint tokens` "compares a checkpoint's token usage against the branch average" and "recommends optimizations like switching models or enabling prompt caching." The code does neither: `--compare` is a strictly pairwise comparison against one user-supplied baseline checkpoint (`buildCheckpointTokensComparison`), there is no branch-average aggregation anywhere, and `recommendationRules` never emits a model-switch or prompt-caching recommendation (its rules cover cache-replay, API-call count, subagents, context pressure, and long sessions). The code itself is internally consistent and its `--help` text is accurate, so this is a description/scope gap rather than a code defect — but it should be reconciled before merge so reviewers and users aren't expecting branch-average or cost/model advice the command doesn't provide.

**[MEDIUM] `--compare` qualification can mislead because per-session cache state isn't normalized.** *(checkpoint_tokens.go, `checkpointComparisonQualification` / `buildCheckpointMetricDelta` ~L380-420)*
The comparison reports `observed_reduction` / `observed_increase` purely from the signed delta of summed `Total` tokens between two checkpoints. Because `Total` includes `CacheReadTokens` (large-context replays), a checkpoint that simply had more cache reads will read as an "increase" and a cache-warmed follow-up as a "reduction," independent of actual work done. The qualification strings do hedge ("does not prove quality was preserved"), which is good, but the directional verdict itself is driven by a metric dominated by cache replay. Consider qualifying the verdict on the non-cache delta (input+output) or surfacing the cache-read delta as the headline caveat, so "reduction"/"increase" isn't dominated by replay volume.

**[MEDIUM] `recommendationRules` and the agent-brief use fixed magic thresholds with no provenance.** *(session_tokens.go `recommendationRules` ~L235-300)*
The thresholds — cache-read `&gt;= 80%` (high), API calls `&gt;= 20` (medium), subagent share `&gt;= 10%`, context `&gt;= 80%`, turn count `&gt;= 10` / checkpoint count `&gt;= 5` — are hardcoded inline with no named constants or comment explaining their basis. These directly drive user- and agent-facing advice (the agent-brief literally tells an agent to "batch the next diagnostic step" / "compact or restart"). They are defensible defaults, but as written they're unexplained and untunable. Extract them into named constants with a one-line rationale so the behavior is reviewable and adjustable without hunting through the rule body.
