## MEDIUM+ FINDINGS

**[MEDIUM] Destructive deletes have no confirmation and no `--force`/`--yes` flag — `cmd/entire/cli/org.go:84-108`, `project.go:142-166`, `grant.go` repo remove ~411-461 (also inherited `repo.go:175-193`)**
`org delete`, `project delete`, `grant repo remove`, and `repo delete` call the destructive API immediately after resolving the ref, with no `interactive.CanPromptInteractively()` confirmation and no explicit `--force` flag — the only output is `cmd.Printf("Deleted org %s\n", ...)` after the fact. Deleting an org/project is high-blast-radius and irreversible, and a name typo that happens to resolve to a real resource (or a wrong-but-valid ULID) deletes silently. The codebase already has the right pattern in `trail_cmd.go` (`confirmTrailDeletion` gated on `CanPromptInteractively`, with a `force` bypass); these commands should adopt it, or the team should consciously accept "control-plane deletes are unguarded" as policy. This matches the base branch's existing `repo delete`, so it's a pre-existing gap this PR extends rather than introduces, but it now covers four destructive verbs.

**[LOW-MEDIUM] Deletes are not idempotent: deleting an already-gone resource surfaces a raw 404 — `org.go:99`, `project.go:157`, `grant.go` repo remove, `repo.go`**
The generated decoders (e.g. `decodeDeleteOrgResponse`) return only 204 as success; any 404 becomes an `ErrorModelStatusCode` that `renderCoreError` turns into a plain error. So `entire org delete X` twice errors the second time, and `grant repo remove` for an already-revoked grantee errors. This is defensible (you learn the target didn't exist), but it makes the commands awkward in scripts/CI where "ensure absent" is the intent. Consider treating 404 as success for delete/revoke, or at minimum documenting the non-idempotent behavior. Consistent with existing `repo delete`.

**[LOW-MEDIUM] No command-level tests for any new verb's wiring — `cmd/entire/cli/` (grant/org/project/repo)**
Tests added cover only pure helpers (`pickRepo`, `validateGrantRole`, `parseGranteeMode` in `resolveref_test.go`/`grant_test.go`). Nothing exercises the actual command path — ref resolution → correct API call → output rendering — for `org/project get/delete`, `grant repo list/remove`, or the `repo get/delete` name-resolution change. The package already provides the `activeCoreClient` seam and `repo_mirror_test.go`/`trail_cmd_test.go` demonstrate the httptest-server pattern, so a test that asserts e.g. "`grant repo remove --provider github --provider-user-id 12345` hits the by-provider route, not the typed-id route" is cheap and would lock in the mode→route mapping. The whole org/project/repo/grant surface has historically lacked these tests, so this isn't a regression, but the new revoke-mode branching is exactly the kind of logic that warrants one.

## LOW NITS

- **`grant.go` repo remove success message uses raw `args[0]`** (e.g. `"Revoked %s/%s from repo %s\n", provider, providerUserID, args[0]`): when the user passed a name, the message echoes the name while the operation targeted the resolved ULID. Same pattern in `org delete`/`project delete`/`repo delete` (`Deleted org %s` with `args[0]`). Minor — arguably friendlier to echo what the user typed — but it can read confusingly if resolution picked an unexpected target. Consider echoing the resolved ID, or both.
- **`resolveRepoRef` ULID passthrough silently ignores `--project`** (resolveref.go): documented in the helper comment and PR description, but if a user passes both a repo ULID and a `--project` that doesn't actually own it, there's no validation — the flag is just dropped. Acceptable as documented; flagging only so it's a conscious choice.
- **`pickRepo` ambiguity branch is effectively dead** given repo names are unique per project (the comment says so). The defensive multi-match error is fine to keep, but the "ambiguous" test case asserts behavior the API contract says can't occur — harmless.

No issues found in core resolution / `CoreOrigin` handling, the typed-enum role casts, or the spec-to-client consistency.
