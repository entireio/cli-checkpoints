## MEDIUM+ FINDINGS

**MEDIUM — Region-picker default pre-selection is silently discarded when the catalog has no `is_default` for the caller's jurisdiction, and the cross-product can fan out very large with no confirmation.** `repo_mirror_create_wizard.go` ~line 250 (`runMirrorCreateWizard`) → `mirrorTargets`. The wizard creates the full cross-product of every selected repo × every selected region and immediately fires `CreateMirror` for all of them (bounded only by `mirrorCreateConcurrency = 8`), with no summary/confirmation step. Selecting, say, 10 repos and 4 regions silently registers 40 mirror placements. Each `CreateMirror` is idempotent on (upstream, cluster) so this isn't catastrophic, but there's no "About to create N mirrors — proceed?" gate, and a mis-click in the multi-select is unrecoverable through the wizard. Consider a final confirm step showing the target count before the create fan-out begins.

**MEDIUM — Partial-failure leaves registered placements with no cleanup path, and the "N mirror(s) failed" exit can mask that some placements were successfully created.** `repo_mirror_create_wizard.go`, `createOneMirror`/`reportMirrorResults` (~lines 370–470). If `CreateMirror` succeeds but the subsequent clone wait times out or the clone reaches `failed`/`suspended`, `res.err` is set and the run exits non-zero via `NewSilentError(fmt.Errorf("%d mirror(s) failed"))` — but the placement *was* registered on the cluster and is left in place. There is no rollback and no message telling the user the placement exists despite the "failed" status. This is defensible (a timed-out clone may still complete server-side), but the results table shows `timed out`/`failed` with a clone URL present, which is ambiguous about whether the placement persists. Worth a one-line note in the failure detail clarifying that registered-but-not-ready placements remain and can be retried (the create is idempotent).
