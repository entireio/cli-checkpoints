The result is a UI side-effect baked into a shared fetch primitive that callers can neither redirect nor suppress.
- It's inconsistent *within the same diff*: the sibling spinner `refreshMetadataFromRemote(ctx, errW)` (resume.go) correctly threads the caller's `errW`; this one bypasses it. That asymmetry is the tell that the blob spinner is one layer too deep.
- **Blast radius is wider than "resume/explain":** `FetchBlobsByHash` is installed as the blob fetcher by `GetStrategy()` (config.go:70), and `GetStrategy()` is called from `lifecycle.go`, `hooks_git_cmd.go`, `hooks_claudecode_posttodo.go`, `doctor.go`, `clean.go`, `reset.go`, `rewind.go`. So any of those that triggers an on-demand blob fetch on a TTY will now emit `"Downloading checkpoint data from remote"` — including git hooks invoked from an interactive shell. The change was reasoned about as a resume/explain concern, but it actually fires for every consumer of the global strategy's store.
- The gate is `startSpinner → IsTerminalWriter(os.Stderr)`, which checks *only* the raw fd. It does **not** consult `interactive.CanPromptInteractively()`, so it ignores the agent sentinels (`GEMINI_CLI`, `COPILOT_CLI`, `GIT_TERMINAL_PROMPT=0`, `CI`) that the codebase uses elsewhere to mean "non-interactive." An agent running `entire` as a hook over a pty can therefore animate this spinner despite signalling non-interactive intent. (Note: the existing `startSpinner` call sites share this gating, so this isn't novel — but those sites are all explicit interactive commands; this one isn't.)

Proper-depth form: thread a writer (or a "progress sink") through `BlobFetchFunc`/`SetBlobFetcher` so the store fetches report to the owning command's stderr. **That is a refactor across the `checkpoint` package and every BlobFetcher wiring site — outside this diff.** Per the no-large-refactor constraint, I'm flagging rather than prescribing it.

Option (b) is a one-line tightening that meaningfully shrinks the unintended blast radius without the package-wide refactor.
